整体看，这一版已经明显比之前**收敛**了。我不会建议再增加 Agent、数据库、事件总线、状态机之类的东西。现在真正值得提升的，是少数几个**边界、数据模型和职责分配**问题。

我按“值得改 / 可以先不改 / 明确不要加”来判断。

## 一、最值得改的 6 个点

### 1. `knowledge.ts` / `learner.ts` / `conceptGraph.ts` 的职责还有一点重叠

现在：

* `conceptGraph` 负责知识关系
* `knowledge` 负责知识点内容
* `learner` 负责掌握度和推荐

这个方向是对的。

但你这里又让 `conceptGraph` 定义：

> `isMastered/isAttempted` 与薄弱阈值 `WEAK_*`

这其实已经开始把“知识关系”和“学习状态”混在一起了。

我建议非常简单地收紧：

```text
conceptGraph.ts
  只负责：
  prerequisite
  related
  closure
  topo

knowledge.ts
  只负责：
  knowledge metadata
  required
  misconceptions
  angles

learner.ts
  负责：
  mastery
  attempted
  weak
  coverage
  recommendation
```

也就是说：

> **图只回答“知识之间是什么关系”；Learner 才回答“用户掌握得怎么样”。**

你文档其实已经接近这个结论，只是当前 `conceptGraph` 还留了一点 learner policy。

---

### 2. `Question = 知识对象` 这个表述建议改掉

你现在写：

> `Question 是知识对象，题目只是它的 View`

但从整个模型看，实际上更准确的是：

```text
Knowledge
   ↑
 Question
   ↑
 SessionQuestion
```

因为知识点本身才是真正的一等公民；题目只是一个**可评估表达**。

你后面又已经明确写：

> 知识点是一等公民、题目只是它的 View。

所以这里存在一点术语冲突。

我建议统一为：

> **Knowledge 是学习对象，Question 是知识点的 assessment view，SessionQuestion 是一次训练实例。**

这个小改动很重要，因为以后你增加：

* explanation
* flashcard
* follow-up
* scenario
* system-design

它们都可以自然成为 knowledge 的不同 view，而不是继续往 `Question` 上堆职责。

---

### 3. `LearnerProfile.mastery = avgScore/100` 是当前最大的“过度简化”

你现在明确规定：

> `mastery = avgScore/100`，置信度由 attempts 表达，不做加权公式。

作为 MVP，我认为**完全可以先这样做**。

但是我建议至少把它从“概念定义”改成：

> **当前 mastery heuristic**

因为平均分实际上不等于 mastery。

例如：

```text
第一次：100
第二次：100
第三次：20
avg = 73
```

这和：

```text
第一次：20
第二次：100
第三次：100
avg = 73
```

学习状态显然不同。

你已经有：

* attempts
* trend
* recent sessions
* evidence

所以根本没必要现在引入复杂 Bayesian / ELO / IRT。

只要把语义改成：

```text
mastery = simple current heuristic
trend   = recent performance signal
attempts = confidence signal
evidence = provenance
```

即可。

**不要现在升级 scoring model。**

---

### 4. LLM Provider 与 `ai → domain` 的边界已经不错，但 `ai` 稍微有一点胖

目前 `ai` 同时承担：

* provider
* variant
* evaluation
* local
* Chrome
* fallback
* JSON extraction

这在当前规模下没问题。

但这里有一个地方值得固定：

> **LLM 不应该知道 `LearnerProfile`、`InterviewSession`、`adaptive strategy`。**

你已经写了这一点。

我建议进一步把接口概念固定成：

```ts
LLMProvider
  generateVariant(...)
  evaluateAnswer(...)
```

而不是未来继续扩成：

```ts
recommendNextQuestion()
buildLearningPlan()
analyzeLearner()
...
```

因为一旦这样做，**domain 就会逐渐被 LLM policy 接管**。

你的架构现在最好的地方恰恰是：

> **domain 决策，LLM 增强语言。**

这个原则应该继续保持。

---

### 5. `useAI` 现在语义有点过宽

目前：

> `useAI` 同时门控变体出题和开放题评分。

这个设计很简单，但从产品行为上有一点奇怪：

```text
useAI = false
```

结果同时意味着：

* 不改题目
* 不评分开放题

这两个能力其实不是一回事。

不过这里我**不建议马上增加复杂配置**。

最简单的演进：

```ts
useAI: boolean
```

先保留。

以后真的出现用户需求，再拆：

```ts
enableVariants
enableEvaluation
```

现在不要为了“架构纯洁”提前做。

---

### 6. `SessionQuestion` 最好明确区分“题目快照”和“题目引用”

你现在：

> `SessionQuestion = session instance`
>
> 会持有 `question snapshot`。

这个设计我认为是对的。

但最好明确两层：

```ts
type SessionQuestion = {
  questionId: string
  topic: string
  format: ...
  question: string
  options?: ...
  referenceAnswer?: ...
  rubric?: ...
  answer?: ...
  evaluation?: ...
}
```

也就是：

> **session 保存“当时看到的东西”，而不是实时重新解析题库。**

特别是你以后修改题库时：

```text
Question v1
Question v2
```

历史 session 仍然应该保持 v1 的内容。

你现在实际上已经这么做了，只是建议把这个作为**明确不变量**写出来，而不是只是实现细节。

---

# 二、几个现在不要动的地方

### 1. 不要引入数据库

你现在：

```text
localStorage
```

对于：

* LearnerProfile
* SessionRecord
* settings

是合理的。

而且你已经有：

> 数据量大、对话/流式结果增加后再迁 IndexedDB。

我赞成。

**现在不要 SQLite / Dexie / IndexedDB abstraction / repository pattern。**

---

### 2. 不要重新引入 Agent

这一点非常正确：

> 当前 LLM 都是 one-shot；只有真正需要“追问 → 回答 → 继续追问”时才引入 pi-agent-core。

不要因为这是“AI Interview App”就硬塞一个 Agent。

现在：

```text
InterviewEngine
+
LLMProvider
```

足够。

真正出现：

```text
Question
 → candidate answer
 → interviewer follow-up
 → clarification
 → challenge
 → answer
 → next question
```

再考虑 agent loop。

---

### 3. 不要做独立的 Question Repository

你现在：

> `import.meta.glob eager`
>
> 不建 index / database layer。

非常合理。

237 题完全没有必要：

```text
QuestionRepository
QuestionIndex
QuestionDAO
QueryService
```

这种 enterprise-style abstraction。

---

### 4. `@dagrejs/graphlib` 现在足够

你已经明确限定：

> 只在 `conceptGraph` 模块内部使用。

很好。

不要再为了“未来 DAG 更复杂”引入一个 graph abstraction。

---

# 三、我认为还有一个很值得做、但很小的改进

## 给整个系统增加一个非常清晰的“核心数据流”

现在文件很多，但其实产品核心只有这条：

```text
Question Bank
      │
      ▼
Knowledge
      │
      ▼
Interview Definition
      │
      ▼
Interview Engine
      │
      ▼
Session
      │
      ▼
Answer
      │
      ▼
Evaluation
      │
      ▼
Learner Signal
      │
      ▼
Learner Profile
      │
      ▼
Recommendation
      │
      └──────────────► Interview Definition
```

也就是：

> **题库 → 训练 → 评估 → 学习信号 → 推荐 → 下一次训练**

你其实已经写出来了。

我甚至认为这个 loop 才是系统真正的“主架构”。

其他东西都是支撑：

```text
LLM Provider
Concept Graph
Knowledge Metadata
Storage
UI
```

这个层次一旦明确，你以后就不容易 over-design。

---

# 四、我会做一个更重要的小调整：把 `Knowledge` 提到架构中心

现在你的文档里已经有：

> “知识点是一等公民，题目只是它的 View”。

我认为这是**这版架构最正确的决定之一**，甚至可以进一步明确成：

```text
                     Knowledge
                    /    |    \
                   /     |     \
                  ↓      ↓      ↓
             Question  Concept  Learner
               View     Graph   State
                 │
                 ↓
             Session
                 │
                 ↓
             Evaluation
                 │
                 ↓
           Learner Signal
```

这样很多未来需求天然解决：

```text
一个 Knowledge
 ├─ MCQ
 ├─ Open Question
 ├─ Scenario
 ├─ Calculation
 ├─ System Design
 └─ Follow-up
```

而不是：

```text
Question
QuestionVariant
QuestionTransform
QuestionFollowup
QuestionScenario
...
```

你前面一直在考虑“选择题 ↔ 开放题”，这个模型尤其适合。

---

# 五、还有一个我会修的小地方：`conceptGraph` 不一定需要 `Graphlib` 单例

不是因为它错，而是：

> 现在 graph 只不过是 prerequisite + related 两种边。

实际上用普通：

```ts
Record<TopicId, TopicId[]>
```

都可能够用。

但是因为你已经需要：

* topsort
* closure
* cycle detection

所以保留 `graphlib` **完全合理**。

只是：

> **不要让 Graphlib 的数据结构向 domain 其他地方泄漏。**

这一点你已经做得不错。

# 六、整体架构，我会收敛成这样

```text
                       ┌──────────────┐
                       │     UI       │
                       └──────┬───────┘
                              ↓
                     ┌────────────────┐
                     │ InterviewEngine│
                     └───────┬────────┘
                             ↓
        ┌────────────────────┼────────────────────┐
        ↓                    ↓                    ↓
   ┌─────────┐        ┌────────────┐       ┌──────────┐
   │  Quiz   │        │ Evaluation │       │ Learner  │
   └────┬────┘        └─────┬──────┘       └────┬─────┘
        │                    │                   │
        └────────────────────┼───────────────────┘
                             ↓
                        ┌──────────┐
                        │ Knowledge│
                        └────┬─────┘
                             │
                 ┌───────────┴───────────┐
                 ↓                       ↓
          ┌─────────────┐        ┌─────────────┐
          │ Question DB │        │ ConceptGraph │
          └─────────────┘        └─────────────┘


                   ┌──────────────────┐
                   │    LLMProvider   │
                   │  one-shot only   │
                   └────────┬─────────┘
                            │
                  ┌─────────┼─────────┐
                  ↓         ↓         ↓
               Chrome     Local     Cloud
```

核心原则只有四句话：

1. **Knowledge 是中心，Question 是 View。**
2. **InterviewEngine 掌管业务流程。**
3. **Domain 决定，LLM 只增强。**
4. **Learner Memory 驱动下一次训练。**

我认为这已经足够支撑你当前产品，**不需要再增加任何“大架构”**。

如果只允许我改三件事，我会选：

**① 统一 Knowledge / Question / SessionQuestion 的概念层级；
② 把 ConceptGraph 与 Learner State 完全分开；
③ 把 `mastery` 明确成 heuristic，而不是“学习能力的真实度量”。**

其他地方目前都可以先保持。
