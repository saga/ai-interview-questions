对。基于你现在这个结论，我会把**“如何补充题库”**再往前推进一步：不要把它理解成“找题 vs 生成题”的二选一，而应该拆成 **Knowledge Coverage → Question Coverage → Question Authoring** 三层。

### 1. 最核心的原则

你现在应该维护的不是一个单纯的 `questions.json`，而是：

```text
Knowledge
   ↓
Knowledge Coverage
   ↓
Question Coverage
   ↓
Question Bank
```

也就是说：

> **先发现知识覆盖缺口，再决定需要什么类型的题，最后才决定是从现有题库找题还是让 LLM 生成题。**

这和“看到一个知识点就让 LLM 出一道题”完全不同。

---

# 2. 补题库时，推荐这个流程

例如你现在有：

```text
MoE
├── basic-concept
├── routing
├── load-balancing
├── expert-capacity
├── auxiliary-loss
└── distributed-training
```

首先不要问：

> “给 MoE 生成 20 道题。”

而应该先建立一个 **Knowledge Coverage Matrix**：

| Knowledge            | Concept | Mechanism | Trade-off | Scenario | Design | Misconception |
| -------------------- | ------: | --------: | --------: | -------: | -----: | ------------: |
| MoE basic            |       ✓ |         ✓ |           |          |        |             ✓ |
| Routing              |       ✓ |         ✓ |         ✓ |        ✓ |        |             ✓ |
| Load balancing       |       ✓ |         ✓ |         ✓ |        ✓ |      ✓ |             ✓ |
| Expert capacity      |       ✓ |         ✓ |         ✓ |        ✓ |      ✓ |               |
| Aux loss             |       ✓ |         ✓ |         ✓ |          |      ✓ |             ✓ |
| Distributed training |       ✓ |         ✓ |         ✓ |        ✓ |      ✓ |             ✓ |

一看就知道：

```text
MoE / distributed-training / design
MoE / load-balancing / scenario
MoE / expert-capacity / misconception
```

是缺口。

**这才是你下一步需要补题的地方。**

# 3. 然后再问：这个缺口有没有现成题？

对于每一个 coverage gap：

```text
Knowledge Gap
      ↓
Question Bank Search
      ↓
   ┌──┴──┐
   │     │
 有题    没题
   │     │
   ↓     ↓
复用     生成
```

所以实际上应该：

### 第一优先级：复用已有题

因为已有题：

* 已验证
* 有答案
* 有 rubric
* 有 difficulty
* 可以比较历史表现
* 可以控制面试体验

### 第二优先级：变体

如果已有：

```text
"什么是 MoE？"
```

但是缺少：

```text
"为什么 MoE 比 dense Transformer 更容易出现负载不均衡？"
```

不一定需要完全生成新题。

可以：

```text
existing question
        ↓
LLM transformation
        ↓
new angle / difficulty / type
```

### 第三优先级：LLM 生成新题

只有真正发现：

```text
Knowledge × Question Dimension
```

没有题的时候，才生成。

---

# 4. 但是这里还有一个非常重要的东西：Question Blueprint

我甚至建议你**不要让 LLM 直接从 Knowledge 生成最终 Question**。

中间加一个很轻量的：

```text
QuestionBlueprint
```

例如：

```json
{
  "knowledge": "moe-load-balancing",
  "target": "mechanism",
  "angle": "tradeoff",
  "difficulty": "hard",
  "type": "open",
  "purpose": "test whether learner understands why routing imbalance occurs",
  "expectedConcepts": [
    "router",
    "expert capacity",
    "token distribution",
    "overflow"
  ]
}
```

然后：

```text
QuestionBlueprint
        ↓
   LLM Authoring
        ↓
Question
```

这样 LLM 的任务就从：

> “自己决定考什么，然后自己出题”

变成：

> “按照已经确定的考察目标，把题目写出来。”

这会稳定很多。

# 5. 于是你的题库建设可以变成一个非常简单的 Pipeline

我建议最终就是：

```text
              Knowledge Base
                    │
                    ▼
           Coverage Analyzer
                    │
                    ▼
        ┌─────────────────────┐
        │ Coverage Gap        │
        │                     │
        │ topic               │
        │ angle               │
        │ difficulty          │
        │ question type       │
        └──────────┬──────────┘
                   │
                   ▼
            Question Search
                   │
          ┌────────┴────────┐
          │                 │
       existing           missing
          │                 │
          ▼                 ▼
       reuse          Question Blueprint
                            │
                            ▼
                       LLM Generate
                            │
                            ▼
                       Validation
                            │
                            ▼
                       Question Bank
```

这里的 `Validation` 很重要：

```text
LLM generated
     ↓
answer correctness
     ↓
rubric consistency
     ↓
knowledge alignment
     ↓
difficulty
     ↓
ambiguity
```

通过以后才进入正式题库。

这比“再给我生成 10 道 MoE 题”有价值得多。

# 7. 而且 Knowledge 本身也不应该无限扩张

这里要避免另一个坑：

```text
LLM
 ↓
发现一个新知识点
 ↓
添加 Knowledge
 ↓
生成题
 ↓
又发现新知识点
 ↓
...
```

最后变成知识图谱大爆炸。

我建议：

### Knowledge 有两个来源

**A. Curated Knowledge**

你主动定义：

```text
Transformer
MoE
RAG
Agent
MCP

Memory

...
```

这是核心 syllabus。

**B. Derived Knowledge**

LLM 可以发现：

```text

```

但不要自动加入正式 Knowledge。

而是：

```text
LLM发现
   ↓

   ↓
人工/规则确认
   ↓

```

这样你的知识体系不会失控。

# 9. 这会让你的系统形成一个很漂亮的闭环

最终不是：

```text
Question Bank
      ↓
Interview
      ↓
Score
```

而是：

```text
             Knowledge
                 ↓
          Coverage Model
                 ↓
           Question Bank
                 ↓
             Interview
                 ↓
           Learner Signal
                 ↓
          Knowledge State
                 ↓
        Coverage / Gap Update
                 ↓
          Question Selection
                 ↓
             Interview
```

而**题库建设**则是另一条慢速 pipeline：

```text
Knowledge
    ↓
Coverage Analysis
    ↓
Gap Detection
    ↓
Existing Question Search
    ↓
   ┌───────────────┐
   │ reuse/variant │
   │      or       │
   │ LLM generate  │
   └───────┬───────┘
           ↓
       Validation
           ↓
       Question Bank
```

### 所以回答你最初的问题：

**不要直接“找题”，也不要直接“从知识点让 LLM 生成题”。**

最合适的是：

> **先从 Knowledge 定义应该覆盖什么 → 找出 Question Coverage Gap → 优先从题库复用 → 没有合适题时做变体 → 仍然缺失才让 LLM 按 Question Blueprint 生成 → 验证后进入题库。**

而你的**运行时面试**仍然完全可以保持：

> **Knowledge/Learner State → Selection Policy → Question Bank → Question**

这两条 pipeline 分开以后，你的架构会非常清楚，而且不会为了“AI 自动出题”而把系统设计复杂。



-----------


如果你现在要**真正开始补题库**，我建议不要先写“自动生成题库 Agent”。先做一个非常轻量的 **题库生产流水线**，人工定义方向，LLM 辅助生产。

核心原则就一句：

> **先补知识覆盖，再补题目覆盖；先复用，再变体，最后生成。**

## 1. 第一步：先把 Knowledge 定义稳定

不要一上来就生成题。

例如你要补：

```text
MoE
```

先整理成：

```text
MoE
├── concept
│   ├── sparse activation
│   ├── expert
│   └── router
│
├── mechanism
│   ├── token routing
│   ├── top-k routing
│   ├── expert capacity
│   └── load balancing
│
├── tradeoff
│   ├── compute efficiency
│   ├── communication cost
│   └── routing instability
│
├── scenario
│   ├── training
│   └── inference
│
├── design
│   └── distributed MoE
│
└── misconception
    ├── MoE ≠ smaller model
    └── sparse ≠ cheap communication
```

这里不要追求完整知识图谱。

**面试系统需要的是“可考察的知识结构”，不是百科全书。**

---

# 2. 第二步：给 Knowledge 加 Question Coverage

这是我认为你现在最应该增加的东西。

例如：

```json
{
  "knowledge": "moe-load-balancing",
  "coverage": {
    "concept": true,
    "mechanism": true,
    "tradeoff": false,
    "scenario": false,
    "design": false,
    "misconception": true
  }
}
```

但我甚至建议不要只记录 `true/false`。

可以直接统计：

```text
MoE / load-balancing

concept       1
mechanism     3
tradeoff      0
scenario      0
design        1
misconception 1
```

于是你马上知道：

> 这个知识点不是“没有题”，而是 **tradeoff/scenario 缺题**。

这非常重要。

---

# 3. 第三步：建立一个简单的 Question Blueprint

补题时不要直接让 LLM：

> “生成一道 MoE 题。”

而是先指定：

```json
{
  "knowledge": "moe-load-balancing",
  "angle": "tradeoff",
  "difficulty": "hard",
  "type": "open",
  "purpose": "判断候选人是否理解负载均衡机制的实际代价",
  "expected_concepts": [
    "expert utilization",
    "auxiliary loss",
    "routing",
    "capacity"
  ]
}
```

这一步可以完全由你的程序生成，甚至不用 LLM。

---

# 4. 第四步：先搜索已有题

然后做：

```text
Blueprint
   ↓
Question Bank Search
```

判断：

### A. 已经有完全合适的题

```text
→ reuse
```

不要生成。

### B. 有相近题

```text
→ variant
```

例如：

```text
已有：
为什么 MoE 需要 load balancing？

Blueprint：
如果取消 auxiliary loss，MoE 会出现什么问题？
```

这种就可以让 LLM 基于已有题生成变体。

### C. 完全没有

```text
→ generate
```

这时候才真正让 LLM 创作。

---

# 5. 第五步：生成时，LLM 的输入一定要“受约束”

不要：

```text
请生成一道关于 MoE 的面试题。
```

而是给：

```text
Knowledge
Question Blueprint
Expected concepts
Difficulty
Question type
Existing similar questions
```

例如：

```text
Knowledge:
moe-load-balancing

Target:
tradeoff

Difficulty:
hard

Question type:
open

Expected concepts:
- expert utilization
- routing
- auxiliary loss
- capacity

Similar questions:
...

Generate one interview question.
Do not introduce concepts outside the target knowledge unless necessary.
```

这样生成质量会高很多。

---

# 6. 第六步：生成后必须 Validation

这是你这个项目里非常值得做的一步。

不要：

```text
LLM Generate
    ↓
直接进题库
```

而是：

```text
LLM Generate
      ↓
LLM Validate
      ↓
Publish
```

验证至少检查：

### Knowledge alignment

是不是在考：

```text
moe-load-balancing
```

而不是偷偷变成：

```text
distributed training
```

### Answerability

这个问题有没有明确的正确回答空间？

### Difficulty

标记 `hard`，实际是不是只有基础概念？

### Ambiguity

是否存在多个合理答案，但 rubric 没办法区分？

### Rubric quality

尤其是开放题。

---

# 7. 对开放题，Rubric 比 Question 本身更重要

例如：

> 为什么 MoE 需要 load balancing？

不能只保存：

```json
{
  "answer": "为了让专家负载均衡"
}
```

而应该：

```json
{
  "rubric": {
    "essential": [
      "理解 token routing",
      "理解 expert utilization",
      "理解负载不均衡造成的效率问题"
    ],
    "strong": [
      "解释 auxiliary loss",
      "解释 capacity constraint"
    ],
    "bonus": [
      "讨论通信成本",
      "讨论训练稳定性"
    ]
  }
}
```

这样你的评分 Agent 才有稳定的依据。

---

# 8. 特别注意：不要让一个 LLM 同时负责所有事情

这是我比较建议你避免的：

```text
LLM
 ├── 决定知识
 ├── 决定考点
 ├── 出题
 ├── 定答案
 ├── 定难度
 └── 定 rubric
```

这样很容易产生“自己出题、自己证明自己正确”。

最好拆成：

```text
Knowledge
    ↓
Coverage / Blueprint
    ↓
Question Generator
    ↓
Question Validator
    ↓
Question Bank
```

而运行时：

```text
Learner State
    ↓
Adaptive Policy
    ↓
Question Selector
```

**Generator 和 Selector 是两件完全不同的事情。**

# 9. 实际补题时，我建议你采用这个顺序

假设你现在要补：

```text
Transformer
MoE
RAG
Agent
MCP
Tool Calling
Memory
Context Engineering
```

不要一次生成几百道。

可以：

### Phase 1：每个 Knowledge 建基础 coverage

例如每个知识点先保证：

```text

```

也就是先形成：


### Phase 2：根据实际面试结果补题

这时候你会获得非常有价值的数据：

```text

   ↓

   ↓

   ↓

```

比如发现：

```text

```

那么下一轮不是：

> 再生成 20 道 Tool Calling。

而是：

> **补 Tool Calling / scenario + tradeoff。**

这就是你的系统真正开始“自我完善”的地方。

# 10. 还有一个非常重要的注意事项：不要过度细分 Knowledge

比如不要搞成：

```text
MoE
 └─ Router
     └─ TopK
         └─ Top2
             └─ Token Routing
                 └─ Expert Capacity
                     └─ Capacity Factor
```

很快你会得到一个巨大的知识树。

对于你的面试系统，我更建议：

```text

├── routing
├── load balancing
├── capacity
└── distributed training
```

**Knowledge 粗一点，Question Angle 细一点。**

这是非常重要的设计原则。

## 我会把整个系统分成两个速度

**慢速：题库生产**

```text
Knowledge
 → Coverage
 → Blueprint
 → Search
 → Variant/Generate
 → Validate
 → Question Bank
```

**快速：用户面试**

```text
Learner State
 → Training Target
 → Question Selection
 → Question
 → Answer
 → Score
 → Learner State
```

这两个千万不要混在一起。

尤其是**不要让线上面试过程中发现一个知识缺口，就现场生成一道题并直接使用**。第一版可以这么做实验，但正式架构最好让生成题进入 `candidate question` 状态，经过验证后再进入正式题库。

### 如果让我现在帮你排优先级

我会按：

**① Knowledge schema → ② Coverage matrix → ③ Blueprint → ④ coverage CLI → ⑤ LLM question generator → ⑥ validator**

这个顺序做。

其中 **①～④ 几乎不需要增加复杂架构，却会直接决定你后面题库质量**。你现在最不应该做的反而是先写一个很复杂的“AI 出题 Agent”。
