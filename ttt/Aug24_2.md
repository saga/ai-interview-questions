可以。结合你现在这个 Interview Trainer 的架构，我建议 **不要做“一次性全面 Zod 化”**，而是分 4 个阶段逐步迁移：

> **先建立 schema → 接管 JSON 数据 → 接管 AIConfig → 接管 LLM 边界 → 最后处理持久化和业务 invariant。**

核心原则是：

> **Zod 负责“数据长什么样”；domain 负责“数据之间是否合理”。**

这点非常重要。比如：

```text
Zod
├── question.type 是不是合法值
├── difficulty 是不是合法值
├── options 是不是数组
└── question.question 是不是 string

Domain validation
├── 单选题必须恰好一个正确答案
├── 多选题至少两个正确答案
├── topic 必须存在于 knowledge
├── prerequisite 不能形成环
└── question 必须真的覆盖某个 knowledge topic
```

Zod 4 现在已经稳定，支持 TypeScript 类型推导、runtime validation，而且自带 JSON Schema 转换能力。([Zod][1])

# 四、不要一开始设计一个巨大的 QuestionSchema

你的题型已经支持：

* single
* multiple
* open

所以推荐使用 **discriminated union**。

例如：

```ts
// src/schemas/question.ts

import { z } from "zod";

const baseQuestionSchema = z.object({
  id: z.string().min(1),
  category: z.string().min(1),
  topic: z.string().min(1),

  tags: z.array(z.string()).default([]),

  difficulty: z.enum([
    "easy",
    "medium",
    "hard"
  ]),

  question: z.string().min(1),
});
```

然后：

```ts
const choiceOptionSchema = z.object({
  id: z.string().min(1),
  text: z.string().min(1),
});
```

Single：

```ts
const singleQuestionSchema = baseQuestionSchema.extend({
  type: z.literal("single"),

  options: z.array(choiceOptionSchema).min(2),

  answer: z.string().min(1),
});
```

Multiple：

```ts
const multipleQuestionSchema = baseQuestionSchema.extend({
  type: z.literal("multiple"),

  options: z.array(choiceOptionSchema).min(2),

  answer: z.array(z.string()).min(1),
});
```

Open：

```ts
const openQuestionSchema = baseQuestionSchema.extend({
  type: z.literal("open"),

  answer: z.string().optional(),

  expectedConcepts: z.array(z.string()).default([]),
});
```

最后：

```ts
export const questionSchema = z.discriminatedUnion("type", [
  singleQuestionSchema,
  multipleQuestionSchema,
  openQuestionSchema,
]);
```

Zod 本身支持 union/discriminated union 这类组合方式，非常适合你的多题型模型。([Zod][2])

# 五、非常重要：让 Zod 成为 TypeScript 类型来源

如果你现在有：

```ts
export interface Question {
  id: string;
  type: ...
  ...
}
```

不要继续维护两套。

应该：

```ts
export type Question = z.infer<typeof questionSchema>;
```

也就是：

```text
                    Question Schema
                         │
              ┌──────────┴──────────┐
              ▼                     ▼
        Runtime validation     TypeScript type
              │                     │
              └──────────┬──────────┘
                         ▼
                     Question
```

这就是 Zod 最大的价值之一：

> **schema 写一次，runtime validation + TypeScript type 两边同时得到。**

官方也把 static type inference 作为 Zod 的核心能力。([Zod][1])

# 六、但不要把所有业务规则塞进 Zod

这是迁移过程中最容易犯的错误。

例如：

```ts
const questionSchema = z.object({
  topic: z.string(),
});
```

Zod 可以检查：

```text
topic 是 string
```

但是不要写：

```ts
.refine(q => knowledge.has(q.topic))
```

因为这已经不是 Question 自身的 schema 了。

它依赖：

```text
Question
+
Knowledge Bank
```

这是 domain invariant。

应该：

```ts
questionSchema.parse(rawQuestion);
```

然后：

```ts
validateQuestionAgainstKnowledge(
  question,
  knowledge
);
```

所以最终：

```text
                    Raw JSON
                       │
                       ▼
                 Zod Schema
                       │
                 shape valid?
                    /      \
                  no        yes
                  │          │
               error         ▼
                       Domain validation
                              │
                       cross-reference
                              │
                         business valid?
```

这会让你的 architecture 很干净。

```ts
import { questionSchema } from "@/schemas/question";
```

```ts
export function loadQuestionBank(raw: unknown): Question[] {
  const result = z.array(questionSchema).safeParse(raw);

    throw new Error(
      formatQuestionValidationError(result.error)
    );

  return result.data;
}
```

# 八、不要直接把 ZodError 扔到 UI

例如：

```ts
questionSchema.parse(data);
```

产生：

```text

```

这对开发者很好。

但 UI 不应该直接显示：

```text

```


```ts
export function formatSchemaError(error: z.ZodError) {
  return error.issues.map(issue => ({
    path: issue.path.join("."),

}
```

然后：

```text
Question bank validation failed

questions[17]
options[2].text
→ Required
```

这样对于你维护大量 JSON 题库会非常有用。

# 十、ConceptGraph 也用 Zod，但不要让 Zod 做图算法

你的 ConceptGraph 是非常适合这种分层的：

```text
Zod
 ↓
Graph structure valid
 ↓
Domain
 ↓
DAG / prerequisite / closure
```

例如：

```ts
const conceptGraphSchema = z.object({
  nodes: z.array(
    z.object({
      id: z.string().min(1),
    })
  ),

  prerequisite: z.record(
    z.string(),
    z.array(z.string())
  ),

  related: z.record(
    z.string(),
    z.array(z.string())
  ),
});
```

Zod 检查：

```text
nodes 是数组
node.id 是 string
prerequisite 是 object
edges 是 string[]
```

然后你的 `conceptGraph.ts` 检查：

```text
A → B → C
```

是不是 DAG。

不要把 DFS/topological-sort 塞到 Zod `.refine()`。

# 十三、Schema 和 sanitize 要分开

你现在可能有类似：

```text

```

不要因为用了 Zod 就删除所有 sanitize。

应该区分：

### Schema validation

```text
这个值是否合法？
```

### Sanitization

```text
这个值是否应该被清洗/规范化？
```

例如：

```ts
const providerSchema = z.object({
```

```ts
function normalizeProvider(
  provider: Provider

  return {
    ...provider,
    baseUrl: provider.baseUrl?.replace(/\/$/, "")
  };
```

最终：

```text
raw
 ↓
Zod parse
 ↓
validated
 ↓
normalize
 ↓
domain config
```

不要把所有 transform 都塞进 Zod。

# 十九、Phase 7：Persisted data 最后迁移

你的：


也应该 schema 化。

例如：

```ts
const sessionRecordSchema = z.object({

  createdAt: z.string(),

    attemptSchema

  completed: z.boolean(),
```

```ts
function loadSession(id: string) {
  const raw =
```


* 手工修改
* migration
* bug
* 浏览器异常

# 二十、但是 Persistence 需要 Version

这里不要直接：

```ts
sessionRecordSchema.parse(raw)
```

然后未来改 schema 就炸掉。

建议：

```ts
const persistedSessionSchema = z.object({
  version: z.literal(1),
  data: sessionRecordSchema,
});
```

以后：

```text
version 1
version 2
version 3
```

变更时：

```text
raw
 ↓
detect version
 ↓
migration
 ↓
current schema
```

例如：

```ts
function loadSession(raw: unknown) {
  const parsed =
    persistedSessionSchema.parse(raw);

  return migrateSession(parsed);
}
```

**Migration 仍然是 domain/storage logic，不要塞进 Zod。**

# 二十一、Phase 8：建立统一的 parse API

这是整个迁移过程中非常值得做的一步。

不要让业务代码到处出现：

```ts

```

例如：

```text
application/
  interviewEngine.ts

components/
  Settings.tsx

storage/
  sessionStorage.ts

llm/
  evaluator.ts
```

全部直接调用 Zod。

这样 Zod 会渗透整个代码库。

我更推荐：

```text
schemas/
    ↓
boundary adapters
    ↓
domain/application
```

例如：

```ts
// questionLoader.ts

export function parseQuestion(
  input: unknown

  return questionSchema.parse(input);
}
```

```ts

  input: unknown
```


于是：

```text
Zod
 ↓
Boundary
 ↓
Trusted domain object
```

进入 domain 后：

> domain 不需要知道 Zod 存在。

这个非常符合你现在强调的 domain/application 分层。

# 二十七、测试策略也一起改

每个 schema 至少：


```ts

  it("rejects missing question text", () => {
    expect(() =>

  it("rejects unknown question type", () => {
```

# 二十九、我认为你的项目最终应该达到这个状态

```text
                         Interview Trainer
                                │
             ┌──────────────────┴──────────────────┐
             │                                     │
         Data Contracts                       Business Logic
             │                                     │
          Zod Schema                         Pure Domain
             │                                     │
      ┌──────┼───────┐                     ┌───────┼──────┐
      │      │       │                     │       │      │
   Question Knowledge AIConfig          Quiz   Adaptive Graph
      │      │       │                     │       │      │
      └──────┼───────┘                     └───────┼──────┘
             │                                     │
             ▼                                     ▼
       Runtime Validation                   Domain Invariants
             │                                     │
             └─────────────────┬───────────────────┘
                               ▼
                         InterviewEngine
```

这里最重要的是：

> **Zod 不应该成为你的业务层。它应该成为你的“数据边界层”。**

这与你现在的架构其实非常契合：你的 `domain` 已经是纯函数、`InterviewEngine` 负责 orchestration，而 LLM 是可选增强；Zod 只需要补上目前比较薄弱的 **runtime contract** 这一层。
