可以，而且我认为这其实是你这个 **AI Trainer App 当前架构最值得做的一次调整**。

你现在的问题不是“要不要加 Agent”，而是：

> **把 `pi-agent-core` 放在哪里，才能让 Agent 成为 Trainer 的运行时核心，而不是 LLM 的一个附加能力？**

我的建议是：**不要让 `pi-agent-core` 负责题库、评分、UI 状态这些领域逻辑；让它负责“面试过程中的自主决策循环”。**

### 先给结论

你现在的架构里，可以把下面这些东西交给 `@earendil-works/pi-agent-core`：

| 当前能力            |        是否交给 pi-agent-core | 作用                                                 |
| --------------- | ------------------------: | -------------------------------------------------- |
| 面试流程控制          |                **✅ 强烈建议** | Agent 决定下一步问什么/追问/结束                               |
| 追问生成            |                     **✅** | 根据用户当前答案自主决定是否追问                                   |
| 动态选择题型          |                     **✅** | open ↔ choice、difficulty 调整                        |
| 根据用户表现选择知识点     |                     **✅** | 从“固定抽题”升级为 adaptive interview                      |
| 面试上下文管理         |                     **✅** | 当前题、历史回答、评分、弱点等作为 context                          |
| Tool calling    |                     **✅** | 查询题库、知识图谱、用户历史、评分等                                 |
| 评分              | **⚠️ Agent 调用 evaluator** | Agent 不直接实现评分算法                                    |
| 题库              |                     **❌** | 仍然是 domain data                                    |
| Knowledge graph |                     **❌** | 仍然是 domain model                                   |
| Zod schema      |                     **❌** | 仍然由你的 application domain 定义                        |
| UI state        |                     **❌** | React/Next/etc. 管                                  |
| persistence     |                     **❌** | DB/local storage 管                                 |
| LLM provider    |                    **部分** | pi-agent-core 负责调用模型，但 provider abstraction 仍应由你控制 |

核心架构可以变成：

```text
                    AI Trainer
                         │
              ┌──────────▼──────────┐
              │     Interview       │
              │       Agent         │
              │  pi-agent-core      │
              └──────────┬──────────┘
                         │
             ┌───────────┼───────────┐
             │           │           │
          Tools       Context     Policies
             │           │           │
      ┌──────▼─────┐ ┌──▼──────┐ ┌──▼────────┐
      │ Question   │ │ Memory  │ │ Interview │
      │ Bank       │ │ /History│ │ Strategy  │
      └────────────┘ └─────────┘ └───────────┘
             │           │           │
             └───────────┼───────────┘
                         │
                  ┌──────▼──────┐
                  │ Evaluator   │
                  │ LLM / Rules │
                  └─────────────┘
```

这比：

```text
Question Bank
     ↓
Random Selector
     ↓
LLM generates question
     ↓
LLM scores answer
```

要 **AI-native 很多**。

# 1. 最值得改的是 Interview Orchestrator

你之前设计里最容易变成“workflow”的地方，就是：

```text
start
 ↓
select question
 ↓
ask
 ↓
answer
 ↓
evaluate
 ↓
select next question
 ↓
...
```

如果这些步骤全部由 application code 写死：

```ts
if (score < 0.5) {
  askFollowUp()
} else {
  nextQuestion()
}
```

那其实还是一个传统 workflow。

**pi-agent-core 最适合接管这里。**

变成：

```text
InterviewAgent
    │
    ├── inspect_context
    │
    ├── decide_action
    │
    ├── call_tool
    │
    ├── observe_result
    │
    ├── decide_next_action
    │
    └── repeat
```

例如 Agent 可以自主决定：

```text
User answers:
"What is the difference between RAG and fine-tuning?"

        ↓

Evaluator:
score = 0.55
missing = ["knowledge injection",
           "parameter update",
           "retrieval failure modes"]

        ↓

Agent reasoning:

Candidate understands basic distinction,
but lacks engineering trade-offs.

        ↓

Agent chooses:

ask_followup(
  topic="rag-vs-finetuning",
  angle="scenario",
  difficulty="hard"
)
```

而不是你的代码决定：

```ts
if (score < 0.6) {
   followUp()
}
```

**这就是 Agent 真正产生价值的地方。**

# 2. Question Bank 应该变成 Agent Tool

这一点非常重要。

不要让 Agent 直接操作：

```ts
questions.json
```

而是提供 tool：

```ts
searchQuestions()
getQuestion()
findRelatedQuestions()
findQuestionsByConcept()
```

例如：

```ts
const tools = {
  searchQuestions: ...,
  getQuestion: ...,
  findRelatedQuestions: ...,
  getKnowledgeNode: ...,
  getUserWeaknesses: ...,
}
```

于是 Agent 可以：

```text
Agent
 │
 ├── get_user_profile()
 │
 ├── get_weak_topics()
 │
 ├── search_questions({
 │      topic: "transformer",
 │      difficulty: "hard"
 │   })
 │
 └── select_question()
```

这样你之前讨论的：

> “到底是直接从题库抽题，还是先找知识点，再找题？”

其实可以自然解决。

**Agent 负责策略，domain service 负责执行。**

# 3. Knowledge → Question 的关系尤其适合 Agent

你现在已经有：

```text
Knowledge
   │
   ├── transformer
   ├── attention
   ├── MoE
   ├── RAG
   ├── Agent
   └── ...
```

以及：

```text
Questions
   │
   ├── q1
   ├── q2
   ├── q3
   └── ...
```

我不建议 Agent 直接“生成一道题”。

更好的方式：

```text
                Agent
                  │
        "What should I test?"
                  │
                  ▼
          Knowledge Graph
                  │
         "MoE routing"
                  │
                  ▼
            Question Bank
                  │
          q17 / q43 / q91
                  │
                  ▼
               Agent
                  │

```

所以 Agent 的核心问题变成：

> **What should I test next?**

而不是：

> Generate me a question.

这是非常大的区别。

# 4. Adaptive Difficulty 是另一个 Agent 核心能力

例如：

```text
Candidate
   │
   ├── Transformer fundamentals: 90%
   ├── Attention: 85%
   ├── MoE: 65%
   ├── RAG: 55%
   └── Agent: 40%
```

Agent 可以判断：

```text
Current weakness:
Agent fundamentals

Current confidence:
low

Therefore:
don't ask another definition question.

Instead:
ask scenario question.
```

于是：

```text
Knowledge
   ↓
weakness
   ↓
angle
   ↓
difficulty
   ↓
question
```

全部成为 Agent decision。

这比一个：

```ts
selectNextQuestion()
```

函数强很多。

# 5. Follow-up 应该成为 Agent 的核心 loop

这是我最推荐你做的地方。

传统：

```text
Question
 ↓
Answer
 ↓
Score
 ↓
Next Question
```

Agent：

```text
Question
 ↓
Answer
 ↓
Evaluate
 ↓
Agent observes
 ↓
┌─────────────────────┐
│ What should I do?   │
├─────────────────────┤
│ follow-up?          │
│ clarify?            │
│ challenge?          │
│ change topic?       │
│ increase difficulty?│
│ decrease difficulty?│
│ finish?             │
└─────────────────────┘
```

例如：

### 用户回答很好

```text
score: 0.9

Agent:
Candidate clearly understands the concept.

→ increase difficulty
→ move from concept → architecture trade-off
```

### 用户回答模糊

```text
score: 0.55

Agent:
Candidate knows terminology but lacks mechanism.

→ ask "why" follow-up
```

### 用户明显不会

```text
score: 0.2

Agent:
Repeated probing is not useful.

→ explain briefly
→ record weakness
→ move to prerequisite topic
```

这就是一个真正的 **Interview Agent**。

# 6. Evaluation 不应该完全交给 Agent

这里我反而建议你**不要过度 Agent 化**。

不要：

```text
Agent
 └── "I think your answer is 7/10"
```

而应该：

```text
Agent
 │
 └── evaluate_answer()
          │
          ▼
       Evaluator
          │
          ▼
{
  score: 0.72,
  conceptsCovered: [...],
  missingConcepts: [...],
  misconceptions: [...],
  confidence: 0.81
}
```

Evaluator 可以是：

```text
LLM
 +
rubric
 +
expectedConcepts
 +
structured output
```

然后 Agent 读取结果。

因此：

```text
Agent = decision maker

Evaluator = measurement system
```

这个职责分离非常重要。

你之前已经提到希望：

而不是：

# 12. 但不要把所有逻辑都 Agent 化

这是你这个项目最容易踩的坑。

不要变成：

```text
Agent
 ├── database
 ├── scoring
 ├── question generation
 ├── question validation
 ├── session management
 ├── UI
 ├── memory
 ├── routing
 └── everything
```

那会变成一个不可测试的黑盒。

我更推荐：

```text
                Agent
                  │
       ┌──────────┼──────────┐
       │          │          │
    Decide     Decide     Decide
       │          │          │
       ▼          ▼          ▼
   Question    Followup   Topic
       │          │          │
       └──────────┼──────────┘
                  │
              Tools/API
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
   Question    Evaluation  Memory
   Service      Service     Service
```

**Agent 做“不确定的决策”，代码做“确定性的执行”。**

这是我认为你这个项目最好的 Agent 边界。

                              │

                              │
