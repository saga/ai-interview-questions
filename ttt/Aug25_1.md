对，这其实是你现在题库设计里一个更核心的问题：

> **不要把“题目”作为最小知识单位，而应该把“Concept / Knowledge”作为中心，再围绕 Concept 生成多个不同角度的考察。**

例如 `Transformer` 不应该只有：

> Transformer 是什么？

而应该形成一个 **concept coverage / question angle matrix**：

```text
Transformer
├── Fundamentals
│   ├── self-attention
│   ├── Q/K/V
│   ├── positional encoding
│   └── residual + layer norm
│
├── Computation
│   ├── attention complexity
│   ├── KV cache
│   └── memory bottleneck
│
├── Architecture
│   ├── encoder vs decoder
│   ├── pre-norm vs post-norm
│   └── MHA vs MQA vs GQA
│
├── Training
│   ├── causal masking
│   ├── teacher forcing
│   └── training vs inference
│
├── Engineering
│   ├── long context
│   ├── memory optimization
│   └── distributed inference
│
└── Trade-offs
    ├── attention alternatives
    ├── dense vs sparse
    └── accuracy vs efficiency
```

这样才会从“背知识”变成真正的 **interview trainer**。

---

# 1. 先把现在的 `topic` 概念升级

你现在可能类似：

```json
{
  "topic": "transformer",
  "question": "..."
}
```

这个粒度太粗。

我建议至少拆成：

```json
{
  "concept": "transformer",
  "subtopic": "self-attention",
  "angle": "mechanism",
  "difficulty": "medium"
}
```

但我**不建议把所有东西都做成 taxonomy 节点**。

最重要的是区分：

### Concept

**“考什么”**

```text
transformer
self-attention
kv-cache
MoE
RAG
tool-calling
```

### Angle

**“从什么角度考”**

```text
definition
mechanism
comparison
tradeoff
scenario
debugging
design
calculation
misconception
```

这是非常重要的分离。

# 2. 你的 Question 最好变成

例如：

```json
{
  "id": "tr-sa-001",

  "concept": "transformer",
  "subtopic": "self-attention",

  "angle": "mechanism",

  "difficulty": "medium",

  "type": "open",

  "question": "...",

  "knowledgeContract": {
    "core": [
      "Q/K/V",
      "attention weights",
      "weighted aggregation"
    ],
    "misconceptions": [
      "Q/K/V are three independent models"
    ]
  }
}
```

这里：

```text
concept
   ↓
subtopic
   ↓
angle
   ↓
question
```

就形成了层次。

---

# 3. Angle 不应该太多

这里一定要防止你之前一直担心的 **over-design**。

我不会创建 20～30 个 angle。

对于 AI Trainer，我建议第一版只有 **7 个核心角度**：

| Angle         | 考察什么          |
| ------------- | ------------- |
| `fundamental` | 基本原理、概念       |
| `mechanism`   | 内部如何工作        |
| `comparison`  | A vs B        |
| `tradeoff`    | 为什么这样设计、代价是什么 |
| `scenario`    | 工程场景应用        |
| `debugging`   | 出问题如何定位       |
| `design`      | 如何设计/改进系统     |

再加一个：

```text
calculation
```

如果你的 Trainer 很重视 ML fundamentals。

---

# 4. Transformer 就会自然形成一个“题目空间”

例如：

### Fundamental

> Transformer 为什么需要 positional encoding？

### Mechanism

> 给定 Q、K、V，self-attention 是如何计算输出的？

### Comparison

> MHA、MQA 和 GQA 在 KV cache memory consumption 上有什么区别？

### Tradeoff

> 为什么现代 LLM 通常采用 Pre-LN，而不是原始 Transformer 的 Post-LN？

### Scenario

> 一个 LLM inference 服务在 context length 增加后 GPU memory 快速耗尽，应该首先检查 Transformer 的哪个部分？

### Debugging

> 模型训练 loss 正常下降，但推理时生成结果明显重复。怀疑 causal mask 实现错误时，你会如何定位？

### Design

> 如果需要将 Transformer 的 context window 从 32K 扩展到 1M，你会从哪些方面修改或优化架构？

### Calculation

> 给定 hidden size、head 数和 sequence length，如何估算 attention 的计算和 KV cache memory？

**这才是“围绕一个概念从多个角度考察”。**

---

# 5. 这里最关键的是：不要让 LLM 自己随机决定 angle

如果你只是：

```text
请围绕 Transformer 生成 10 道不同角度的问题
```

LLM 很可能还是：

```text
self-attention
self-attention
positional encoding
self-attention
QKV
self-attention
```

因为这些最容易生成。

所以应该让你的系统维护一个：

```text
Concept → Angle coverage
```

例如：

```json
{
  "concept": "transformer",
  "coverage": {
    "fundamental": 2,
    "mechanism": 3,
    "comparison": 1,
    "tradeoff": 1,
    "scenario": 1,
    "debugging": 0,
    "design": 0,
    "calculation": 0
  }
}
```

然后生成时：

```text
优先选择：
debugging
design
calculation
```

而不是继续生成 mechanism。

---

# 6. 这会让你的 Adaptive Interview 也变得更合理

你之前的系统是：

```text
weak topic
   ↓
recommend question
```

我建议升级为：

```text
weak concept
      ↓
coverage
      ↓
under-tested angle
      ↓
question
```

例如：

```text
Transformer
mastery = 82%

但是：

fundamental    90%
mechanism      88%
comparison     85%
tradeoff       70%
scenario       55%
debugging      30%
design         20%
```

那么系统不应该说：

> Transformer 掌握度 82%，换一个 topic。

而应该：

> **Transformer 基本知识掌握较好，但工程设计和 debugging 能力缺少证据。**

下一题：

```text
concept = transformer
angle = debugging
difficulty = hard
```

这就非常像真正的面试官。

# 7. 题目生成应该变成“两阶段”

这也是你之前问的：

> 是直接从题库抽，还是先找知识点？

现在这个问题有了更明确的答案：

## Stage 1：选择 Knowledge + Angle

```text
Learner Profile
       +
Concept Graph
       +
Coverage
       ↓
Question Blueprint
```

例如：

```json
{
  "concept": "transformer",
  "subtopic": "attention",
  "angle": "debugging",
  "difficulty": "hard",
  "purpose": "test whether candidate can diagnose attention implementation problems"
}
```

## Stage 2：生成 / 选择具体题目

```text
Blueprint
   ↓
Question Bank
   ↓
existing question?
   ├── yes → use it
   │
   └── no → LLM generate
```

这比：

```text
random question
```

强很多。

---

# 8. 这也正好解决你前面说的 Variant 问题

现在的 Variant 不应该只是：

```text
Question A
   ↓
改写
   ↓
Question A'
```

而应该：

```text
Knowledge Contract
      │
      ├── Angle: mechanism
      │
      └── Angle: scenario
```

例如：

```text
Original:
Transformer 的 self-attention 为什么需要 Q/K/V？

Variant:
一个在线推理系统希望减少 KV cache memory，
应该考虑 MHA → GQA 还是增加 FFN hidden size？为什么？
```

它们：

```text
concept = transformer
subtopic = attention
```

可能相同，

但：

```text
angle
```

不同。

这才是真正有价值的 variation。

# 9. 我建议你的 Knowledge JSON 也稍微变化

不要：

```json
{
  "topic": "transformer",
  "questions": [...]
}
```

而是：

```json
{
  "id": "transformer",
  "name": "Transformer",

  "concepts": [
    {
      "id": "self-attention",
      "name": "Self-Attention",

      "core": [
        "Q/K/V",
        "attention score",
        "weighted aggregation"
      ],

      "commonMisconceptions": [
        "attention weights are learned parameters",
        "Q/K/V are separate neural networks"
      ],

      "recommendedAngles": [
        "fundamental",
        "mechanism",
        "comparison",
        "scenario",
        "debugging"
      ]
    }
  ]

```

注意：

**不是每个 concept 都必须支持所有 angle。**

例如：

```text

→ mechanism
→ scenario

```

而：

```text
Positional Encoding
→ fundamental
→ mechanism
→ comparison
→ tradeoff
```

这样比建立一个巨大的 taxonomy 更简单。

# 11. 对你当前项目，我建议最小改造

**不要现在大改 Question schema。**

先增加：

```ts
type QuestionAngle =
  | 'fundamental'
  | 'mechanism'
  | 'comparison'
  | 'tradeoff'
  | 'scenario'
  | 'debugging'
  | 'design'
  | 'calculation';
```

然后 Question：

```ts
interface Question {
  ...
  topic: string;
  subtopic?: string;
  angle?: QuestionAngle;
}
```

再增加一个简单的 coverage：

```ts
type ConceptCoverage = {
  concept: string;
  angle: QuestionAngle;
  attempts: number;
  avgScore: number;
  lastAskedAt?: number;
};
```

然后你的选择逻辑：

```text
1. 找 weak concepts
2. 看该 concept 哪些 angles 缺证据
3. 选择最有价值的 angle
4. 找现有题
5. 没有 → LLM 根据 blueprint 生成
6. 做 deterministic validation
7. 面试
8. 把结果写回 Concept × Angle evidence
```

**这已经足够实现你说的“围绕 Transformer 从各个角度出题”，不需要再增加一层复杂 Agent orchestration。**

而且这会和你准备加入的 `pi-agent-core` 非常自然地结合：**Agent 的价值不是随机出题，而是根据 learner evidence 决定“下一个应该从哪个 Concept × Angle 继续追问”。**
