明白。你的问题不是“哪些地方可以不用 LLM”，而是：

> **在当前 AI Trainer 架构中，哪些任务实际上属于 classification / ranking / recommendation / statistics / optimization 问题，用传统算法或小模型可以做得更稳定、更便宜，而且不会牺牲最终效果？**

答案是：**不少，而且我建议主动把 LLM 从这些环节拿掉。**
LLM 应该集中在“需要语言理解、生成、语义判断”的地方。

可以把整个系统分成：

```text
                    AI Trainer
                        │
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
   Deterministic     ML / Algorithm      LLM
   Logic             Intelligence        Intelligence
```

# 1. 最值得替换：下一道题选择

这是我认为**最应该从 LLM 中拿出来**的地方。

你现在正在往：

```text
Concept × Angle
```

发展，那么：

```text
Learner Profile
       ↓
选择下一个 Concept × Angle
```

本质上是一个 **ranking / recommendation problem**，完全没必要让 LLM 决定。

---

## 可以直接做成一个 scoring function

例如：

```text
QuestionScore =
    0.35 × weakness
  + 0.25 × informationGain
  + 0.20 × coverageGap
  + 0.10 × importance
  + 0.10 × difficultyFit
```

例如：

```text
Transformer / debugging

weakness       = 0.9
informationGain = 0.8
coverageGap    = 1.0
importance     = 0.9
difficultyFit  = 0.8
```

得到：

```text
score = 0.89
```

然后：

```text
Transformer/debugging  0.89
RAG/tradeoff           0.82
Agent/design           0.77
MoE/mechanism          0.64
```

直接选最高。

### 为什么不会降低效果？

因为这个任务不是语言任务。

LLM 并没有什么特殊优势：

> “用户已经在 Transformer mechanism 做过 5 次题，应该下一题测试 debugging。”

这是典型的 recommendation / ranking。

而传统算法反而：

* 可解释
* 可预测
* 不会 hallucinate
* 不需要 token
* 非常容易测试
* 可以精确控制 coverage

**这里我强烈建议不要用 LLM。**

---

# 2. Learner Profile / mastery estimation

你现在的：

```text
attempts
avgScore
mastery
weakness
commonWeaknesses
```

也完全不需要 LLM。

但是这里我反而建议你进一步升级：

## 不要只使用 avgScore

因为：

```text
答对 9 / 10
```

和：

```text
第一次答对
后来连续答错
```

含义不同。

可以使用传统的 **Bayesian Knowledge Tracing（BKT）** 或简化版 Bayesian model。

例如：

```text
Concept:
KV Cache

prior mastery = 0.5

correct → 0.65
correct → 0.76
wrong   → 0.68
wrong   → 0.59
```

最终：

```text
mastery = 0.59
```

甚至可以做到：

```text
Transformer
├── attention        0.91
├── KV cache         0.63
├── GQA              0.47
└── positional       0.84
```

这比：

```text
Transformer average = 72%
```

有价值得多。

---

# 3. Concept × Angle coverage

这个更加明显是传统算法。

你可以维护：

```text
               fundamental mechanism scenario debugging design
Transformer       5          4          2        0        0
RAG               3          2          4        1        0
Agent             2          3          1        2        1
```

然后计算：

```text
coverageScore = 1 - observed / expected
```

或者更简单：

```text
coverageGap =
    importance ×
    (1 - confidence) ×
    recencyDecay
```

完全不需要 LLM。

---

# 4. Question selection / deduplication

这个地方也很适合传统算法。

例如你生成了：

```text
50 questions
```

需要选 10 个。

你真正需要的是：

```text
quality
+
diversity
+
coverage
```

这其实是一个非常经典的 **ranking + diversity selection** 问题。

甚至可以用：

### MMR

Maximal Marginal Relevance：

```text
score(q) =
    relevance(q)
    -
    λ × similarity(q, selected)
```

这样：

```text
Q1 self-attention mechanism
Q2 self-attention mechanism
Q3 KV cache tradeoff
Q4 GQA comparison
```

不会全部被选进去。

---

# 5. Question similarity / 重复检测

这个地方我甚至建议：

> **不要用 LLM。**

使用 embedding：

```text
question
   ↓
embedding
   ↓
cosine similarity
```

例如：

```text
Q1 ↔ Q2 = 0.93
```

说明高度重复。

```text
Q1 ↔ Q3 = 0.51
```

说明比较独立。

然后：

```text
similarity > 0.85
→ duplicate candidate
```

这里 embedding model 比 LLM 更合适。

甚至可以使用：

* cosine similarity
* HNSW
* clustering
* MinHash / locality-sensitive hashing（如果更偏 lexical）

---

# 6. Question difficulty estimation

这个地方也不一定需要 LLM。

实际上如果你的 Trainer 积累了足够多的用户数据，可以直接从真实答题数据学习。

例如：

```text
question
  ↓
historical responses
  ↓
P(correct)
```

那么：

```text
difficulty = 1 - P(correct)
```

进一步可以使用：

### Item Response Theory（IRT）

这是我非常推荐你的。

经典模型：

```text
P(correct) =
σ(ability - difficulty)
```

其中：

```text
ability = learner ability
difficulty = question difficulty
```

然后你可以得到：

```text
Question A
difficulty = 0.3

Question B
difficulty = 1.2

Question C
difficulty = 2.1
```

同时得到：

```text
User ability = 1.0
```

于是系统自然知道：

> B 最适合当前用户。

这比 LLM：

> “我觉得这道题 medium。”

科学得多。

# 7. 题目选择可以进一步变成 Adaptive Testing

如果你真的想把 Trainer 做得 AI-native，我非常推荐这一层。

不是：

```text
random question
```

也不是：

```text
LLM choose question
```

而是：

```text
Learner ability estimate
           ↓
Question bank
           ↓
choose question with maximum information gain
```

这就是 **Computerized Adaptive Testing / CAT**。

例如：

```text
当前：
Transformer / attention ability ≈ 0.8

候选：
easy       information gain = 0.12
medium     information gain = 0.31
hard       information gain = 0.08

→ 选择 medium
```

这实际上是你 Trainer 最值得算法化的地方之一。

# 8. Choice Question 的评分

这个当然：

```text
selected === answer
```

完全 deterministic。

不需要 LLM。

甚至多选：

```ts
sameSet(userAnswer, correctAnswer)
```

也不需要。

你之前发现的：

```text
gaps: ['答案不正确，请参见解析']
```

其实就是这里暴露出来的架构问题：

> Choice evaluation 应该是 deterministic signal，而不是模拟成 LLM evaluation。

我建议：

```text
ChoiceResult
├── correct
├── selected
├── expected
└── score
```

而：

```text
gaps
```

只由**明确的 knowledge misconception mapping**产生。

例如：

```json
{
  "option": "B",
  "misconception": "KV cache reduces model parameters"
}
```

用户选 B：

```text
correct = false

misconceptions = [
  "KV cache reduces model parameters"
]
```

这个非常有价值，而且完全不需要 LLM。

# 9. Open Question 的第一层评分

这里就不能完全去掉 LLM。

因为：

> “用户是否解释清楚 KV Cache 为什么减少重复计算？”

本质是 semantic evaluation。

但你可以做成：

```text
                 Open Answer
                      │
             ┌────────┴────────┐
             ▼                 ▼
        deterministic          LLM
        checks
```

例如：

### Deterministic / NLP

检查：

```text
required concept present?
technical keywords?
contradiction?
length?
structure?
```

然后：

```text
LLM
```

只负责：

> semantic correctness / reasoning quality

这样可以减少 LLM 工作量。

---

# 10. Open Question 的 rubric scoring

你现在有：

```text
correctness
completeness
depth
clarity
```

这里 LLM 仍然是合理的。

但是可以考虑：

```text
required concepts
        ↓
embedding / classifier
        ↓
coverage
```

例如：

```text
required:
Q
K
V
attention score
weighted sum
```

用户答案：

> Q 和 K 用来计算 attention，V 被加权聚合……

embedding / semantic matcher 可以判断：

```text
Q/K → covered
V → covered
attention score → covered
weighted aggregation → covered
```

然后：

```text
coverage = 4 / 4
```

LLM 只需要判断：

> 是否有概念性错误？解释是否准确？是否有重要 nuance 缺失？

这样评分更加稳定。

---

# 11. Recommendation text 才是非常典型的 LLM 任务

例如：

> 你最近在 KV Cache 的基础概念掌握较好，但在 GQA 与 MQA 的工程 trade-off 上仍存在薄弱点。

这里：

```text
数据分析 → algorithm
自然语言表达 → LLM
```

这是非常理想的分工。

不要让 LLM自己计算：

```text
你哪里弱？
```

应该：

```text
algorithm
   ↓
weakness = GQA/tradeoff
   ↓
LLM
   ↓
自然语言 recommendation
```

这样 LLM 不会胡编。

# 12. Question generation 仍然需要 LLM

这里我不建议为了“去 LLM 化”而去掉。

因为：

```text
Concept
+
Angle
+
difficulty
+
context
```

→

> 生成自然、有区分度、有场景的面试题

这确实是 LLM 擅长的。

尤其是你现在要求：

* self-contained
* context synthesis
* scenario
* different angles
* distractors
* explanation

传统算法很难达到同样效果。

所以：

**题目生成 → 保留 LLM。**

# 13. Question validation 可以大量不用 LLM

生成之后：

```text
LLM generated question
        ↓
        validation
```

可以先做：

### Schema

```text
question exists
options >= 2
answer valid
```

### Deterministic

```text
duplicate options
duplicate question
answer index valid
type correct
required fields
```

### Semantic / embedding

```text
similarity with existing questions
concept similarity
```

最后才：

```text
LLM semantic validation
```

也就是说：

```text
cheap checks
    ↓
embedding
    ↓
LLM judge only when necessary
```

而不是每次都 LLM judge。

# 14. Article → Knowledge extraction

这个地方比较特殊。

你现在：

```text
文章
 ↓
LLM
 ↓
知识点
```

我会保留 LLM。

因为这里需要：

```text
concept identification
importance
misconception
technical relationship
```

传统 NLP 可以辅助：

```text
NER
TF-IDF
keyword extraction
embedding clustering
```

但如果你的目标是**不降低效果**，我不会用它们替代 LLM。

可以作为：

```text
LLM extraction
+
algorithmic validation
```

而不是：

```text
algorithm instead of LLM
```

## 最重要的一点

我其实不建议你把目标定义成：

> **“让 AI Trainer 少用 LLM。”**

而应该定义成：

> **“让每一个问题由最适合它的技术解决。”**

尤其是你现在准备加入 `pi-agent-core`，更应该避免一个误区：

```text
AI-native
     ↓
everything = Agent + LLM
```

真正好的 AI-native architecture 应该是：

```text
                 Agent / LLM
                     │
          ┌──────────┴──────────┐
          │                     │
     semantic work          decision work
          │                     │
          ▼                     ▼
         LLM              algorithms / ML
```

甚至 **Agent 本身也不应该决定所有东西**。

比如：

> “下一道题问什么？”

这是最适合 **IRT/BKT + ranking/CAT** 的地方。

而：

> “这道题怎么问得更自然、更有挑战性？”

才是 **LLM / Agent** 的地方。

这样不仅不会降低效果，很多地方反而会**比纯 LLM 架构更准确、更稳定、更可解释**。
