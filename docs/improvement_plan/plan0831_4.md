我重新检查了当前 `main`。这次修改已经把 **Copilot Chat → 题目能力 → 评分能力** 接起来了，但有一个关键判断：

> **现在只是“Chat 能出题了”，还没有真正做到“Chat 与 Agent Interview 融合”。**

也就是说，你之前指出的“割裂”问题已经解决了一半，但当前设计又停在了一个中间态。

当前仓库已经新增了 conversation router、question capability、evaluation capability，并且 Chat 的 `"给我出一道题"` 确实会进入 `askQuestion()`，不是普通 LLM chat 了。

## 1. P0：`start_interview` 其实没有启动 Agent Interview

这是当前最大问题。

Router 定义：

```text
start_interview
ask_question
continue_interview
```



但是 Chat 这里三个 intent 全部走：

```ts
askQuestion(...)
```

也就是：

```text
start_interview
      ↓
askQuestion
      ↓
出一道题
```

而不是：

```text
start_interview
      ↓
createInterviewAgent / createAgentSession
      ↓
Agent 决定第一题
      ↓
回答
      ↓
评分
      ↓
Agent 决定下一题
```

代码实际上已经明确证明这一点：`start_interview` 只是设置：

```ts
mode: 'interview'
```

然后仍然调用共享的 `askQuestion()`。

所以现在：

> **“开始模拟面试”只是换了一个 mode 名字，并没有进入 Agent runtime。**

这个应该直接修。

# 2. P0：Chat 的 `continue_interview` 也不是真正 continuation

现在：

```text
下一题
  ↓
askQuestion()
```



所以它并没有使用：

```text
上一题评分
↓
Learner state
↓
Agent strategy
↓
下一题
```

而只是重新从题库 rank 一次。

虽然 `rankQuestions()` 已经复用 `rankCandidatePool()`，这一点是对的。

但：

```text
rankCandidatePool
```

≠

```text
Agent Interview continuation
```

因为缺少：

```text
本轮历史
当前 session
已考察 topic
上一题 evaluation
追问状态
```

# 3. P0：Chat 每答一道题，就被当成一个新的 SessionRecord

这里尤其值得注意：

```ts
const record = sessionFromQuiz(
  {
    questions: [{ question: chatQuestion, format }],
    ...
  },
  { [chatQuestion.id]: evaluation },
  ...
);
await onSessionComplete(record);
```



所以：

```text
给我出一道题
→ Q1
→ 回答
→ 保存 session #1

下一题
→ Q2
→ 回答
→ 保存 session #2

下一题
→ Q3
→ 保存 session #3
```

而用户认知却是：

```text
一个连续训练 session
Q1 → Q2 → Q3
```

这会导致 Learner Memory 层面产生一个非常奇怪的语义：

> Chat 中的一次连续训练，被拆成了 N 个“一题 session”。

这不是马上会坏，但会影响：

* session history
* progress
* average
* duration
* session replay
* interview summary
* 后续 BKT / IRT

# 4. P0：`ConversationContext.sessionId` 现在基本只是“标签”

Schema 有：

```ts
sessionId?: string
```



`start_interview` 会：

```ts
crypto.randomUUID()
```



但这个 id 并没有真正对应：

```text
InterviewAgentSession
```

也没有一个 application-level `LearningSession` 被创建。

因此现在：

```text
conversationContext.sessionId
```

不是一个真正拥有生命周期的 session，只是一个 context 字段。

这个需要纠正。

# 5. P0：Chat 与 Agent 现在仍然是两个 runtime

当前实际结构仍然是：

```text
CopilotSidebar
    ↓
conversation/router
    ↓
questionCapability
    ↓
evaluationCapability
```

而另一边：

```text
useAgentInterview
    ↓
createInterviewAgent
    ↓
pi-agent-core
    ↓
agent/tools
```

虽然两边复用了：

```text
rankCandidatePool
evaluateSessionQuestion
LearnerProfile
Question
```

但是 **orchestration 还是两套**。

这意味着：

```text
Chat：
下一题 → rankQuestion

Agent：
下一题 → Agent + tools

Training：
下一题 → interviewEngine

```

最终还是三个行为源。

# 6. 应该怎么收敛

我建议你不要继续加第四套 abstraction。

最简单的正确结构是：

```text
                    Conversation
                         │
                  mode / session state
                         │
          ┌──────────────┴──────────────┐
          │                             │
     Question Mode                 Interview Mode
          │                             │
   Question Capability          Agent Interview Runtime
          │                             │
          └────────── shared ───────────┘
                  Question
                  Evaluation
                  Learner
                  Session
```

关键是：

### `Chat` 是入口，不是独立业务实现

例如：

```text
用户：
给我出一道 RAG 的题
```

进入：

```text
Question mode
```

回答：

```text
继续
```

继续：

```text
Question mode
```

而：

```text
用户：
开始模拟面试
```

才进入：

```text
Interview mode
   ↓
Agent Runtime
```

此后 Chat 不再自己执行：

```text
askQuestion()
evaluateAnswer()
```

而是：

```text
Conversation
    ↓
InterviewAgent.submitAnswer()
```

# 7. 一个更重要的 UX：应该允许 Chat 动态升级成 Agent

其实没必要要求用户显式说：

> “开始模拟面试”

用户说：

> “给我出一道题。”

得到 Q1。

然后用户：

> “我来回答……”

评分。

然后：

> “再难一点，继续问我。”

这时候系统完全可以：

```text
Question mode
      ↓
用户要求连续/追问
      ↓
upgrade → Interview mode
      ↓
Agent 接管
```

这样你的产品会自然很多。

也就是说：

```text
Question
    ↓
Practice
    ↓
Adaptive Practice
    ↓
Interview
```

不是四个孤立页面。

# 8. Router 现在还有一个问题：`结束` 被识别成 `evaluate_answer`

这是一个实际 bug。

当前：

```ts
if (/^(结束|停止|先到这里|结束面试)/u.test(text)) {
  return {
    intent: 'evaluate_answer',
    confidence: 0.95
  };
}
```



但是 `evaluate_answer` 的语义明显是：

> 评价当前答案

不是：

> 结束面试

schema 里也没有：

```text
end_interview
```



所以目前：

```text
结束
```

→ `evaluate_answer`

然后 Chat：

```ts
appendAssistant('当前题已结束评分流程...')
```



这显然不是正确语义。

应该直接增加：

```ts
end_interview
```

# 9. `evaluate_answer` 和 `answer_current_question` 也有语义重复

现在有：

```text
answer_current_question
evaluate_answer
```

但实际流程应该非常明确：

```text
answer_current_question
    ↓
evaluation capability
```

`evaluate_answer` 更像：

> “刚才那个答案到底怎么样？”

而不是一个状态转换。

建议：

```text
answer_current_question
```

保留。

`evaluate_answer` 改成真正的显式请求：

> “重新评价刚才的答案”

或者直接删掉。

# 10. `messages` 没有持久化，只有 ConversationContext 持久化

目前保存的是：

```text
conversationContext
```

但：

```text
messages
```

仍然只是 React state。

所以刷新后：

```text
session context 还在
聊天记录没了
```

这两个状态是不一致的。

更重要的是，下一次 general chat：

```ts
const history = messages.map(...)
```



因此刷新页面后，LLM 失去对话历史。

这至少要做到：

```text
ConversationSession
 ├── context
 └── messages
```

统一持久化。

# 11. `buildSystemPrompt()` 仍然直接放在 React Component 内

现在 Copilot 自己构造：

```text
weakness
currentQuestion
session
```

然后生成 prompt。

这意味着：

```text
Conversation domain
```

的信息又开始重新耦合到 UI。

建议至少把：

```text
buildConversationContext()
buildCopilotSystemPrompt()
```

抽到：

```text
application/conversation/
```

这样 Chat component 只负责 UI。

# 12. Router 的 deterministic intent 还太弱

现在只覆盖非常有限的：

```text
下一题
结束
开始面试
给我出一道题
```



其它像：

```text
考考我 Agent
来个 RAG 的
给我一个难一点的
问个 system design
继续考
再追问一下
针对刚才的错误继续
```

大量依赖 LLM classification。

这本身没问题，但应该把：

```text
current state
+
last question
+
last evaluation
+
available modes
```

全部作为 router context。

现在 context 只有：

```text
mode
sessionId
currentQuestionId
pendingAction
```



没有真正的：

```text
lastEvaluation
questionHistory
```

所以 LLM router 对“继续考我 / 针对刚才薄弱点继续”缺少结构化依据。

# 最终判断

这次修改以后，我会把状态评为：

```text
原来：

Chat ────────┐
             ├── 各自孤立
Quiz ────────┤
Agent ───────┘


现在：

              ┌─ QuestionCapability
Chat → Router ┤
              └─ EvaluationCapability

Agent ───────────────┐
                     └─ 另一套 runtime
```

所以：

### 已经解决

```text
✅ “给我出一道题”不再是普通聊天
✅ Chat 已经进入题库
✅ Chat 已经使用统一 question ranking
✅ Chat 已经使用统一 evaluation
✅ Chat 已经开始使用 learner profile
```

### 现在最需要继续解决

```text
P0-1  start_interview 真正接入 Agent Runtime
P0-2  continue_interview 不要再变成“重新 askQuestion”
P0-3  Chat 建立真正的 Learning/Interview Session
P0-4  一次连续 Chat 训练不要保存成 N 个独立 session
P0-5  end_interview 独立成真正 intent
P1-1  Conversation messages 与 context 一起持久化
P1-2  Agent / Chat / Training 三套 orchestration 再收敛一次
```

其中我认为 **最核心的一刀只有一个**：

> **把 `ConversationSession` 变成真正的 session，并让它可以在 `question mode` 与 `interview mode` 之间切换；进入 `interview mode` 后直接把控制权交给现有 `InterviewAgent`。**

这样就不用再造新的 Agent，也不用再继续扩展 `CopilotSidebar`。现有 `pi-agent-core + AgentTools + adaptive + learner` 已经够了。

另外，当前 repo 顶层 README 仍然把产品描述为独立的“五页：训练 / 进度 / 面试 / Agent 面试 / 设置”，而新加入的 Chat 已经开始具备跨这些能力的入口性质；文档模型也应该随这个变化调整。([GitHub][1])

GitHub 自己对 Copilot Chat 的定位也是“共享上下文中的连续对话”和“根据当前上下文执行不同任务”，而不是一个完全独立的问答入口；这个方向与你现在把 Chat 做成统一入口是一致的。([docs.github.com][2])
