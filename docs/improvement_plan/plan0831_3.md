是的。你指出的是一个比前面那些问题更根本的架构问题：**当前 Chat、Agent 面试、训练系统虽然复用了底层能力，但没有形成一个统一的“交互入口 / 意图路由层”**。

从当前代码看，`Agent 面试` 是一条独立 runtime：`pi-agent-core Agent → InterviewAgent tools → session`；它的 system prompt 也明确把自己限定为“面试决策中心”。

因此用户在 Chat 中说：

> “给我出一道题”

实际上不会自然进入：

```text
意图识别
  ↓
出题
  ↓
等待回答
  ↓
评分
  ↓
继续追问
```

而更像：

```text
Chat
  ↓
普通 LLM conversation
  ↓
回答“当然可以，以下是一道题……”
```

这就是你说的“割裂”。

# 核心问题

当前架构实际上是：

```text
                    ┌── Training
                    │
UI ────────────────┼── Mock Interview
                    │
                    ├── Agent Interview
                    │      └── pi-agent-core
                    │
                    └── Copilot Chat
                           └── 普通 LLM
```

但是产品真正需要的是：

```text
                         ┌── Training
                         ├── Interview
User → Conversation → Intent Router
                         ├── Question
                         ├── Evaluation
                         ├── Explain
                         └── General Chat
```

也就是说：

> **Chat 不应该是 Agent 面试的旁边一个功能，而应该是整个系统的自然语言入口。**

---

# P0：增加一个统一的 Interaction / Intent 层

不要直接让 Copilot Chat 自己处理所有东西。

应该增加：

```text
src/application/conversation/
```

或者更简单：

```text
src/application/conversationRouter.ts
```

核心概念：

```ts
type UserIntent =
  | { type: 'start_interview' }
  | { type: 'ask_question'; topic?: string; difficulty?: Difficulty; format?: FormatId }
  | { type: 'answer_current_question'; answer: AnswerValue }
  | { type: 'continue_interview' }
  | { type: 'evaluate_answer' }
  | { type: 'explain_topic'; topic?: string }
  | { type: 'general_chat' };
```

关键不是这个 enum 本身，而是：

> **所有入口都进入同一个 application layer。**

---

# P0：把“出一道题”变成一等公民能力

你现在已经有：

```text
searchQuestions
getQuestion
evaluateAnswer
finishInterview
```

这些实际上已经足够构成一个很好的 Question capability。

所以不要再让 Chat 自己生成题。

应该变成：

```text
Chat:
“给我出一道 RAG 的题”

        ↓

Intent:
ask_question(topic=RAG)

        ↓

QuestionService

        ↓

search/rank

        ↓

getQuestion()

        ↓

UI render question
```

这样：

```text
训练页出题
Agent 面试出题
Chat 出题
```

最终都使用同一个：

```text
QuestionService
```

# P0：更重要的是，Chat 必须能够“进入状态”

这是目前真正缺的。

例如：

```text
用户：
给我出一道 Agent 的题

系统：
[题目]

用户：
我的答案是：...

系统：
88 分。
你漏掉了 tool use 和 feedback loop。
要不要继续下一题？

用户：
继续

系统：
[下一题]
```

这已经不是普通 chat。

它实际上是：

```text
Conversation
     ↓
Stateful Interview Session
```

因此 Chat 需要能够 attach 一个：

```ts
ConversationContext
```

例如：

```ts
interface ConversationContext {
  mode: 'chat' | 'interview';
  interviewSessionId?: string;
  currentQuestionId?: string;
  pendingAction?: 'answer' | 'choose_question';
}
```

# P0：不要把 Chat 和 Agent Interview 做成两个 Agent

我不建议：

```text
Copilot Agent
Interview Agent
```

继续独立发展。

应该变成：

```text
                   Conversation Agent
                         │
             ┌───────────┼───────────┐
             ↓           ↓           ↓
        Question      Interview    Knowledge
        capability    capability   capability
```

其中 Interview 只是一个**stateful mode**。

也就是说：

```text
“给我出一道题”
```

是：

```text
Conversation Agent
   → question capability
```

而：

```text
“开始模拟面试”
```

是：

```text
Conversation Agent
   → interview capability
   → create session
   → enter interview mode
```

这样产品行为才统一。

# P1：Agent tools 不应该只服务 Agent Interview

现在 `createAgentTools()` 的定位非常明显，是给 `InterviewAgent` 使用的。其工具集合主要围绕题目选择、评分、弱项和结束面试设计。

建议把底层能力再向下抽一层：

```text
domain
   ↑
application capabilities
   ↑
agent tools
   ↑
chat / interview UI
```

例如：

```text
application/
    questionService.ts
    evaluationService.ts
    learnerService.ts
    interviewService.ts
    conversationService.ts

agent/
    tools/
       questionTools.ts
       evaluationTools.ts
       learnerTools.ts
       interviewTools.ts
```

而不是：

```text
agent/tools.ts
   ↓
domain
```

否则最终会变成：

> 只有 Agent 才能使用系统最重要的能力。

这是现在架构割裂的根源之一。

# P1：增加“自然语言 → Capability”的轻量路由

不要一开始做复杂 multi-agent / planner。

实际上只需要一个非常轻的 router：

```text
用户输入
   ↓
是否正在 interview session？
   ├── yes → Interview handler
   └── no
        ↓
   intent classify
        ├── question
        ├── explain
        ├── start interview
        └── general chat
```

甚至第一版可以由 LLM 做 structured intent：

```json
{
  "intent": "ask_question",
  "topic": "agent-fundamentals",
  "difficulty": "medium",
  "format": "open"
}
```

然后：

**LLM 只识别意图，真正执行由 deterministic application service 完成。**

这和你之前整个项目的设计原则是一致的。

例如：

LearnerProfile

# 推荐最终架构

我建议把现在结构收敛成：

```text
                         User
                           │
                     Conversation UI
                           │
                  Conversation Controller
                           │
                    Intent / Mode Router
                           │
       ┌───────────────────┼───────────────────┐
       ↓                   ↓                   ↓
 Question Capability   Interview Capability   Knowledge Capability
       │                   │                   │
       └────────────── Application Layer ─────┘
                           │
       ┌───────────────┬───┴────┬───────────────┐
       ↓               ↓        ↓               ↓
 Question Bank      Evaluation  Learner       Session
       │               │        Memory           │
       └───────────────┴────────┴────────────────┘
                           │
                     Agent Runtime
                     (optional)
```

注意这里 **Agent Runtime 是 application capabilities 的消费者，而不是它们的拥有者。**

# 最关键的一点

你现在的：

```text
Agent 面试
```

其实不应该再被视为一个独立功能。

它应该是：

> **Conversation-driven Interview capability**

于是用户从任何地方都可以自然进入：

```text
“给我一道题”
        ↓
题目

“我回答……”
        ↓
评分

“继续”
        ↓
下一题

“针对刚才的弱点再问我”
        ↓
Agent follow-up

“今天先到这里”
        ↓
结束并更新 Learner Memory
```

这才真正符合你这个项目 **Personal AI Interview Coach** 的定位，而不是：

```text
一个 Quiz App
+
一个 Agent Interview App
+
一个 Chatbot
```

当前代码已经有足够多的底层能力实现这个方向；主要问题是**没有一个统一的 Conversation/Application orchestration 层把它们接起来**。当前 Agent prompt 本身已经把“下一题、评分、弱项、结束”定义成连续决策，所以最适合把这套能力向上抽象，而不是继续给 Chat 单独造一套逻辑。

此外，这种“Chat 作为入口、专用 agent/capability 作为后端能力”的模式也更符合当前 Copilot 类产品的交互趋势：对话可以从一般问答自然进入特定任务，并通过共享上下文持续后续操作。([docs.github.com][1])

**我会把这个定义为当前架构的 P0，而不是一个 UX enhancement。**
