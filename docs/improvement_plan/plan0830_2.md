# 一、总体结论

当前架构整体是**成立的，而且没有必要再大改**。

核心边界现在比较清楚：

```text
Question / Knowledge
        ↓
Interview Engine / Domain
        ↓
Evaluation / Learner
        ↓
Agent
        ↓
只负责“不确定决策”
```

同时：

```text
LLM
 ├─ Variant generation
 ├─ Open-answer evaluation
 ├─ Question challenge
 └─ Agent decision
```

而：

```text
Domain
 ├─ choice scoring
 ├─ mastery
 ├─ coverage
 ├─ adaptive selection
 ├─ prerequisite
 └─ validation
```

这个方向是正确的。架构文档也明确坚持“Knowledge 是中心、Question 是 View、Domain 决策、LLM 只增强”。

**我不会建议你把系统进一步 Agent 化，也不会建议现在引入 BKT / IRT / embedding judge / 多 Agent。**

真正值得修的是下面 **6 个点**：

| 优先级    | 问题                                                               | 我的判断                          |
| ------ | ---------------------------------------------------------------- | ----------------------------- |
| **P0** | Variant 的 `format` 与实际 Session format 脱节                         | **应该修**                       |
| **P0** | Variant semantic validation 目前仍然偏弱                               | **应该修**                       |
| **P1** | Agent context 虽然已经能工作，但缺少“上下文预算/裁剪策略”                            | **应该补一个简单护栏**                 |
| **P1** | Agent 的决策依据仍有部分信息缺失/不一致                                          | **应该收敛**                      |
| **P1** | Learner Memory 的 concept-level weakness 信号仍不完整                   | **应该修，但不要把 choice 错误伪装成 gap** |
| **P2** | DeepSeek capability table 已建立，但部分 capability 只是声明，没有真正参与 runtime | **需要收敛，避免“假能力抽象”**            |

另外还有几个**非功能性问题**：文档已经出现版本漂移，尤其 README/ARCHITECTURE 与实际 React 版本、server/worker 架构不完全一致。

# 二、P0：Variant 的 format 设计现在仍然有一个真正的问题

这是我认为当前代码里最值得优先修的地方。

现在 `finalizeQuestion()`：

```ts
const variant = await provider.generateVariant(sq.question);
```

传进去的只有：

```ts
Question
```

没有：

```ts
sq.format
```

而 `generateVariant()` 自己判断：

```ts
format: q.formats.choice
  ? single / multiple
  : open
```

也就是说：

> **只要一个 Question 同时拥有 choice + open，Variant prompt 就默认按 choice 生成。**

而你的题库里：

> 1078 / 1084 道题同时有 choice + open。

所以这不是理论问题。

---

## 举例

当前题：

```json
{
  "formats": {
    "choice": {...},
    "open": {...}
  }
}
```

本次 Session：

```ts
format = "open"
```

但：

```ts
generateVariant(q)
```

看到：

```ts
q.formats.choice !== undefined
```

于是 prompt 认为：

```text
题型 = single / multiple
```

然后把：

```text
options
answer
```

都塞给模型。

最后 `applyVariant()` 又根据：

```ts
const isChoice = !!canonical.formats.choice;
```

判断。

这实际上把：

> **Question 是否支持 choice**

和：

> **当前 Session 正在考什么 format**

混成了一件事。

---

## 应该怎么修？

非常简单，不需要重构：

```ts
generateVariant(
  q,
  format: 'choice' | 'open'
)
```

然后：

```ts
finalizeQuestion({
  question: q,
  format: fmt
}, provider)
```

传进去。

Variant 的 contract 变成：

```text
canonical question
+
current presentation format
```

然后：

```text
choice
 → 只生成 choice presentation

open
 → 只生成 open presentation
```

`applyVariant()` 也应该根据 `v.format` / session format，而不是：

```ts
!!canonical.formats.choice
```

决定。

### 这是我认为当前真正的 P0。

# 三、P0：`validateVariant()` 现在虽然已经有 fuzzball，但语义校验仍然偏弱

这一点尤其值得注意。

当前已经：

```ts

```

并且使用：

```ts
fuzz.token_set_ratio()
fuzz.partial_ratio()
```

所以之前那个：

> “validateVariant 是空实现”

已经**不成立**了。

当前已经是真正的 gate，而且生成失败会重试一次，重试后再次 validate。

这是正确进展。

但是现在这个 semantic gate 的问题是：

```ts
const text = [
  v.question,
  ...v.options,
  v.explanation
].join(' ')
```

然后：

```ts
anchors = [
  canonical.topic,
  ...canonical.tags,
  ...required
]
```

最后：

```ts
if (任意 anchor 有一点匹配)
    return true
```

也就是说：

> **只需要一个 concept 有证据，就可以通过。**

甚至：

> explanation 里提到 required concept，也可以帮助通过。

这和你的 prompt：

> `requiredConcepts 必须被实际考察，而不仅仅是在题干、选项或解析中出现`

其实还是不一致。

```text

```

当前 validator 很可能：

```text

↓

```

但题目实际上已经漂移。

# 四、怎么修 Variant semantic validation？

不要上 embedding judge。

当前阶段没必要。

我建议把规则从：

```text
any concept matched
```

改成：

```text
question / options
    ↓
requiredConcept evidence
    ↓
至少达到合理覆盖
```

关键是：

### **不要把 explanation 当作 semantic evidence。**

应该：

```ts
const assessmentText = [
  v.question,
  ...(v.options ?? [])
].join(' ');
```

解析只能用于：

```text
explanation consistency
```

而不能用于：

```text
knowledge preservation
```

---

### 第二步：requiredConcept 不要要求 100% 全匹配

因为你允许 paraphrase。

所以比较合理：

```text
requiredConcepts = 3
```

至少：

```text
2 / 3
```

能够找到可靠证据。

如果只有：

```text
1 / 3
```

应该：

```text
reject / retry
```

而不是现在的：

```text
1 个命中 → pass
```

---

### 第三步：fuzzball 不要直接比较

现在：

```ts
fuzz.token_set_ratio(anchor, entireText)
```

这个粒度太粗。

应该至少：

```text
required concept
    ↓
question
    +
each option
```

分别比较。

这样：

```text
required:
"independent of batch statistics"

question:
"Why is LayerNorm preferred when batch size varies?"
```

才有机会识别。

---

## 所以 fuzzball 可以保留

**不需要删除。**

它现在已经可以浏览器运行，而且 package 中已经正式依赖 `fuzzball`。

但应该把它从：

> “语义判断器”

定位成：

> **cheap lexical/paraphrase evidence detector**

这就对了。

# 七、P1：Agent 的“决策”与 deterministic adaptive engine 有一点重复

这个是当前架构里我认为最值得关注、但不应该大改的地方。

### Deterministic adaptive


负责：

```text

```

Prompt 又要求：


这意味着：

而不是 Agent：


**保持这个方向即可，不要继续扩大 Agent 的权力。**

之类的更多工具。

**现在工具数量已经够了。**

# 二十、一个真正值得注意的状态一致性问题

当前 Agent 有：

```text
Agent message history
session
UI
LearnerProfile
IndexedDB
```

四套状态。

而：

```text
session
```

是 Agent runtime authoritative state。

这个没问题。

但是：

```text
finishInterview
```

只是：

```ts
session.status = 'finished'
```

然后外部再持久化。

所以存在：

```text
Agent finish
 ↓
UI crash / tab close
 ↓
Learner profile 未更新
```

这个是实际的“事务边界”。

不过我不建议现在引入复杂 transaction。

只需要：

> **finishInterview 后立即触发持久化，并在 `agentSessions` 草稿里保持可恢复状态。**

架构文档已经提到 agentSessions 草稿和续接机制。

如果当前代码已经实现恢复，那就不需要继续改；如果只是 schema/设计层已经写了但实际没有恢复，则应该列 P1。

---

# 二十一、题目 Variant 与 Agent 之间还有一个边界问题

当前：

```text
getQuestion
 ↓
finalizeQuestion
 ↓
variant
 ↓
session.currentQuestion
```

这是合理的。

但是：

```text
Agent 选择的是 canonical Question
```

而用户实际看到的是：

```text
Generated Variant
```

因此 Agent 的：

```text
searchQuestions
```

看到：

```text
topic
difficulty
formats
```

但看不到最终变体。

这本身没问题，因为 Agent 不负责题目内容。

但是如果 Agent 后续想说：

> “这道题是在考察某个具体角度”

它只能依据：

```text
canonical metadata
```

而不是最终变体。

所以 prompt 已经禁止它复述题干，这是正确的。

# 二十二、`QUESTION_CHALLENGER` 是一个不错的设计，但不要把它变成 runtime judge

当前 Question Challenger：

```text
self-contained
sufficiency
logic
answer uniqueness
distractors
explanation
```

并且还做了 deterministic source-prerequisite check。

这个非常适合：

```text
题库建设 pipeline
```

不适合：

```text
每次 runtime variant 都再调用 challenger
```

现在没有这么做，这是对的。

保持 offline / authoring gate。

# 二十六、最终架构评价

我现在对这个 repo 的判断是：

```text
                    Knowledge
                       │
                       ▼
                Question Bank
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
      Deterministic Engine     LLM Enhancement
             │                   │
       ┌─────┼─────┐       ┌─────┼──────┐
       │     │     │       │     │      │
     score  adapt  learner variant eval challenge
       │     │     │       │     │
       └─────┴─────┴───────┴─────┘
                       │
                       ▼
                 Agent Runtime
                       │
              decision / routing
                       │
                       ▼
                  Tool Calls
```

**这个总体架构不需要推倒重来。**

真正的问题已经从早期的：

> “Agent / LLM 到处参与，边界混乱”

收敛成了现在几个更具体的问题：

1. **Variant presentation format 没有跟 Session format 对齐**
2. **Variant semantic validation 仍然是 heuristic，而且目前过于宽松**
3. **Agent context 需要一个轻量的候选数量控制**
4. **`missingConcepts` 尚未真正进入 Learner Memory**
5. **Agent prompt 可以再减少重复 tool 查询**
6. **DeepSeek capability abstraction 中有少数“声明了但还没有实际行为”的能力**
7. **文档版本存在 drift**

其中我认为真正需要马上改的只有前两个。

尤其是 **Variant format + semantic gate**，这是目前最直接影响题目正确性的地方；相比之下，Agent context、KV Cache、tool-call、choice fast path，目前的整体设计已经比较合理，不值得为了“看起来更 Agentic”而继续复杂化。

另外，当前仓库的 `main` 已经明确显示为 **1084 题、1078 道双形态题**，并且 `pi-agent-core` / `pi-ai` 已经进入实际 Agent 与 LLM 管线，因此上面的判断是基于当前代码而不是之前的旧版本。([GitHub][1])
