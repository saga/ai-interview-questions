我这次把 `dev0902` 按独立版本重新审了一遍，重点核对了实际代码、schema、offline variant pipeline、skills、prompt、文档，以及已经提交进仓库的变体数据。结论比上一版更明确：

> **没有发现需要推倒重来的架构大问题。**
>
> 但有 **3 个我认为已经达到“大问题”级别的问题**：其中两个是离线 Variant 体系本身的问题，一个是 Prompt 与实际数据模型的冲突。
>
> 另外还有几项 P1 级问题，主要是题库质量和 release gate。

# 一、最严重的问题：当前已经提交的离线 Variant 池，存在明显的低质量内容

这是这次检查里最值得你优先处理的。

现在 `dev0902` 已经真正实现：

```text
canonical
  ↓
question-variants.ts
  ↓
oversampling
  ↓
variantChallenger
  ↓
variant pool
```

而且默认是 offline 生成，runtime variant 只是可选增强。这部分架构方向是正确的。

问题出在：

> **现在已经 commit 进 `src/data/variants/` 的实际变体，并没有达到你在 prompt/spec 里规定的质量标准。**

例如 `evaluation.wb-llm-20260903.json` 里已经出现这种明显异常的中文 Variant：

> “流程量度、器具唤起、即是可……”

以及一批存在明显机器翻译/语序异常的 `context-options`。例如 `agentic-10` 以及后面的多个 `agentic-*` 变体都存在这种问题。这个不是理论风险，而是**已经进入当前仓库资产的实际问题**。([raw.githubusercontent.com](https://raw.githubusercontent.com/saga/ai-interview-questions/dev0902/src/data/variants/evaluation.wb-llm-20260903.json))

这说明：

```text
Prompt
  ↓
LLM
  ↓
validator
  ↓
challenger
  ↓
persist
```

目前这个质量链条虽然“有”，但**没有真正挡住语言质量异常的 Variant**。

---

## 为什么现有 challenger 没挡住？

你的 challenger 是 5 维：

```text
concept-preserved
answer-preserved
difficulty-preserved
diagnostic-value
accidental-clue
```

这个设计本身没问题。

但当前 challenger 的输入明确告诉 judge：

```text
原题正确项
原题干扰项
```

也就是把 ground truth 直接给了 challenger。

这会导致一个明显的问题：

> Challenger 很擅长回答“你觉得这个 Variant 有没有保持原答案”，但不等于它真的能发现 Variant 本身语言质量差、表达怪异、语义表达不自然。

换句话说：

```text
semantic validity
≠
linguistic quality
```

你现在检测得比较重的是前者，但题库真正需要的还有：

```text
naturalness
clarity
professional wording
ambiguity
translation artifact
```

这也是为什么这种明显不自然的中文仍然可能通过。

# 二、离线 Variant pipeline 最大的结构性问题：缺“语言质量”这一层

目前离线 pipeline 大体是：

```text
generate N
  ↓
structural validation
  ↓
similarity / drift
  ↓
5D challenger
  ↓
top N
```

我认为应该增加一个很轻的独立 gate：

```text
Language / Readability Gate
```

但我**不建议再增加一个复杂 LLM judge**。

可以先非常简单：

```text
乱码 / 异常 Unicode
异常中英文混排
重复 token
异常标点
极低中文自然度
疑似翻译腔
选项内部句法残缺
```

然后只让明显异常的进入 challenger。

这样：

```text
cheap deterministic
    ↓
language sanity
    ↓
semantic challenger
```

比：

```text
LLM challenger
```

一个模型承担所有 QA 要合理得多。

# 三、第二个大问题：Variant Prompt 与当前实际 Variant 架构发生了冲突

这是我认为最值得现在改的文档/Prompt 问题。

当前 `docs/添加题库prompt.md` 仍然定义：

> Variant 可以改变 cognitive task、angle、engineering scenario。([raw.githubusercontent.com](https://raw.githubusercontent.com/saga/ai-interview-questions/dev0902/docs/添加题库prompt.md))

甚至明确举了：

```text
Canonical → mechanism
Variant   → diagnose
Variant   → tradeoff
```

也就是说，这份 Prompt 的 Variant 是：

> **重新设计一道同 Concept、不同认知任务/Angle 的 assessment item。**

这个概念本身其实很好。

但当前真正落地的 offline variant 数据模型却不是这个东西。

当前 `variant.ts` 的 Variant 是：

```text
kind:
  surface
  context
  surface-options
  context-options
```

并且它是 canonical question 的一个外部变体资产，运行时：

```text
canonical answer
canonical explanation
canonical metadata
```

全部继续继承。

换句话说，现在实际实现的是：

> **Presentation Variant**

而 Prompt 描述的是：

> **Assessment Variant**

这两个东西不是完全一样的。

---

## 这会带来什么实际问题？

假如 LLM 严格执行当前 Prompt：

```text
Canonical
angle = mechanism

Variant
angle = debugging
```

那么它可能真的会重新设计问题：

```text
为什么 KV cache 工作？
          ↓
一个服务延迟突然升高，如何诊断 KV cache 问题？
```

这已经不只是“改写”。

而当前 runtime/variant pool schema 并没有保存：

```text
variant angle
variant difficulty
variant cognitiveTask
variant concepts
```

它只是：

```text
question
options
kind
sourceHash
```

于是出现：

```text
Prompt 认为：
Variant = 新 assessment item

Runtime 认为：
Variant = canonical 的替代表达
```

这是一个**设计契约冲突**。

# 四、这里我建议你直接二选一

我比较建议第二个。

## 方案 A：Variant 真正升级成 Assessment Variant

那就要给 Variant 增加：

```text
angle
cognitiveTask
difficulty
diagnosticTarget
```

甚至完整继承 Question metadata。

这样：

```text
Canonical
  angle=mechanism

Variant
  angle=debugging
```

就是合法的。

但这会增加 runtime adaptive、coverage、learner evidence 的复杂度。

**现在没有必要。**

---

## 方案 B：保持现在轻量 Variant 架构

我更推荐。

那就应该直接把 Prompt 改掉：

### Canonical

负责：

```text
knowledge contract
angle
difficulty
diagnostic target
```

### Variant

只允许：

```text
换 framing
换 scenario
换问法
换选项表达
保持 cognitive task 不变
保持 angle 不变
保持 difficulty 不变
保持 answer logic 不变
```

也就是说：

```text
Canonical
   mechanism

Variant
   mechanism
   ↑
   different scenario / wording
```

而不是：

```text
mechanism
   ↓
debugging
```

后者应该创建一条**新的 canonical question**，然后再生成它自己的 variant pool。

这和你现在的：

```text
topic × angle
```

coverage 架构也更一致。

# 五、这会同时解决一个 skills 层面的混乱

`fill-coverage-gap` 现在做的是：

```text
找到 coverage gap
 ↓
reuseCandidateIds
 ↓
可以通过调整已有题来覆盖
```

这个逻辑没问题。([raw.githubusercontent.com](https://raw.githubusercontent.com/saga/ai-interview-questions/dev0902/skills/fill-coverage-gap/SKILL.md))

但必须把：

```text
rewrite canonical to another angle
```

和：

```text
generate expression variant
```

明确区分。

推荐最终语义：

```text
Coverage gap
    ↓
是否已有 canonical 可以重构？
    │
    ├─ yes → curate/rewrite canonical
    │
    └─ no  → create new canonical
                  ↓
             offline variants
```

而不能：

```text
coverage gap
    ↓
variant
```

否则会把题库 coverage 和 variant corpus 混在一起。

# 六、第三个大问题：Variant validator 现在仍然只是“防坏”，不是“选好”

`validate-variants.ts` 本身做得挺干净：

```text
stale
near duplicate
schema
```

它也明确是 read-only audit。([raw.githubusercontent.com](https://raw.githubusercontent.com/saga/ai-interview-questions/dev0902/scripts/validate-variants.ts))

但是这里有个重要问题：

## 它目前不会让 CI / build 失败

最后只是：

```text
if (
  stale.length === 0 &&
  dupPairs.length === 0
) {
  console.log("✓ 池健康")
}
```

没有：

```ts
process.exit(1)
```

所以即使：

```text
stale = 100
nearDuplicate = 50
```

脚本依然可以正常结束。

这意味着：

```text
question validation
```

和：

```text
variant validation
```

目前在 release gate 的强度上不对称。

### 建议

至少：

```text
stale > 0
  → exit 1

duplicate > 0
  → exit 1
```

然后 CI：

```text
validate questions
+
validate variants
```

都必须 green。

这非常值得修。

# 七、还有一个历史数据问题：旧 Variant 很可能需要重新清洗

这次检查还发现一个比较重要的“历史债”。

`assemble-variants.ts` 自己的注释已经承认：

> 第一批 mass production 出现了大量 option overlap / near duplicate，79 对、约 81% 的题受影响；之后才修正 assembler。([raw.githubusercontent.com](https://raw.githubusercontent.com/saga/ai-interview-questions/dev0902/scripts/assemble-variants.ts))

另外还记录：

> 第一批 117/117 dual variants 都曾出现 option similarity 问题。([raw.githubusercontent.com](https://raw.githubusercontent.com/saga/ai-interview-questions/dev0902/scripts/assemble-variants.ts))

这意味着：

```text
旧 generator
   ↓
旧 variants
   ↓
现在 generator 已修复
```

但：

> **修复 generator ≠ 修复已经 commit 的旧数据。**

所以这次我不建议只改代码。

应该实际执行：

```text
question:validate-variants
```

把当前仓库里的：

```text
stale
near duplicate
```

全部列出来。

然后：

```text
bad historical variants
       ↓
delete / regenerate
```

否则你会出现：

> 生产管线现在是对的，但仓库里还保存着以前产出的坏资产。

# 八、Variant sourceHash 还有一个隐患

现在 Variant 的 `sourceHash` 只覆盖：

```text
question id
question text
options
```

而没有覆盖：

```text
topic
angle
difficulty
concepts
answer
```

这意味着：

```text
canonical metadata 改变
```

可能不会触发 Variant stale。

尤其是：

```text
angle
difficulty
concepts
```

这些字段越来越成为题库治理的重要信息。

如果你的最终 Variant 定义是：

> 轻量表达变体

那么至少我建议 source hash 包含：

```text
id
question
options
topic
angle
difficulty
concepts
```

`answer` 是否加入则需要看你最终的数据契约。

这个是 P1，不需要阻塞现在的整体架构。

# 九、题库本身：最大的问题已经不是“覆盖不够”，而是“Assessment Quality”

这一点和前一版相比变化很大。

现在已经有：

```text
1317 questions
77 files
topic × angle
misconceptions
curation
coverage
```

所以我不认为你当前最大的风险是“知识面不够”。

现在主要是：

```text
题目数量
    ↓
已经够

知识覆盖
    ↓
基本够

题目质量一致性
    ↓
仍然是短板
```

尤其是：

### 1. 正确项的信息密度偏高

虽然现在已经有 length / bias 检查，但：

```text
长度相似
```

不代表：

```text
信息量相似
```

一个选项可以和其他三个一样长，但它里面：

```text
条件更多
术语更多
限定更多
因果链更完整
```

依然非常容易被猜。

你的 `question-content-spec` 已经把这个问题写得很完整，但目前更多依靠生成 Prompt，而不是自动检测。([raw.githubusercontent.com](https://raw.githubusercontent.com/saga/ai-interview-questions/dev0902/docs/question-content-spec.md))

这属于：

**规范已经领先于执行。**

---

### 2. 部分 multiple choice 仍然有“多个正确项只是 explanation 的拆句”

你现在已经明确规定：

> 每个正确选项应该独立成立。

这个规范是对的。

但从当前题库样本看，仍然有一些：

```text
A = 原因
B = 结果
C = 原因 + 结果
```

这种题。

形式上是 multiple，实际上不是三个独立判断。

这会直接降低：

```text
diagnostic value
```

因为你不知道用户到底错在：

```text
mechanism
还是
consequence
还是
条件
```

建议把这一类作为 curator 的重点审查对象。

# 最后给一个真正需要执行的优先级

## P0 — 我建议现在就改

**1. 统一 Variant 定义**

把：

```text
Prompt Variant = 可以改变 angle / cognitive task
```

改成与你当前实际 schema/runtime 一致的：

```text
Variant = 同一 assessment contract 的表达/情境变体
```

需要改变 angle 的题，创建新的 canonical。

**2. 清洗当前已经提交的 Variant Pool**

尤其当前已经发现的：

```text
低自然度
历史 near-duplicate
```

不能继续留在正式题库里。

**3. `validate-variants` 改成真正的 release gate**

```text
stale > 0 → fail
duplicate > 0 → fail
```

## P1 — 下一轮做

```text
4. Variant sourceHash 扩展 metadata
5. 增加 deterministic language sanity gate
6. curator 增加“正确项信息密度/层级”重点检查
7. 对当前 1300+ canonical 做一次 multiple-choice quality audit
```

## 暂时不要做

```text
不要引入 vector DB
不要引入复杂 Variant ontology
不要让 Variant 自己参与 coverage
不要把 BKT/IRT 塞进题库生成
不要再增加大量 lint 规则
不要增加多个在线 LLM judge
```

### 最终判断

**`dev0902` 的架构已经基本过了“设计正确性”这一关，当前最大的风险已经转移到了“内容生产质量”和“生成资产治理”。**

尤其是这次实际看到的情况：

> **offline variant pipeline 已经搭起来了，但第一批真实 Variant 已经证明仅靠当前 `validateVariant + 5D challenger`，还不足以保证进入仓库的 Variant 都是高质量的。**

这是现在最应该解决的问题；而不是再去改 Agent 架构。
