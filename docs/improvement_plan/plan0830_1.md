我看了你现在 `main` 分支的实际代码，以及你给的 DeepSeek 四份官方文档。我的判断比较明确：

> **现在这个项目“能用 DeepSeek”，但还没有真正“按 DeepSeek 的能力来设计”。**

# 2. 最大的问题其实是 JSON Mode

你现在的 `pi.ts`：

```ts
const context: Context = {
  systemPrompt: system,
  messages: [message]
};

const res = await models.complete(model, context, {});
```

然后：

```ts
export function extractJSON<T = unknown>(raw: string): T {
  ...
  return JSON.parse(...)
}
```

也就是说，现在逻辑实际上是：

````text
LLM
 ↓
字符串
 ↓
自己找 ```json
 ↓
自己截取 {...}
 ↓
JSON.parse
 ↓
Zod
````

而 DeepSeek 官方明确提供 JSON Output：

```text
response_format: {
  type: "json_object"
}
```

而且官方还特别要求 prompt 中出现 `json`，并建议提供 JSON example。([DeepSeek API Docs][2])

所以现在的 `extractJSON()` 属于：

> **兼容性 fallback，而不是应该承担主结构化输出职责的机制。**

# 3. 应该把 `CompleteFn` 升级成“结构化请求”

现在：

```ts
type CompleteFn =
  (system: string, user: string) => Promise<string>
```

这个抽象对于 DeepSeek 太弱了。

我更建议：

```ts
type CompleteOptions = {
  responseFormat?: 'text' | 'json';
  temperature?: number;
  maxTokens?: number;
};

type CompleteFn = (
  system: string,
  user: string,
  options?: CompleteOptions
) => Promise<string>;
```

然后：

```ts
await complete(
  systemPrompt,
  buildEvalUser(...),
  {
    responseFormat: 'json',
    temperature: 0.1,
    maxTokens: 1500
  }
);
```

DeepSeek provider：

```ts
if (options?.responseFormat === 'json') {
  // response_format = { type: "json_object" }
}
```

其他 provider：

```text
DeepSeek      → native JSON mode
OpenAI        → native structured output / JSON
Gemini        → Gemini structured output
Chrome AI     → prompt + parser
Ollama        → format/schema
```

这样你仍然保持：

```text
application
    ↓
provider abstraction
    ↓
provider-specific optimization
```

而不是把 DeepSeek API 细节污染整个业务层。

# 4. 甚至可以比 JSON Mode 再进一步：Tool Call 作为结构化输出

这是我觉得你这个项目**特别值得利用 DeepSeek 的地方**。

DeepSeek 的 Tool Calls 本身就可以用于结构化输出，而且官方现在支持 strict schema。strict 模式要求：

```json
{
  "strict": true
}
```

并且 object 必须：

```json
"additionalProperties": false
```

所有 properties 都 required。([DeepSeek API Docs][3])

例如你的 Evaluation：

```json
{
  "correctness": 82,
  "completeness": 70,
  "architecture": 90,
  "communication": 85,
  "strengths": [],
  "gaps": [],
  "feedback": "..."
}
```

完全可以定义：

```text
submit_evaluation(
    correctness,
    completeness,
    architecture,
    communication,
    strengths,
    gaps,
    feedback
)
```

让 DeepSeek **必须调用这个工具**。

这样：

```text
现在

LLM
 ↓
text
 ↓
JSON parser
 ↓
Zod
```

变成：

```text
DeepSeek
 ↓
tool call
 ↓
schema validation
 ↓
domain validation
```

这是更干净的。

不过我不会马上把所有 JSON 都换成 tool call。

我的建议是：

### 普通结构化生成

使用：

```text
JSON Mode
```

例如：

* question variant
* evaluation

### Agent 决策

使用：

```text
Tool Calls
```

例如：

* searchQuestions
* getQuestion
* evaluateAnswer
* finishInterview

这正好符合你现在的架构。

# 7. 真正被你低估的是 KV Cache

这个可能是这次最值得改的。

DeepSeek 官方现在的 Context Caching 是**默认开启的**，不需要额外 API 参数。只要后续请求拥有完全匹配的 prefix，就可以命中缓存。([DeepSeek API Docs][5])

也就是说：

> 你不用“实现 KV Cache”。

你需要做的是：

> **设计一个容易命中 KV Cache 的 prompt/message layout。**

这是两回事。

# 10. 更进一步：Agent session 应该天然利用 KV Cache

你的 Agent 现在本身就是 multi-round。

DeepSeek API 是 stateless 的，也就是说每次请求必须把历史 messages 一起发送。([DeepSeek API Docs][6])

但这并不意味着这是坏事。

恰恰相反：

```text
Round 1

system
user(question1)


Round 2

system
user(question1)
assistant(tool call)
tool(result)
assistant(...)
user(answer2)
```

DeepSeek 可以对共同 prefix 做 cache。官方也明确说明：

```text
A + B
A + B + C
```

第二次请求可以命中 `A+B`。([DeepSeek API Docs][5])

所以你现在的 Agent architecture：

```text
pi-agent-core
   ↓
persistent message history
   ↓
DeepSeek
```

其实是**非常适合 DeepSeek 的**。

Adaptive interview
Agent
```

如果未来一次 session：

```text
10 questions
```

那么 DeepSeek 请求会变成：

```text
Round 1
system + profile + policy
        ↓
Round 2
system + profile + policy + Q1 + evaluation
        ↓
Round 3
system + profile + policy + Q1 + evaluation + Q2 + evaluation
...
```

这就是一个**非常典型的 KV-cache-friendly long-lived agent session**。

而且 DeepSeek 的 cache 命中信息可以直接告诉你：

```text
第 1 题：0%
第 2 题：72%
第 3 题：83%
第 4 题：88%
...
```

你甚至可以把它作为性能 telemetry。

# 27. 最后说 Prompt：我认为确实应该“DeepSeek 化”，但不要写成 DeepSeek 专属 prompt

这是最关键的一点。

我建议：

```text

       +
Structured Output Contract
       +
Provider Capability
```

而不是：

```text

```

也就是说：

```text
业务层：

↓

Structured layer：

↓

response_format=json_object
```

```text

"你决定下一步..."

↓

Tool layer：

tools=[...]

↓

DeepSeek adapter：

native tool calling
```

这样：

**同一个业务 prompt 可以服务多个 provider，但 DeepSeek 能吃到自己的 API 优势。**

# 28. 最终架构我建议是这个

```text
                    Interview Engine
                           │
                           ▼
                    LLM Abstraction
                           │
              ┌────────────┼─────────────┐
              │            │             │
          Variant       Evaluate       Agent
              │            │             │
          JSON Mode     JSON Mode    Tool Calling
              │            │             │
              └────────────┼─────────────┘
                           │
                     DeepSeek Adapter
                           │
             ┌─────────────┼─────────────┐
             │             │             │
          JSON Mode     Tool Calls    Thinking
             │             │             │
             └─────────────┼─────────────┘
                           │
                    Multi-round Messages
                           │
                           ▼
                      KV Cache
```

这其实和你现在项目的设计哲学非常一致：

> **LLM 负责不确定性，Domain 负责确定性。**

只是现在可以进一步变成：

> **DeepSeek 负责 reasoning / generation / tool orchestration；Domain 负责 truth / state / scoring / constraints；KV Cache 负责让长 session 变便宜。**

## 一句话评价当前代码

我会给现在的 DeepSeek integration：

**6.5/10。**

不是因为代码写得不好——恰恰相反，当前 `pi-agent-core + tools + domain-owned scoring + provider abstraction` 的方向已经不错。([GitHub][7])

主要问题是：

> **你现在是在“通过 DeepSeek 使用一个通用 LLM abstraction”，而不是“让 abstraction 暴露 DeepSeek 最擅长的能力”。**

其中最值得动的不是业务架构，而是 **LLM adapter + prompt layout**：

**Native JSON → Native Tool Calls → Multi-round message persistence → Stable Prefix → KV Cache telemetry → Agent Thinking。**

这条路线我认为很适合你当前这个项目，而且**不需要 over-design**。
