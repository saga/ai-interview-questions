我仔细看了当前 `main`，包括代码、Agent、题库 schema、Adaptive、Variant 管线、两段出题 Prompt、CI、README/ARCHITECTURE/ADR，以及最近几轮改动留下的设计痕迹。

先给结论：

**现在没有那种“马上跑不起来”的大故障，代码整体已经比较成熟；但仍有 4 个真正值得修改的大问题。**
其中 **P0 是“题库的测量契约已经升级，但系统没有把这个新契约真正贯彻到底”**。这个问题比某个函数 bug 更重要。

# P0-1：`cognitiveTask` 已成为 assessment contract，但实际上没有进入完整的“覆盖 / 选择 / 学习证据”闭环

这是目前最大的问题。

你现在明确把 canonical identity 定义成：

`topic × angle × difficulty × cognitiveTask`

`questionIdentity.ts` 也确实按四维判断 identity 是否变化。

但是系统其余部分仍然基本是 **`topic × angle` 世界**：

* coverage 还是 `topic × angle`
* Learner Memory 的 angle evidence 还是 `topic|angle`
* adaptive ranking 没有 `cognitiveTask`
* 选题策略没有根据 cognitiveTask 缺口做决策
* 没有 cognitiveTask coverage
* 没有 cognitiveTask mastery/evidence
* Agent 也没有一个“这个 Knowledge 哪种 cognitive task 已经验证过”的事实来源

`rankCandidatePool()` 的排序键明确只有：

`topic → angle → evidence → difficulty`

没有 cognitiveTask。

而 Learner Memory 也明确把 angle 作为独立证据维度，key 是：

`topic|angle`

没有 cognitiveTask。

这就产生一个很严重的语义问题：

> 你已经声明“explain / diagnose / compare / predict / apply / design …”是不同的测量能力，但系统实际上并不知道用户是否已经在这些不同认知任务上被验证过。

例如：

```text
Knowledge = KV Cache
angle = mechanism
cognitiveTask = explain
```

和：

```text
Knowledge = KV Cache
angle = mechanism
cognitiveTask = diagnose
```

按现在的 identity 设计是两个不同 assessment contract。

但 Adaptive 只看到：

```text
KV Cache × mechanism
```

所以用户刚刚做过 `explain`，系统完全可能认为这个 angle 已经有证据，然后继续换别的角度；或者反过来在同一 `topic × angle` 上反复问同一种 cognitiveTask。

### 更本质的问题

你现在实际上存在两个互相竞争的模型：

**模型 A：**
`Knowledge → Angle → evidence`

**模型 B：**
`Knowledge → Angle → CognitiveTask → assessment identity`

现在 B 只落实到了 schema / ID / prompt，却没有落实到 learner model 和 selection policy。

这会让新的 `cognitiveTask` 变成一种“metadata-only feature”。

### 应该怎么改

不是简单给 `angleCoverage` 再加一个字段就完事。

应该明确：

```text
assessment evidence key
    = topic × angle × cognitiveTask
```

然后：

```text
coverage
    = topic × angle × cognitiveTask

learner evidence
    = topic × angle × cognitiveTask

adaptive ranking
    = weak / missing assessment cells
      → angle
      → cognitiveTask
      → difficulty
```

`topic × angle` 可以保留作为较粗粒度的 dashboard 指标，但不能再是唯一的 assessment coverage 主索引。

否则 ADR-077 的核心设计事实上只实现了一半。

# P0-2：新的 Blueprint 明确生成 `assessmentTarget / reasoningGoal`，但转换后被直接丢掉

这是第二个结构性问题，而且和 P0-1 是一脉相承的。

`prompt_part1` 明确要求 Blueprint 输出：

* `assessmentTarget`
* `reasoningGoal`
* `keyConcepts`
* angle
* cognitiveTask
* difficulty

而且整个新 Prompt 的核心理念就是：

> 不是“这个知识叫什么”，而是“考生必须完成什么认知行为、走什么推理链才能答对”。

`prompt_part2` 继续要求最终题目严格遵守这些 blueprint 属性，并再次要求：

* assessmentTarget
* reasoningGoal
* cognitiveTask
* angle

必须与 Blueprint 保持一致。

但是 `convert-blueprint-output.ts` 在真正落库的时候：

* `assessmentTarget` → warning，然后丢掉
* `reasoningGoal` → schema 里甚至没有
* `knowledgeId` → 只用于检查，随后丢掉
* 真正保留下来的核心 assessment 描述，主要只剩 `angle / cognitiveTask / difficulty / topic`

代码本身写得非常明确：`assessmentTarget` 只产生 warning，canonical 写入对象里没有它；`reasoningGoal` 也没有进入最终 Question。

这意味着你的新生成管线实际上变成：

```text
网页
 ↓
Knowledge
 ↓
Blueprint
   ├─ assessmentTarget
   ├─ reasoningGoal
   ├─ cognitiveTask
   └─ angle
 ↓
最终 Question
   ├─ cognitiveTask
   ├─ angle
   └─ difficulty
```

**最有价值的“测量意图”信息在中间被丢了。**

这会产生两个后果。

### 第一，后续无法真正验证“题目是不是在测 Blueprint 指定的东西”

例如 Blueprint：

> reasoningGoal：先根据现象识别 load imbalance，再区分 importance/load 两种平衡，再判断为什么单独增加某项 loss 无法解决 OOM。

最终题目只留下：

```json
{
  "topic": "...",
  "angle": "diagnosis",
  "cognitiveTask": "infer"
}
```

以后你再审题，已经失去了：

> “这道题原本究竟要求考生走哪条 reasoning path？”

这对题库长期治理非常不利。

### 第二，Variant 的“不同 reasoning path”更难验证

你现在新的 Variant 定义是：

> 同一个 Knowledge，但采用不同 reasoning path。

但系统没有持久化真正的 reasoning contract，最终只能依赖：

```text
angle changed?
cognitiveTask changed?
```

这其实不够。

**不同 angle / cognitiveTask 是必要条件，但不是 sufficient condition。**

两个题完全可能：

```text
angle = diagnosis
cognitiveTask = diagnose
```

相同，但 reasoning path 完全一样。

### 应该怎么改

我建议至少把：

```text
assessmentTarget
reasoningGoal
```

变成真正的 question-level metadata，或者更加结构化一些，例如：

```ts
assessment: {
  target: string
  reasoningGoal: string
}
```

它们不是给 UI 展示的，而是：

* blueprint → question 的契约
* question review 的审计上下文
* variant challenger 的比较依据
* 后续质量分析的依据

**不需要拿它们直接参与 runtime selection。**

这样就能形成：

```text
Knowledge
  ↓
Assessment Contract
  ├─ angle
  ├─ cognitiveTask
  ├─ difficulty
  ├─ assessmentTarget
  └─ reasoningGoal
```

这才是你现在 Prompt 真正设计出来的东西。

# P0-3：Variant 的 `sourceHash` 漏掉了 `cognitiveTask`，会导致“canonical 已变，但 variant 仍被认为新鲜”

这是一个很具体，但影响很大的实际 bug。

你现在已经明确说：

> `cognitiveTask` 是 assessment contract 的第四维。

但是 `variantSourceOf()` / `computeVariantSourceHash()` 的 source hash 字段是：

```text
id
topic
subtopic
angle
difficulty
tags
question
options
```

**没有 cognitiveTask。**

这和它自己的注释其实直接冲突：

> “sourceHash 覆盖元数据”

现在实际上并没有覆盖完整 assessment contract。

假设：

```text
canonical v1
topic = rag
angle = diagnosis
difficulty = medium
cognitiveTask = diagnose
```

生成 variant。

之后你把 canonical 改成：

```text
cognitiveTask = infer
```

按你的 identity 设计，这是 assessment contract 变化。

但因为 `sourceHash` 不看 cognitiveTask：

```text
old sourceHash == new sourceHash
```

所以旧 variant **可能不会被判 stale**。

这会出现非常隐蔽的数据污染：

```text
canonical:
    新的 cognitiveTask

variant:
    按旧 cognitiveTask 生成
    stale checker:
        fresh
```

而系统自己还会认为这一切合法。

### 这个我建议直接修

`VariantSource` 增加：

```ts
cognitiveTask?: string
```

并纳入 hash。

也应该同步修：

* source hash 单测
* stale validator
* variant generation / assembly
* 文档中的 sourceHash 定义

这是一个明确的 P0/P1 级 correctness bug，不属于细碎问题。

# P1-1：Runtime Variant 仍然是“表达改写器”，和你新的 ADR-077 Variant 定义并不完全一致

这是现在最容易被忽视的问题。

新 Prompt 已经明确规定：

> Variant 不是改写，而是同 Knowledge 的不同 measurement / reasoning path。

新的文档也已经明确采用 ADR-077 口径。

但是 runtime variant 的实际 Prompt 还是：

> 改写题干 + 逐项改写选项表达，保持技术含义不变。

而 `buildUser()` 给模型的输入只有：

```text
topic
requiredConcepts
question
options
```

甚至：

* 不给 angle
* 不给 cognitiveTask
* 不给 assessmentTarget
* 不给 reasoningGoal

所以这个 LLM **根本无法按 ADR-077 设计去产生“不同 reasoning path”**。

它真正生成的是：

```text
Presentation Variant
```

而不是：

```text
Assessment Variant
```

现在代码通过 `QuestionVariant.angle/cognitiveTask` 给它预留了字段，`applyVariant()` 也已经会落地这些字段，所以前面的“死字段”问题已经修掉了。

但：

> **runtime generation 本身还是不知道这些字段应该怎么变化。**

### 这件事应该明确二选一

#### 方案 A：runtime variant 就定义成 Presentation Variant

这是我更推荐的现实方案。

那么明确规定：

```text
offline Variant
    = Assessment Variant
    = 可以换 angle / cognitiveTask

runtime Variant
    = Presentation Variant
    = 不可以换 angle / cognitiveTask
```

两者使用不同 schema / kind。

这样最干净。

#### 方案 B：runtime 也支持 Assessment Variant

那就必须把：

```text
current assessment contract
target assessment contract
reasoningGoal
assessmentTarget
```

交给模型，而且必须增加真正的 validator/challenger。

以你当前产品阶段，我觉得 **没必要把 runtime 做这么重**。

所以我建议 A。

# P1-2：题库的“质量门禁”仍然明显落后于你的 Prompt 质量要求

代码现在有非常多 validation：

* answer index
* duplicate options
* option prefix
* angle
* topic
* misconceptionMap
* option length bias
* semantic drift
* near-duplicate variant
* stale variant

这部分已经相当扎实。

但真正决定题目有没有价值的规则，仍然大部分不能自动检查。

例如 Prompt 明确要求：

> 多选题至少两个彼此独立的正确选项。

> 正确选项不能只是一个事实的不同表达。

> distractor 必须像“懂一些但理解不完整的工程师”。

> Variant 必须真的需要不同 reasoning path。

而 `audit-question-quality.ts` 自己已经非常诚实地承认：

* mixed-correct-level：0/4
* stuffed-option：1/7
* density cueing：3/8
* single-judgement：1/1

最终它只能：

> **exit 0，只做候选排序，不做门禁。**

这本身没错，我甚至不建议简单地把这些 detector 全部变成 hard gate。

真正的大问题是：

> **现在“机器可证”的质量和“Prompt 要求的质量”之间缺了一个正式的 challenger 层。**

尤其是你自己已经发现：

> “两个正确项逻辑上互为逆否，但字符串相似度很低”，机器 detector 抓不到。

你在最近的审计记录里已经实际遇到这一类问题。这个方向说明：

```text
detector
≠
question quality evaluator
```

你现在真正需要的是：

```text
Deterministic validation
        +
LLM Challenger
        +
Human review
```

而不是继续堆 heuristic。

这个我认为值得做，但优先级低于前三项，因为它不会马上污染架构，只是会继续产生质量不稳定题。

# P1-3：`misconceptionMap` 仍然不是完整的题库能力

这点目前已经比之前好很多，不能再说“完全没做”。

`Learner` 已经真正支持：

```text
misconceptionHits
```

并且 selection-choice 可以产生非 LLM 的误解证据。

schema 也保证：

* map 与 options 等长
* index 合法
* 正确项不能映射 misconception

这一块已经比较规范。

但是题库里的这一层仍然很稀疏。

你自己的仓库审计记录已经指出：

> 目前只有约 10% 量级的题真正拥有 misconceptionMap，绝大多数题并没有这类确定性反证信号；没有 `misconceptions` 的题本身也无法依靠 backfill 自动补齐。

所以现在的状态是：

```text
Learner infrastructure：有
schema：有
runtime aggregation：有
题库 coverage：不足
```

这意味着你的“选择题 → 误解诊断 → adaptive”能力，在整体题库中仍然不是主路径。

### 我不会建议现在继续做复杂算法

不要上 DKT / Bayesian / IRT 来掩盖这个问题。

先把：

```text
high-value question
→ misconceptions
→ misconceptionMap
```

覆盖率提高到真正可用的水平。

否则上层的“诊断智能化”收益很低。

否则后面再改一次 Variant、assessment contract 或 Question schema，很容易再次出现“代码是新版，Prompt 是另一版，ADR 又是第三版”。

## 我对当前项目的总体判断

现在这个项目已经**不是“架构方向有问题”**，而是进入了一个非常典型的阶段：

```text
第一阶段：
Schema / Runtime / Agent / Validator 建起来
        ↓
第二阶段：
Prompt / Question Quality / Variant Model 升级
        ↓
现在：
“新测量模型有没有真正进入整个系统”
```

所以现在最大的风险不是缺功能，而是出现这种状态：

```text
Prompt 已经变聪明了
      ↓
Schema 也升级了
      ↓
ADR 也升级了
      ↓
但 runtime / learner / coverage 仍按旧模型运行
```

你目前 **最大的结构性债务就是这一点**。

最值得下一轮直接做的是把整个系统统一成：

```text
Knowledge
   ↓
Assessment Contract
   ├── angle
   ├── cognitiveTask
   ├── difficulty
   ├── assessmentTarget
   └── reasoningGoal
        ↓
Canonical Question
        ↓
Assessment Variant
        ↓
Learner Evidence
        ↓
Adaptive Selection
```

一旦这一条链打通，当前代码 / Prompt / 题库的整体设计会真正闭环；现在虽然已经有了绝大多数零件，但还没有完全成为同一个模型。
