需要改，但不需要再造一套复杂的题库系统。你现在已有 `question:add`、`question:audit`、`question:coverage`、语义重复分析，以及 `article-to-questions / fill-coverage-gap / check-question-bank-quality` skills，基础已经够了。真正缺的是把“**题目质量**”从人工原则提升成一套统一的生成门槛和验证信号。当前仓库的校验仍主要集中在 schema、答案索引、重复、长度、topic/angle 和 coverage；它还不能直接判断“题是不是好题”。([GitHub][1])

我建议按下面改。

---

# 1. `docs/prompt.md`：只增加 4 个核心约束

你现在这份 Prompt 已经有 `Concept`、`Angle`、self-contained、干扰项、architecture、diagnostic value 等内容，不建议继续堆规则。([GitHub][2])

只补这四条。

### A. Concept Scope

放到 Concept 部分：

```md
每道题必须有一个明确的核心 Concept。

默认只考一个核心 Concept，可包含 0～2 个 supporting/prerequisite concepts。
除 comparison / design / system-design 外，不要要求考生同时掌握多个独立 Concept 才能作答。

一道题如果答错后无法较明确判断考生缺失的是哪一个知识点，则题目范围过大，应拆分。
```

这会约束现在容易出现的“大杂烩题”。

---

### B. Answer Determinism

放到选择题部分：

```md
正确答案必须在当前题干约束下唯一且稳定。

对于 multiple：
- 每个正确选项都必须独立成立；
- 每个错误选项都必须独立可解释地错误；
- 不得存在“技术上也可能成立”的模糊选项；
- 不得依赖未写出的隐藏前提才能区分答案。
```

---

### C. Option-level consistency

放到选项设计：

```md
所有选项应处于相同的决策层级、抽象层级和粒度。

不要让正确项天然包含更多组件、更多条件或更完整的解决方案。
难度应来自技术判断，而不是正确选项的信息量。
```

你现在已经有长度 1.8× 的硬门禁，但那只能解决表面泄题，不能解决“正确答案更完整”的结构性泄题。当前自动审计确实只直接检查长度比。([GitHub][3])

---

### D. Diagnostic Value

最后增加一句即可：

```md
优先生成能够产生明确诊断信号的题目：
答错后，应能较明确反映 Concept、机制、trade-off、工程判断或典型 misconception 的缺失。

如果一道题“做错了但不知道具体哪里不会”，其诊断价值较低。
```

---

# 2. `skills/article-to-questions/SKILL.md`：这里要明显加强

当前这个 skill 已经正确负责：

```text
文章 → 题目 → add-question-to-bank 校验
```

而且现在已经要求 self-contained、避免产品绑定、每题一个知识点、multiple ≥ 2/3。([GitHub][4])

但是它现在仍然偏“**怎么生成**”，缺少“**生成后怎么判断是不是好题**”。

建议把“内容质量把关”改成下面 5 条：

```md
### 内容质量把关

生成每道题后必须检查：

1. Core Concept
   - 是否存在一个明确核心 Concept？
   - 是否混入过多独立知识点？

2. Cognitive Task
   - 是否要求理解、比较、应用、debugging、trade-off 或设计？
   - definition/fundamental 题只有在具有明显区分度时保留。

3. Answer Determinism
   - 正确答案集合是否唯一？
   - 是否存在“有条件也正确”的错误项？

4. Option Quality
   - 所有选项是否处于同一决策层级和粒度？
   - 是否可以通过长度、完整度、术语数量、语气猜答案？

5. Diagnostic Value
   - 答错后是否能明确反映一个知识或能力缺口？
```

然后明确：

```md
不要把“覆盖新的 topic × angle”作为生成低价值题的理由。
Coverage 是选题信号，不是质量通过条件。
```

你当前 `fill-coverage-gap` 已经写了类似原则，但 article skill 也应该明确，否则两条路径的质量标准会不一致。([GitHub][5])

# 3. `skills/fill-coverage-gap/SKILL.md`：这里不要再强调“把格子填满”

这个 skill 当前已经很好地写了：

> coverage 是信号，不是目标。

这是应该保留的。([GitHub][5])

但还缺一个**题量控制规则**。

建议加：

```md
### 题量控制

同一 topic × angle 已有 3 道以上题目时，新增题必须证明至少一个真实新增价值：

- 不同认知任务
- 不同工程场景
- 不同典型 misconception
- 不同难度层次

仅改变措辞或替换同义词不算新增价值。

同一核心 Concept 不应因为 coverage 而无限扩张。
```

这样可以防止：

```text
KV Cache
→ mechanism 1
→ mechanism 2
→ mechanism 3
→ mechanism 4
→ mechanism 5
```

最后题库变大，但信息增量越来越小。

---

# 4. `skills/add-question-to-bank/SKILL.md`：这里增加“结构质量门槛”

当前 skill 已经有：

* schema
* multiple ≥ 2/3
* 真实干扰项
* option length
* semantic duplicate
* question:add check
* validate/test/typecheck

这些都保留。([GitHub][6])

增加三条即可：

```md
### 结构质量

* 每题必须有一个明确核心 Concept。
* 同一 topic × angle 已有 ≥3 题时，必须确认新题存在新的认知任务或诊断价值。
* 选项必须处于相同的决策层级；不得仅通过“更完整/更具体”制造正确答案。
```

另外，把当前：

> 单选题占比 > 1/3 时直接报错

保持不动；这已经有实际代码门禁。([GitHub][6])

# 5. `skills/check-question-bank-quality/SKILL.md`：这里是最值得改的

现在检查顺序主要是：

```text
schema
重复
distribution
coverage
length
vendor/source
```

然后人工抽查内容。([GitHub][1])

我建议把质量检查正式拆成三层：

```text
Level 1 — Contract
Level 2 — Statistical / heuristic
Level 3 — Content quality
```

### Level 1：Contract

现有保持：

```text
id
topic
angle
answer
format
schema
```

### Level 2：Heuristic

现有保持：

```text
duplicate
semantic duplicate
option length
single/multiple ratio
coverage
difficulty
angle distribution
```

### Level 3：Content

新增：

```text
concept scope
answer determinism
option granularity
diagnostic value
engineering reasoning
```

注意：

**Level 3 不要硬塞成全自动规则。**

应该由：

```text
LLM challenger
+
人工复核
```

负责。

这和你当前 skill 的原则其实一致：结构通过不等于内容正确。([GitHub][1])

# 6. `question_audit.py`：我只建议加 3 个新指标

不要把 Python audit 做成一个大型 NLP 系统。

### A. `topic_angle_density`

现在只有：

```text
topic × angle 是否存在
```

建议再统计：

```text
topic × angle → question count
```

并输出：

```json
{
  "topic": "kv-cache",
  "angle": "mechanism",
  "count": 5
}
```

然后标记：

```text
0 → gap
1 → sparse
2 → healthy
3 → deep
4+ → oversaturated
```

注意这只是**信号**，不是自动删除。

---

### B. `conceptual-cluster-density`

你现在已经有 semantic clustering 能力。`question_analysis.py` 已经使用本地 multilingual MiniLM 做语义重复和概念簇分析。([GitHub][1])

把结果从：

```text
semantic duplicate
```

进一步变成：

```text
cluster:
KV Cache / mechanism
  7 questions
```

然后报告：

```text
cluster size > N
```

它意味着：

> 可能出现“同一知识反复考”的情况。

这比单纯 fuzzy duplicate 更有价值。

---

### C. `difficulty × angle`

现在只统计独立分布。([GitHub][3])

增加：

```text
angle × difficulty
```

例如：

```text
definition:
  easy 18
  medium 4
  hard 0

debugging:
  easy 1
  medium 8
  hard 16
```

这样更容易发现：

> hard 题其实只是被标成 hard，但内容仍然是 definition。

这个指标很便宜，值得加。

---

# 7. `question_analysis.py`：不要马上增加“质量总分”

我不建议现在做：

```text
quality_score = 87.3
```

因为这种分数非常容易产生伪精确感。

更好的输出是：

```text
value:
  high
  medium
  low

diagnostic:
  high
  medium
  low

duplication:
  low
  medium
  high

option-quality:
  pass / review

answer-determinism:
  pass / review
```

然后给出：

```text
KEEP
REVIEW
REWRITE
```

这比：

```text
83/100
```

更适合这个项目。

# 8. 最值得新增一个 `question:review`，但不要做成复杂服务

你现在：

```text
question:add
question:audit
question:coverage
```

我建议只增加一个轻量命令：

```text
npm run question:review -- <id>
```

作用：

```text
读取一题
 ↓
显示：
- topic / angle / difficulty
- 同 topic × angle 已有题
- semantic nearest questions
- option length
- question analysis
 ↓
输出 REVIEW checklist
```

这个非常适合 Agent 在改题之前使用。

不用 DB，不用 API，不用独立服务。

# 9. `question:add --check` 应该增加一个非常小的 batch-level 检查

现在已经能检查：

```text
multiple >= 2/3
```

这是很好的。([GitHub][6])

再加：

```text
same topic + same angle + same cognitive pattern
```

例如一个 batch：

```text
Q1 KV mechanism
Q2 KV mechanism
Q3 KV mechanism
Q4 KV mechanism
Q5 KV mechanism
```

即使每题都不重复，也说明生成策略有问题。

不一定直接失败，可以：

```text
WARN:
batch has 5 questions but 4 share the same topic × angle
```

这样就够了。

# 10. 你现在最缺的不是更多 validation，而是“内容 challenger”真正形成门

你已经有：

```text
Question Challenger
```

而且它现在检查：

```text
self-contained
sufficiency
logic
answer uniqueness
distractors
explanation
value
```

这其实正好覆盖我们刚刚讨论的内容质量。([GitHub][4])

所以不要重新写一套 validator。

应该把流程明确成：

```text
Prompt
 ↓
生成
 ↓
Schema validation
 ↓
Deterministic audit
 ↓
Question Challenger
 ↓
KEEP / REVISE / REJECT
 ↓
人工确认
 ↓
add
```

这是当前最适合这个项目的 pipeline。

# 最终建议的生产链

我会直接把题库相关系统收敛成：

```text
                 ┌─────────────────┐
Article ────────►│ Generation      │
                 │ prompt / skill  │
                 └────────┬────────┘
                          ↓
                    Draft Questions
                          ↓
                 ┌─────────────────┐
                 │ Contract        │
                 │ Zod / bank.test │
                 └────────┬────────┘
                          ↓
                 ┌─────────────────┐
                 │ Heuristic Audit │
                 │ duplicate       │
                 │ length          │
                 │ distribution    │
                 │ coverage        │
                 └────────┬────────┘
                          ↓
                 ┌─────────────────┐
                 │ Challenger      │
                 │ value           │
                 │ determinism     │
                 │ distractors     │
                 │ diagnostic      │
                 └────────┬────────┘
                          ↓
                    Human Review
                          ↓
                    Question Bank
```

其中最关键的原则：

> **Schema validation 保证“合法”；Audit 保证“没有明显问题”；Challenger/人工复核保证“值得保留”。**

这和你当前已经存在的 `add-question-to-bank`、`article-to-questions`、`fill-coverage-gap`、`check-question-bank-quality` 四个 skill 的职责基本一致，不需要重新分层。([GitHub][7])

### 优先级

真正值得现在就改的是：

**P0**

1. `prompt.md` 增加 Concept Scope + Answer Determinism + Option Granularity。
2. `check-question-bank-quality` 明确增加内容质量层。
3. `article-to-questions` / `add-question-to-bank` 统一这些质量规则。

**P1**
4. `question_audit.py` 增加 `topic×angle question count`。
5. 增加 `difficulty×angle` 分布。
6. 用已有 semantic analysis 做“同 Concept / 同认知任务过密”提示。
7. `question:add --check` 增加 batch pattern warning。

**暂时不要做**

* 质量总分 0～100
* 自动 LLM judge 作为硬门禁
* 大型 question-quality ML 模型
* Vector DB / 新知识索引
* BKT/IRT 与题库 validation 强耦合

这样改完以后，题库系统会从现在的：

> **“格式正确 + 不重复 + coverage 合理”**

提升成：

> **“格式正确 + 不重复 + 覆盖合理 + 有明确认知任务 + 答案可判定 + 干扰项有质量 + 能产生有效学习诊断”**

而且不会明显增加你现在这套工程的复杂度。
