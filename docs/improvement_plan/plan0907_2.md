# 三、Concept 就是“业务里大家在说什么”

例如：

```json
{
  "id": "vip-customer",
  "name": "VIP 客户",
  "description": "满足年度消费额、客户等级或合同条件之一的客户",
  "domain": "customer"
}
```

这个东西非常简单。

> “VIP 客户”到底是什么意思？

对于 1000 人企业，这已经非常有用了。

因为现实中最大的问题往往不是没有 ontology，而是：

```text

≠
销售对“客户”的理解
≠
客服对“客户”的理解
≠
数据团队对“客户”的定义
```

企业 semantic layer 真正解决的首先就是这个问题。Microsoft 对 Fabric ontology 的描述也是“统一 enterprise vocabulary”，核心就是 entity type、property、relationship、constraint，而不是先建设一个庞大的理论知识体系。([Microsoft Learn][3])

# 四、Rule 才是企业知识最值钱的部分

很多企业真正重要的知识，其实不是“客户是什么”。

而是：

```text
什么情况下可以做什么
```

例如：

```json
{
  "id": "refund-policy-001",
  "type": "rule",
  "statement": "订单签收后 7 天内且商品未使用时可申请无理由退款",
  "conditions": [
    "order.status = delivered",
    "daysSinceDelivery <= 7",
    "product.used = false"
  ],
  "source": "customer-service-policy-v12"
}
```

这就已经非常有价值了。

因为 Agent 可以拿这个回答：

> “这个订单能不能退款？”

而不是只找到一篇 20 页的 PDF。

# 八、Enterprise Knowledge 最重要的其实不是 Graph，而是“可复用”

没必要做成标准 Knowledge Node。

所以真正应该用的是：


而不是：


# 9. 为什么 Claims 比 `required[]` 更重要

因为你未来肯定会遇到这种问题：

```text

  required[0]
  required[1]
  required[2]
```

其中：

```text

```

后来被证明需要修正。

现在很难做到：

```text
“只修改一个知识断言”
```

因为它只是字符串。

如果以后是：

```text
claimId
```

那么你可以：

```text
Claim C1
  ↓
Question Q1
  ↓
Question Q8
  ↓
Misconception M3
  ↓
Evidence E17
```

就形成真正的知识血缘。

这也是为什么知识图谱/ontology 工程越来越强调结构化语义以及 schema-based representation，而不是完全依赖 LLM 隐式语义。相关综述把 ontology engineering、knowledge extraction、knowledge fusion 分成不同阶段；近期工作还特别强调 ontology modularity。([arXiv][3])

# 10. Knowledge 不应该只有 “是什么”，必须有 Scope

企业知识尤其如此。

例如：

```text
GQA reduces KV cache memory.
```

这句话不是永远成立的。

真正知识应该是：

```text
subject:
  GQA

claim:
  reduces KV cache memory relative to MHA

conditions:
  same hidden size
  same Q-head count
  fewer KV heads
```

即：

```text
Knowledge
  = Claim + Conditions
```

这点对企业比 AI 面试题更加重要。

比如：

```text
“这个审批可以自动化”
```

实际上可能依赖：

```text
region = JP
amount < ¥1,000,000
riskLevel < high
policyVersion >= 2026-04
employeeRole = manager
```

# 12. Provenance 不应该只是 `source`

企业知识尤其应该区分：

```text

evidence
confidence
validity
```

不是：

```json

  "source": "some-doc"
}
```

而更像：

```ts
{
  id: "claim-evidence-17",

  source: {
    type: "official-doc",
    ref: "...",
    location: "...",
  },

  authority: "official",

  observedAt: "...",

  validFrom: "...",

  validTo: null,

  confidence: 0.97
}
```

注意：

> **confidence ≠ truth**

confidence 是“我们有多相信它”。

authority 是“这个来源有多权威”。

provenance 是“它从哪里来的”。

这三个必须分开。

AWS 的当前 semantic-layer architecture 已经把 learned facts 明确设计成带 provenance 和 confidence 的结构化 assertions，并通过 validation / verification 才提升状态。([Amazon Web Services, Inc.][4])

# 19. 但不要走到另一个极端：每一个 proposition 都变成 Knowledge

这里也要特别小心。

不能这样：

```text
Knowledge #1:
KV cache stores K

Knowledge #2:
KV cache stores V

Knowledge #3:
Q is not cached

Knowledge #4:
memory grows with sequence length
```

这样又过度 atomize 了。

真正好的 atomicity 原则是：

> **如果拆开之后会产生不同的 prerequisite、不同的 failure mode、不同的 decision，应该拆。**
>
> **如果拆开之后破坏了一个完整的机制/因果链，就应该保留。**

例如：

```text
KV Cache
  └── memory scaling
```

可以是一个 coherent unit。

但：

```text
KV Cache memory scaling
```

和：

```text
KV Cache implementation correctness
```

已经是两个不同知识单元。

# 20. 可以给 Knowledge 设计一个非常实用的 Atomicity Test

以后所有知识生成都问 6 个问题：

### ① 一句话能否定义？

```text
它到底是什么？
```

### ② 是否只有一个核心现象/机制？

不是：

```text
A + B + C + D
```

### ③ 是否有明确边界？

```text
什么时候成立？
什么时候不成立？
```

### ④ 能否写成若干稳定 Claims？

如果不能，它很可能太模糊。

### ⑤ 是否支持一个连贯的判断/决策？

如果没有，可能只是 Concept。

### ⑥ 是否存在独立证据？

如果不同部分需要完全不同证据，很可能应该拆。

这个比“1 个核心 Concept + 3 个 supporting concepts”更稳。

```text
                        │   Competency    │
                        │ what can be done│
                        └────────┬────────┘
                                 │
                                 ▼
                        ┌─────────────────┐
                        │   Assessment    │
                        │ how to measure  │
                        └────────┬────────┘
                                 │
                                 ▼
                        ┌─────────────────┐
                        │    Question     │
                        │ observable      │
                        │ evidence        │
                        └─────────────────┘
```

而 learner 再独立存在：

```text
Knowledge / Claim
       │
       ▼
Learner Evidence
       │
       ▼
Mastery / Cognitive State
```

这就把：

```text
Knowledge representation
Learning representation
Assessment representation
```

完全分开了。

# 36. 我的最终判断

**当前仓库不需要推翻。**

实际上它已经具备一个不错的雏形：

```text
stable Knowledge ID
+
required claims
+
misconceptions
+
Concept Graph
+
Assessment Contract
+
Question as evidence
```

这些方向都是对的。

但现在最需要解决的不是继续加：

```text
keyIdeas
tradeoffs
more fields
more angles
more tags
```

而是做一次**概念层重构**：

### 从

```text
KnowledgeNode
 = Concept + Summary + Required + Misconceptions + Assessment Metadata
```

变成

```text
Concept
+
Knowledge Unit
+
Claims
+
Relations
+
Evidence
+
Competency
+
Assessment
```

其中真正的核心变化只有一句话：

> **Concept 表示“我们谈论什么”；Knowledge 表示“关于它哪些事情成立以及在什么条件下成立”；Competency 表示“人/Agent 能用这些知识做什么”；Assessment 表示“如何观察到这种能力”。**

这套定义不仅比当前 `KnowledgeNode` 更适合你的 AI Interview Trainer，也更接近企业 semantic layer / ontology / knowledge graph 的长期演化方向。AWS 当前的 semantic-layer 架构和 Palantir 的 operational ontology 都在强调稳定语义结构、结构化事实/关系、可追溯性以及面向决策和行动的能力；学术界的 KG/ontology 研究则强调 schema、模块化、结构化关系与 LLM 之间的结合，而认知诊断研究进一步说明“知识本身的结构”和“学习者掌握状态”应当分开建模。([Amazon Web Services, Inc.][4])

**对你这个 repo，我下一步最建议做的不是直接改代码，而是先把 `Knowledge Model v2` 定下来，然后据此反推 `prompt_part1 → knowledge JSON → concept graph → Question → cognitive diagnosis` 整条链。** 这样后面 BKT/IRT、Agent Knowledge、企业 Knowledge 都能沿着同一个骨架继续扩，而不会再次出现“为了一个新需求给 KnowledgeNode 再加一个字段”的循环。
