### 任务

你会收到一篇 AI/ML 技术文章。你的任务是把文章转化为高质量的**面试选择题**，用于面试题库训练候选人对该主题的理解，而不是检验候选人是否读过这篇文章。

先分析文章内容，识别值得考察的核心知识点（Concept / Subtopic），选出最有面试价值的部分，生成选择题（单选或多选，多选优先，题型依内容自然选择）。不要平均覆盖文章，也不要按段落顺序出题。

优先选择：知识点重要、能区分理解深度、容易产生典型误解、能考察机制/应用/工程判断或 trade-off 的部分。

### 考察角度

围绕同一个 Concept 从不同角度出题，避免只是换个说法重复考察同一件事：

* definition：术语和概念的准确定义
* fundamental：基本概念、核心原理
* mechanism：内部机制、工作过程、因果关系
* comparison：不同方法、架构或方案的区别
* tradeoff：设计取舍、优缺点、适用条件
* scenario：真实工程场景中的应用和判断
* debugging：根据现象定位问题、分析错误原因
* design：根据需求设计或选择技术方案（组件/模块级）
* system-design：更大范围的系统设计权衡（架构选型、容量、可靠性、成本）
* calculation：涉及计算、复杂度、资源关系的定量判断

不要求覆盖所有角度，也不要为凑角度生成低价值问题。重要 Concept 应优先用不同角度形成多维考察——例如 Transformer 不要反复问"是什么/核心是什么"，而是拆成 self-attention 机制、MHA/MQA/GQA 比较、KV cache trade-off、长上下文性能、常见实现错误、架构设计取舍等互补角度。

### 题目必须 self-contained

假设考生看不到原文章，仅凭题干和选项就能理解背景、场景和约束并推理作答。若某个知识点依赖文章特定的背景、架构或实验结果，把回答所需的最小 context 写入题干，但不要把整段文章搬进去。

不要出现"文中提到 / 根据本文 / 上述方法 / 该方案 / 作者认为 / 前文所述"这类依赖原文的表达，除非相关对象已在当前题干中被明确描述。

题目应考察对概念、机制、因果关系、方案比较、工程 trade-off、错误识别或定量分析的理解，而不是原句记忆、单纯记数字，或"文章列出了哪几个……"这类阅读理解题——除非该数字或事实本身就是知识点不可分割的核心组成部分。

### 选择题选项设计

目标：考生必须依靠知识和推理作答，不能靠选项的长度、措辞、语法或信息量猜答案。单选多选，选项最少4个。多选题选项可以在4～6个，最多6个。

* 正确选项不得因为"更严谨"而明显更长、更具体、信息量更大，也不能只有它带限定条件、专业术语或谨慎语气。
* 错误选项必须是完整、自然、有技术可信度的陈述（源自真实的概念混淆、条件遗漏或 trade-off 判断错误），不能写得简短、模糊、荒谬，也不能故意绝对化、极端化。
* 同一题的选项应保持相近的长度、信息密度、句式结构和专业表达程度，尽量用平行结构（例如都采用"通过缓存 X 来减少 Y"式因果表达）。
* 不要靠堆砌无意义文字凑长度；出现长度偏差时应重新平衡整套选项，而不是只缩短正确答案。
* 正确答案位置随机分布，不形成固定模式。

### 最终检查

对每道题确认：删除原文章后题目仍可独立理解；明确对应一个 Concept 和一个考察角度；测试的是理解/应用/判断而非文章记忆；同一 Concept 的多道题角度不重复；仅凭选项的长度、语气或具体程度是否仍可能猜出答案。发现任何答案形式线索，就重新平衡或重写整套选项，而不是只改正确答案。

最终只输出 5～13 道最有面试价值的题目。
