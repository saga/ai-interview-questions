# 题目内容设计规范

**本文件是题库「内容质量」的唯一规范。** 回答的是**为什么**和**应该怎样**。

## 三层分工（不要混）

| 层 | 载体 | 回答的问题 | 谁能改 |
| --- | --- | --- | --- |
| **内容规范**（本文件） | `docs/question-content-spec.md` | 什么算一道好题？为什么这样要求？ | 人工修订，需 ADR |
| **数据契约** | `src/schemas/*.ts` + `scripts/validate-questions.ts`、`scripts/add-question.ts` | 数据**必须**是什么形状 | 代码，机器可执行 |
| **Workflow** | `skills/*/SKILL.md` | 什么时候做什么、跑哪些命令 | skill 自身 |

- **冲突时以数据契约为准**：契约是唯一裁决者，跑 `npm run validate:questions` 就知道。
  本规范描述的是契约**管不到**的部分（语义、认知层级、诊断价值）。
- **生成 Prompt 不是规范**：`docs/prompt_part1.md` 负责 Knowledge / Blueprint，`docs/prompt_part2.md` 负责最终题目与选项生成；两者都必须引用本规范，但不定义规范。
- **skill 不复制规则**：skill 只写 workflow，涉及内容要求时写「见 spec §N」。

> schema / 导入脚本 / CI 能拦住的是：选项重复、答案越界、长度比、正确项与干扰项均长差、单选正确项长度领先及 `topic` 无节点。
> 契约**拦不住**的是：干扰项是稻草人、正确项因"更完整"胜出、多选题实际只考一个判断、
> 变体删掉了关键条件。**后者才是本规范存在的理由。**

## §1 Concept Scope —— 一个核心 Concept

每道题必须能一句话说清「这道题到底在测哪个核心 Concept」。

- 默认 **1 个 Core Concept + 0～2 个 Supporting / Prerequisite Concepts**。
- 仅 `comparison` / `tradeoff` / `design` / `system-design` 可要求多个独立 Concept。
- **去掉某 Concept 后题目仍然成立 ⇒ 该 Concept 不该进来。**

判据：答错之后能否定位到一个具体的知识缺口？大杂烩题诊断不出东西。

## §2 Answer Determinism —— 答案唯一可判定

正确答案必须由**题干约束 + 可靠技术事实**唯一确定。

- `single`：恰好一个正确，其余在给定条件下明确错误。
- `multiple`：每个正确项**独立成立**、每个干扰项**独立可排除**、答案集合唯一。正确项之间不得是同一事实的重复表述、上下位改写或因果链拆分；错误项之间也不得是同一误解的不同措辞。
- 不得依赖：未写出的前提、行业约定、模糊措辞、主观偏好、"也可能成立"。

> 多选题最常见的退化：几个正确项其实是同一个判断的不同说法
> （答对一题只需做一个判断）。`npm run question:quality` 的探测器 ④ 会标出这类嫌疑。

## §3 Self-contained —— 脱离来源可作答

考生默认**没有读过**任何来源文章、产品文档、Lens 或认证考纲。

- 禁止：`文中提到 / 根据本文 / 作者认为 / 前文所述 / 上述方法 / 该模型 / 这种方式`。
- 禁止「哪种做法符合某 Lens / 框架 / 考纲」这类问法——那考的是背诵，不是工程判断。
- 需要背景时：把作答所需的**最小 context 写进题干**，写成目标 + 约束 + 验收标准。

来源名称只放 `source` metadata，不进题干。

## §4 Evidence Boundary —— 不编造事实

正确答案依赖的核心技术事实必须可追溯。

- 禁止编造 benchmark、性能数字、产品行为、文章无依据的技术结论。
- 禁止用「文章外的重要事实」制造唯一答案。
- 允许补 context 使题目 self-contained（context enrichment），但不得新增一个决定正确答案的独立知识点（knowledge injection）；新增内容不得成为决定答案的关键未知事实。
- 涉及厂商 / API / 模型 / 认证的事实，必须在 `source` 里记核验日期；不确定就写条件句，不写绝对结论。

## §5 Option Design —— 同一决策层级、彼此独立

1. **同一决策层级**：所有选项处于相同抽象粒度、回答同一个问题、表达同一类判断。
2. **彼此独立**：每个选项独立可理解、表达一个主要判断，不引用「前者 / 后者 / 上述方案」。
3. **不靠"更完整"胜出**：难度应来自技术判断，不是信息量。

> 典型失败：正确项 A 是「是什么」、正确项 B 是「为什么」、正确项 C 是「反过来为什么不行」，
> 干扰项 D 是一整段反面论述。前三项不在同一认知层级，等于让考生从同一段解析里拆三句话。
> `npm run question:quality` 的探测器 ① 会标出这类嫌疑。

## §6 Wrong Options —— 干扰项必须"差点就对"

干扰项来自**真实技术误解或工程误判**，优先这几类：

- 混淆相邻概念；遗漏必要条件；把充分条件当必要条件；
- 忽略 trade-off / 系统瓶颈；把局部优化当系统优化；把理论最优当工程最优；
- 将训练结论错误迁移到推理、将 benchmark 结论错误迁移到生产；
- 忽略状态、一致性、成本、可靠性或安全。

**禁止稻草人选项**：完全相反、明显荒谬、"换模型 / 删测试 / 只看 token / 完全自动化"——
它们让题目退化成不用读题就能排除。

自检：遮住正确答案后，剩余选项能否让懂行的人**犹豫 2 秒以上**？

## §7 Option Balance & Answer Leakage —— 不能从形式猜出答案

不得通过以下形式泄露答案：**长度、专业术语数量、限定词、语气、绝对化程度、信息完整程度、选项结构**
（除非这些本身就是考察内容）。

### 写题时的硬要求

- 所有选项必须回答同一个问题、处于相同决策层级，信息密度和具体程度相近。
- 正确项不能因为多写条件、补充步骤、列出更多组件或解释更多背景而自然胜出。
- 禁止先写完整正确答案，再用短句拼凑干扰项；也禁止给干扰项补无关条件、重复解释或空洞套话来“凑长度”。
- 发生长度失衡时，**重写整组选项的表达粒度与句式**，不要只给较短选项加字。
- 遮住答案后逐项阅读：四个选项都应像是在回答同一个问题；差异必须来自技术判断，而不是篇幅和完整度。

### 新题和修改题的自动硬门禁

| 检查 | 硬阈值 | 目的 |
| --- | --- | --- |
| 最长 / 最短选项长度比 | ≤ 1.7 | 避免极端篇幅差 |
| 正确项均长与干扰项均长之差的绝对值 | ≤ 8 个字符 | 避免通过整体篇幅识别答案 |
| 单选正确项相对最长干扰项的长度领先 | ≤ 4 个字符 | 防止唯一正确项靠“最长”突出 |

长度统一按 `String(option).trim().length` 计算，中文、英文、数字、空格和标点均计入。
以上检查对**新题与修改过的题目**硬失败：`question:add --check` 在导入时执行，CI 的
`npm run lint:length -- --changed` 按题目对象内容差异检查新增和修改项。无法解析 base commit 时必须失败，
不得以“扫描 0 题”当作通过。

### 历史存量

历史题库按批次整改，不允许因为存量暂未全部收敛而放松新题门禁。历史基线测试可以暂时保留较宽的反向偏差兼容阈值，
但任何被修改的题目必须立即满足上面的严格门槛。

> **长度平衡 ≠ 选项质量平衡。** 自动门禁只能检测篇幅信号，无法判断选项是否同一认知层级、
> 是否存在更隐蔽的专业度或限定词提示。语义质量仍须按 §5 / §6 逐题审查。

## §8 Variant 知识一致性 —— 什么能改、什么不能改

**Variant = 同一 Knowledge 的不同 reasoning path 测量**（ADR-077；`docs/prompt_part1.md` §八 / `prompt_part2.md` §六同口径）。

**能改**（测量方式层）：`angle`、`cognitiveTask`、推理方向、观测证据、约束、工程情境、题型（single/multiple 可互换）。
**不能改**（考察内容层）：Knowledge 本身、正确答案逻辑、诊断目标。变体答对所需的知识不得超出 canonical 的 Knowledge；若回答变体需要额外掌握一个新 Concept，**它应该是新题，不是变体**。

- 变体换 `angle` / `cognitiveTask` 后仍归因同一 canonical evidence 键（见 `src/domain/questionIdentity.ts`）；而**改变 assessment contract 又不归因同一 Knowledge 的派生，必须建新 canonical ID + 填 `derivedFrom`**（assessment identity immutable）。
- 变体池条目自声明的测量面（`angle` / `cognitiveTask`，缺省 = 继承 canonical）见 `src/schemas/variant.ts`；`sourceHash` 覆盖元数据，canonical 变更即标 stale。
- prompt 产出的 inline `variants[]` 经 `npm run question:convert` 拆成变体池格式落盘（`src/data/variants/`），不嵌入 Question JSON。

> **变体不是补覆盖缺口的主要机制。** 变体归因同一 Knowledge，用它补洞等于把 A 格的题搬到 B 格——A 格重新空出来，**覆盖率永远补不满**。
> 变体的正确用途是**同 Knowledge 内扩充题量**（减少重复感），补缺口要靠 curate/rewrite 或新写 canonical。

变体落盘前必须过超采 + 五维质询（`scripts/question-variants.ts --oversample`、
`src/ai/variantChallenger.ts`）。结构校验（`validateVariant`）只是**漂移探测器**，
不是语义等价性证明。

## §9 题型分布 —— 以多选题为主

- 一批新题中 **multiple ≥ 2/3**（`scripts/add-question.ts` 硬门禁：本批 ≥3 道选择题且单选 > 1/3 直接报错）。
- `single` 只用于结论唯一、无法拆成多个独立判断的情形：定义判定、单值计算、唯一根因定位。
- 「下列哪项描述最准确」这类把多个独立判断压成最优选项的单选题，**应改写为多选**。

## 与自动化工具的关系

| 工具 | 覆盖本规范哪些条 | 性质 |
| --- | --- | --- |
| `npm run validate:questions` | 契约层（§2 的索引合法性、§9 的结构前提） | 硬门禁 |
| `npm run question:add --check` | §9 题型分布、§7 长度硬阈值、选项重复 | 硬门禁 |
| `npm run lint:bias` | §7 长度失衡 | 回归探针（不阻断） |
| `npm run question:quality` | §2 多判断退化、§5 层级混杂、§7 信息密度 | **软信号，非门禁** |
| LLM challenger / 人工 | §1、§3、§4、§6 | 不可自动化 |

`question:quality` 的四类嫌疑是**词汇/统计信号**，命中 = 值得复核，**不等于必须改写**。
不因为这些信号新增 lint 硬门禁。


## §10 SAP 场景题 —— 业务上下文和产品边界必须具体

SAP 题目不能只把一个通用顾问原则套上产品主题。题干应使候选人进入一个可以判断的业务或技术场景。

- 根据考察目标提供必要的企业背景、业务流程、项目/运行阶段、当前现象、影响范围和已知约束；不要求每题机械采用固定五段式。
- SAP 产品题应在答案依赖时明确产品与部署边界，例如 S/4HANA Cloud Public Edition、Private Edition、On-Premise、RISE with SAP 或客户自管环境。不能把某一部署模式的责任、功能或升级节奏泛化到其他模式。
- 题干只提供决定答案所需的条件；不为显得专业而堆砌行业、模块、事务码、产品缩写或无关数字。
- 业务场景应明确指标定义、角色、数据来源、服务依赖、系统边界或验收结果中的相关部分。单纯写“客户希望”“项目发现问题”“顾问应如何回应”不构成完整场景。
- 答案必须使用该主题真正需要的 SAP/技术知识。报表分析题应涉及指标口径、数据语义、分析能力或一致性；Basis 题应涉及系统层次与运行边界；HA/DR 题应涉及恢复目标和验证；TSM 题应涉及服务计划、客户沟通和跨团队协调。不要让所有主题最终都回答“先确认需求、看标准流程、记录风险、找负责人”。
- 产品行为、版本、许可、区域和托管服务责任必须有 SAP 官方资料依据；不确定的范围写清适用条件，并在 source 中标出核验日期和相关材料。
- 原创训练题可以参考 SAP 官方认证能力领域和实践场景，但不得声称是 SAP 官方原题、泄露题或复刻考试题。

## §11 岗位级别 —— 毕业生能做什么、不能做什么

岗位导向课程应区分“入职所需基础”与“成熟岗位的最终责任”。

- 依据真实岗位描述、招聘级别和官方学习路径确定课程范围；职位标注 Graduate 不等于岗位没有技术要求，仍需覆盖招聘明确列出的基础能力。
- 对毕业生，优先考察概念理解、风险识别、证据收集、变更/事件流程、材料准备、行动项跟踪、客户沟通和适时升级。
- 对生产级系统管理、复杂 Basis 操作、数据库参数调整、架构批准、灾难切换、客户交付承诺等职责，题目应考察候选人是否理解风险、授权和专家协作边界，不默认候选人有独立操作权。
- 同一道题不得把 Senior/Principal TSM 的独立架构和重大事故领导职责强加给 Graduate 候选人；可以用这些职责确定学习方向，但必须降低为可验证的入门能力。
- 不把“毕业生”理解成只考软技能。若真实招聘明确要求 Linux、SAP HANA、SAP Basis、S/4HANA 迁移、HA/DR、网络或云基础，必须给这些技术内容提供足够的知识节点和题目。

## §12 SAP 题目答案 —— 区分原则、产品事实和行动边界

SAP 题目的解释至少说明其中适用的一层依据；复杂题可以覆盖多层，但不堆砌通用话术。

1. **业务依据**：业务目标、流程、指标、角色、数据口径和验收。
2. **产品依据**：所讨论 SAP 产品/部署形态的功能和边界，引用官方学习或 Help 文档。
3. **技术依据**：系统层次、数据库、网络、集成、性能、可用性和恢复机制。
4. **服务依据**：合同/服务描述、SLA/SLO、责任矩阵、支持路径、升级机制和客户价值。
5. **岗位边界**：毕业生应执行、准备、核对、记录、跟踪或升级什么；哪些决定需由授权的专家或负责人作出。

答案解析应逐一解释主要干扰项为什么在题干条件下不成立。避免只说“风险更高”“不符合最佳实践”而不指出具体遗漏的前提或技术后果。
