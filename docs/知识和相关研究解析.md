# 从知识到题目：AI Interview Trainer 的知识分解、题库建模与金融领域实践

## 引言：真正应该构建的不是“题库”，而是“可测量的知识系统”

传统题库通常把最重要的数据结构定义成：

> 一道题 → 一个答案。

这种设计对于考试系统已经足够，但对于一个希望持续理解用户能力、发现知识缺口、进行自适应训练的 AI Interview Trainer 来说，这个抽象层次太低。

因为真正需要回答的问题不是：

> “用户答对了哪一道题？”

而是：

> “用户掌握了什么知识？”
> “哪些概念掌握不牢？”
> “他是不会这个概念，还是不会把概念应用到具体场景？”
> “他知道答案，但能不能解释原因？”
> “他是否可以在改变问题表面形式后仍然正确回答？”
> “哪些知识是前置条件，哪些知识只是相关知识？”
> “下一道题应该测什么，为什么？”

因此，一个成熟的知识训练系统实际上需要建立：

$$
\text{Knowledge}
\rightarrow
\text{Skill / Competency}
\rightarrow
\text{Concept}
\rightarrow
\text{Assessment Target}
\rightarrow
\text{Question}
\rightarrow
\text{Response Evidence}
$$

题目只是整个系统中最末端的一层。

这也是当前 AI Interview Trainer 最值得坚持的发展方向：**Question Bank 不应该成为系统的知识模型，Question 应该成为 Knowledge Model 上的 measurement item。**

---

# 一、首先区分四个经常被混为一谈的东西

## 1. Knowledge：你知道“什么”

Knowledge 是领域中的事实、概念、关系、机制、规则、方法等。

例如在机器学习领域：

* Transformer
* self-attention
* KV Cache
* RoPE
* MoE
* knowledge distillation

这些都属于知识对象。

但“Transformer”太大，“KV Cache”也仍然可能过大。

因此不能直接把一个大主题作为一个训练单元。

---

## 2. Concept：知识中可以被独立讨论和测量的单元

Concept 更接近：

> 一个能够被独立解释、比较、应用、诊断的最小有意义知识单元。

例如：

```text
Transformer
 ├── Self-Attention
 │    ├── Q/K/V
 │    ├── Attention Score
 │    ├── Scaling
 │    └── Softmax
 ├── Positional Encoding
 ├── FFN
 └── Residual Connection
```

进一步还可以继续细化：

```text
KV Cache
 ├── 为什么存在
 ├── 缓存什么
 ├── Prefill / Decode 差异
 ├── 显存开销
 ├── 长上下文影响
 └── Prefix Cache / Paged KV 等工程优化
```

这里真正适合成为知识图谱节点的，往往不是“Transformer”，而是下面这样的概念粒度。

---

## 3. Skill / Competency：你“能不能做”

Knowledge 和 Skill 并不相同。

例如一个人可能知道：

> “KV Cache 可以减少 autoregressive decoding 中重复的 K/V 计算。”

但是当给他一个真实问题：

> “一个 70B 模型部署在有限显存环境下，context length 从 4K 提升到 32K，为什么 KV Cache 会成为瓶颈？应该从什么方向优化？”

他可能答不上来。

这意味着：

* Knowledge 有
* Application Skill 不足

因此，一个训练系统应该至少区分：

```text
Knowledge
    ↓
Understanding
    ↓
Application
    ↓
Analysis
    ↓
Evaluation
    ↓
Design / Decision
```

这与 Revised Bloom's Taxonomy 的思想高度一致。Anderson 等人把学习目标拆成两个正交维度：

**Knowledge dimension**

* factual
* conceptual
* procedural
* metacognitive

以及：

**Cognitive process dimension**

* remember
* understand
* apply
* analyze
* evaluate
* create

这套二维模型非常适合用来解释“同一个知识为什么需要多道不同类型的题”。

而且研究已经发现，不能简单根据题目中的动词判断认知层级；“Explain / Analyze / Evaluate”等词本身并不足以决定真正测量的认知过程，因此 assessment design 需要同时考虑知识类型和认知过程。

---

# 二、所以一道题实际上应该拆成几个维度

对当前 repo 来说，可以把一条 Question 理解成：

$$
Q = f(K, A, C, D, T, F)
$$

其中：

* **K = Knowledge / Concept**
* **A = Angle**
* **C = Cognitive Task**
* **D = Difficulty**
* **T = Assessment Target**
* **F = Format**

也就是说：

> Question 不是 Knowledge 的一个自然“切片”，而是 Knowledge 在某个 measurement configuration 下生成的一个 item。

例如：

### 同一个 Concept

```text
Concept = KV Cache
```

可以产生：

### Recall

> KV Cache 的主要作用是什么？

### Explain

> 为什么 autoregressive decoding 可以通过 KV Cache 避免重复计算？

### Apply

> 给定序列长度和 head 数，估算 KV Cache 显存占用。

### Analyze

> 为什么长上下文场景中 KV Cache 会成为显存瓶颈？

### Compare

> KV Cache 与 Prefix Cache 分别解决什么问题？

### Tradeoff

> 在显存和吞吐之间受限时，应该如何选择 KV Cache 策略？

### Debug

> 推理服务吞吐下降且显存持续增长，可能与 KV Cache 的哪些设计有关？

这些题虽然都属于同一个 Concept，但它们**不是重复题**。

因为测量的是不同能力。

---

# 三、这也是为什么“Knowledge → Question 一对一映射”会导致题库迅速失真

最常见的题库模型是：

```text
Knowledge
   ↓
Question
```

于是一个概念最后只剩：

```text
KV Cache
→ “什么是 KV Cache？”
```

这实际上把一个多维能力空间压扁成一个点。

更合理的是：

```text
                    ┌── Recall
                    ├── Explain
Concept ─── Angle ──┼── Apply
                    ├── Analyze
                    ├── Compare
                    ├── Debug
                    └── Design
```

因此：

$$
\text{Question Space}
=
\text{Concept}
\times
\text{Angle}
\times
\text{Cognitive Task}
\times
\text{Context}
\times
\text{Difficulty}
$$

题库不是一个 list。

它实际上是一个**多维测量空间**。

---

# 四、题目之间为什么还需要“变体”

这直接解释了当前 repo 的 Offline Variant Pool 设计为什么是合理的。

如果只有：

```text
Concept → Question
```

用户记住的是具体题面，很容易形成：

> recognition ≠ knowledge

例如用户见过：

> “为什么 Transformer 使用 scaling factor 1/√d？”

即使他真正没有理解，只要记忆答案，也可能答对。

因此需要：

```text
Canonical Question
        │
        ├── Variant A
        ├── Variant B
        ├── Variant C
        └── Variant D
```

但真正高质量的 Variant 不应该只是：

> 把“为什么”改成“请解释为什么”。

更好的设计是：

```text
Canonical
→ 原理解释

Variant A
→ 工程场景

Variant B
→ 对比两个方案

Variant C
→ 故障诊断

Variant D
→ 新约束下的决策
```

这样 Variant 实际上是在改变：

$$
\text{Reasoning Path}
$$

而不是简单改变：

$$
\text{Surface Text}
$$

这正是当前 repo 从传统“表达变体”进一步向 Assessment Variant 演进的意义。当前 schema 已允许离线变体声明 `angle / cognitiveTask / assessment`，而 Runtime Variant 被限制为 presentation variant，仅用于表达改写。

---

# 五、学术研究实际上已经提供了一个非常成熟的答案：Q-matrix

如果需要找一个最直接对应“题目到底测什么知识”的理论框架，最值得关注的不是简单 Knowledge Graph，而是：

> **Q-matrix / Cognitive Diagnosis**

Q-matrix 的核心思想是建立：

$$
Question \rightarrow Knowledge\ Attributes
$$

例如：

```text
            Attention   Softmax   Scaling   KV Cache
Q1              1          1         1          0
Q2              0          0         0          1
Q3              1          0         1          0
Q4              1          1         1          1
```

一个题目可能涉及多个知识属性。

这意味着：

> 一道题不是“属于一个 topic”，而是可能测量多个 Knowledge Attributes。

Q-matrix 研究特别强调，item 与 attribute 的映射质量会直接影响认知诊断模型效果。

这对当前 repo 非常重要。

因为 `topic` 更像分类标签，而真正具有诊断价值的是：

```text
question
    ↓
concept(s)
    ↓
required knowledge attributes
    ↓
cognitive task
    ↓
assessment target
```

# 六、Q-matrix 再往前一步，就是 Cognitive Diagnosis

传统考试通常问：

$$
Score = 78
$$

但 Cognitive Diagnosis Model 更关注：

```text
Learner
 ├── Attention       ✓
 ├── KV Cache        ✓
 ├── RoPE            ✗
 ├── MoE Routing     ✗
 └── Quantization    ✓
```

也就是说：

> 不是“考了多少分”，而是“哪些认知属性掌握了”。

这和 AI Interview Trainer 的长期目标高度一致。

Knowledge Tracing 的综述明确讨论了 IRT、Q-matrix、多技能 item、知识状态估计等体系；其中 IRT 从“题目难度”角度建模，而 Q-matrix 则用于描述题目与技能/知识属性之间的关系。

进一步的研究已经开始把：

```text
Q-matrix
+
Knowledge / Skill Graph
+
IRT
+
Knowledge Tracing
```

组合起来，用于学习路径优化和多维认知诊断。2025 年的一项研究就是将 fuzzy Q-matrix、knowledge/skill graph 与 IRT 结合，用于多维认知诊断和学习路径生成。

2025 年的另一项研究则把知识/技能的层级关系与 IRT 和 knowledge tracing 结合，强调 item hierarchy 对知识追踪的重要性。

而 2026 年的研究已经进一步探索：

> adaptive knowledge graph + learner state + personalized learning path

也就是：

$$
Knowledge\ Graph
+
Learner\ State
\rightarrow
Next\ Learning\ Action
$$

---

# 七、因此，一个成熟的 Knowledge Model 至少应该有四层

对于 AI Interview Trainer，更建议采用：

```text
Domain
   │
   ▼
Knowledge / Concept
   │
   ├── prerequisite
   ├── related
   ├── part-of
   ├── contrasts-with
   └── applied-in
   │
   ▼
Capability / Cognitive Task
   │
   ├── remember
   ├── understand
   ├── apply
   ├── analyze
   ├── evaluate
   └── create
   │
   ▼
Assessment Target
   │
   ├── can explain
   ├── can compare
   ├── can diagnose
   ├── can choose
   ├── can calculate
   └── can design
   │
   ▼
Question
```

这里有一个特别重要的区别：

### Concept 是“学什么”

### Cognitive Task 是“怎么用”

### Assessment Target 是“我们究竟要验证什么能力”

### Question 是“用什么 observable item 去测”

这四层不应该合并。

# 八、业界实践其实也在朝这个方向发展

在职业教育和人才管理领域，一个明显趋势是：

> 从 Job → Question
> 转向
> Job → Skill → Competency → Assessment

例如 ESCO 将技能/能力和知识概念分别建模，并构造大规模层级体系；当前 ESCO skill pillar 包含超过 13,000 个概念，同时区分 knowledge、skills、attitudes/values 和 language skills/knowledge。

CFA Institute 在 2026 年关于金融行业 skills taxonomy 的实践文章中也明确强调：

> Skills taxonomy 是详细能力列表，而 skills architecture 更进一步把 skills 与 job roles、组织目标和业务结果联系起来。

也就是说，业界已经逐渐把：

```text
Taxonomy
```

和

```text
Architecture
```

区分开来。

这对 AI Interview Trainer 的启发是：

> `Knowledge Taxonomy` 不等于 `Interview Question Taxonomy`。

前者描述世界。

后者描述：

> “如何测量一个人对这个世界的掌握程度”。

---

# 九、自动题目生成研究也支持“先结构化知识，再生成题目”

Automatic Question Generation 的研究已经持续几十年。

2020 年系统综述分析了 93 篇教育题目自动生成研究，发现题目生成通常可以从：

* structured knowledge sources
* unstructured text
* domain knowledge
* templates

等来源产生。

同时，一个长期问题是：

> 自动生成流畅题目很容易，但控制 difficulty、cognitive level、feedback 和教育价值很难。

2024 年关于 Neural Question Generation 的综述也明确指出，好的教育题目不仅需要 fluent / relevant，还必须具有 educational value。

这说明一个非常关键的工程结论：

> 不应该让 LLM 直接从文章生成最终题目。

更合理的是：

```text
Document
 ↓
Knowledge Extraction
 ↓
Concept Graph
 ↓
Assessment Blueprint
 ↓
Question Generation
 ↓
Validation
 ↓
Measurement Calibration
```

这和当前 repo 的发展方向是一致的。

# 十、对于当前 repo，最合理的知识分解应该是什么

可以把目前的系统抽象成：

```text
                    DOMAIN
                       │
                       ▼
                 KNOWLEDGE
                       │
                       ▼
                  CONCEPT
                       │
              ┌────────┴────────┐
              ▼                 ▼
        Prerequisite        Related
              │
              ▼
        Concept Graph
              │
              ▼
       Assessment Blueprint
              │
      ┌───────┼────────┐
      ▼       ▼        ▼
     Angle  Cognitive  Assessment
             Task
      │       │         │
      └───────┼─────────┘
              ▼
           Question
              │
        ┌─────┴─────┐
        ▼           ▼
    Canonical     Variant
        │
        ▼
    Evidence
        │
        ▼
 Learner Knowledge State
```

其中：

### Concept Graph

描述：

> 世界是什么样的。

### Assessment Blueprint

描述：

> 我们想测什么。

### Question

描述：

> 如何把 measurement target 转成一个 observable task。

### Variant

描述：

> 改变 reasoning path / presentation，而不破坏 measurement contract。

### Learner State

描述：

> 这个人目前对这些知识属性掌握到什么程度。

这样整个系统就从：

```text
Question Bank
```

升级成：

```text
Knowledge Assessment System
```

# 十一、金融领域尤其不能直接照搬普通题库

金融是一个非常适合使用上述架构的领域，但它有一个特殊问题：

> 金融知识高度结构化，同时又高度依赖 context、时间、制度和业务角色。

例如：

```text
Bond
```

本身只是一个概念。

真正的金融知识还包含：

```text
Bond
 ├── Cash Flow
 ├── Coupon
 ├── Yield
 ├── Duration
 ├── Convexity
 ├── Credit Risk
 ├── Interest Rate Risk
 ├── Liquidity
 ├── Issuer
 ├── Market
 └── Regulation
```

而同一个概念对不同角色的意义又不同：

```text
Retail Investor
Portfolio Manager
Risk Manager
Trader
Credit Analyst
Investment Banker
Compliance Officer
Quant
Treasury
```

因此金融知识模型最好同时考虑：

$$
Concept
\times
Role
\times
Context
\times
Decision
\times
Risk
$$

---

# 十二、金融领域应该先建立“金融世界模型”，再建立题库

这里有一个非常成熟的行业参考：

> **FIBO — Financial Industry Business Ontology**

FIBO 是 EDM Council 推动、并由 OMG 标准化的金融行业 ontology，用于定义金融业务领域中的对象及其关系。它覆盖金融业务实体、金融工具、证券、贷款、指标、衍生品等大量领域。

例如 FIBO 将金融领域拆解成：

```text
Financial Business & Commerce
Foundations
Indices & Indicators
Securities
Loans
Derivatives
...
```

其价值并不在于“直接拿来当题库”，而在于：

> 提供金融世界中实体、关系和概念层次的参考 ontology。

因此，一个金融版 AI Interview Trainer 不应该从：

```text
问题：
什么是 Bond？
```

开始。

应该从：

```text
金融世界
 ↓
Asset
 ↓
Security
 ↓
Debt Security
 ↓
Bond
 ↓
Coupon / Yield / Duration / Credit
```

开始。

# 十四、金融知识还必须加入“时间维度”

这是金融和很多传统知识库最大的区别之一。

例如：

```text
Interest Rate
```

不是静态概念。

它受到：

```text
Date
Market
Currency
Central Bank Policy
Yield Curve
Macro Environment
```

影响。

因此金融 Knowledge Node 最好支持：

```text
Concept
+
Valid Time
+
Market Context
+
Jurisdiction
```

例如：

```text
SOFR
→ USD
→ US
→ reference rate
→ specific publication regime
→ specific historical period
```

否则知识库很容易出现：

> 概念没有错，但是答案在当前时间/市场环境已经不成立。

# 十五、金融题目不应该只有“知识题”，而应该大量使用 Decision Items

例如：

### Concept

> Duration 是什么？

这是基础知识题。

---

### Apply

> 一个债券 duration 为 5，利率上升 50bp，价格大致如何变化？

这是应用题。

---

### Analyze

> 为什么两个 duration 相同的债券，在利率冲击下可能产生不同价格变化？

这是分析题。

---

### Compare

> Macaulay Duration 与 Modified Duration 在风险管理中的区别是什么？

这是比较题。

---

### Scenario

> 当前收益率曲线快速陡峭化，投资组合主要持有长久期国债，应该关注什么风险？

这是场景题。

---

### Decision

> 如果目标是降低利率风险，同时尽量保持 carry，应该如何调整组合？

这是决策题。

---

### Debug

> 风险模型报告的利率敏感度与实际 P&L 长期偏差较大，优先检查哪些环节？

这是诊断题。

---

真正高级的金融题库，应该大量覆盖：

```text
Explain
Calculate
Compare
Interpret
Diagnose
Decide
Design
```

而不是：

```text
Define
Recall
Repeat
```

---

# 十六、金融领域特别适合使用“Concept × Scenario × Decision”

金融知识高度依赖场景。

因此一个优秀的金融 Question Generator 可以采用：

$$
Q =
Concept
\times
Scenario
\times
Decision
\times
Role
\times
Difficulty
$$

例如：

```text
Concept = Duration
Scenario = rising rate
Role = Portfolio Manager
Decision = hedge or rebalance
Difficulty = senior
```

于是得到：

> “作为一个固收投资组合经理，如果未来 6 个月利率存在持续上行风险，而组合 duration 明显高于 benchmark，你会如何调整？哪些因素会导致 duration hedging 不完全有效？”

这已经比：

> “什么是 duration？”

高了几个层次。

# 十七、金融领域还应该显式建模“错误模式”

对于金融训练而言，Misconception 非常重要。

例如：

```text
Concept = Bond Price / Yield
```

常见错误：

```text
错误 1：
利率上升 → 所有债券价格必然等比例下降

错误 2：
duration 越高 → 债券收益率越高

错误 3：
duration 完全决定价格变化

错误 4：
credit spread 与 risk-free rate 是同一个东西
```

于是题目不再只是：

```text
正确答案是什么？
```

而是：

```text
这个 distractor 对应哪一种错误模型？
```

这实际上更接近 Cognitive Diagnostic Assessment。

因此金融题库应该维护：

```text
Concept
 ├── Canonical understanding
 ├── Common misconceptions
 ├── Diagnostic signals
 └── Assessment items
```

这会比单纯的 answer/explanation 更有长期价值。

# 二十、最终目标：从 Question Bank 走向 Knowledge Assessment Graph

最值得坚持的长期架构可以浓缩成一句话：

> **Question 不再是系统的中心对象，Knowledge + Assessment + Evidence 才是。**

最终系统应该能够回答：

```text
用户不会什么？
    ↓
具体 Concept 是什么？
    ↓
是 Concept 本身不会，
还是 Apply / Analyze 不会？
    ↓
有哪些 prerequisite gap？
    ↓
哪些 misconception 可能存在？
    ↓
应该通过什么 assessment item 验证？
    ↓
需要什么 reasoning path 的 Variant？
    ↓
回答后获得什么 Evidence？
    ↓
如何更新 Learner Knowledge State？
    ↓
下一步训练哪个 Concept / Capability？
```

这比传统：

```text
Question 1 → Wrong
Question 2 → Correct
Question 3 → Wrong
```

高了一个抽象层级。

而这个层级才是真正适合 AI Interview Trainer 的。

# 二十一、推荐阅读与参考体系

### 认知与知识分解

Anderson & Krathwohl 的 Revised Bloom's Taxonomy 是最适合作为“Knowledge × Cognitive Process”基础框架的经典体系；后续研究也指出，知识类型与认知过程并非简单独立，不能只依赖题目动词判断认知层次。

### Cognitive Diagnosis / Q-matrix

Q-matrix 是理解“Question → Knowledge Attribute”最直接的理论框架。其核心问题正是：

> 一个题目到底测了哪些知识属性？

而 Q-matrix 的构造质量会直接影响 cognitive diagnosis。

### Knowledge Tracing / IRT

Knowledge Tracing 研究解决：

> 学习者的知识状态如何随着答题而变化？

IRT 则解决：

> 题目难度、区分度等测量参数如何与作答结果关联？

两者最终可以与 Q-matrix 和 Knowledge Graph 组合。

### Automatic Question Generation

Kurdi 等人的系统综述系统总结了教育领域的 Automatic Question Generation，并特别指出 controlled difficulty、question structure、feedback 和 evaluation 仍然是核心挑战。

### 金融知识体系

FIBO 是金融领域最值得参考的 ontology 之一，可以作为：

```text
Financial Entity
+
Instrument
+
Relationship
+
Business Context
```

的底层参考，而不应直接当题库。

### 金融能力体系

欧盟与 OECD-INFE 的 Financial Competence Framework 提供了一个面向金融能力的标准化框架，用于描述成年人作出合理金融决策所需的 financial competences。

CFA Institute 在 2026 年进一步强调金融行业 skills taxonomy 与 skills architecture 的价值：前者描述能力层次，后者把能力与 role、业务目标和组织需求连接起来。

# 结论

如果把整个问题压缩成一个公式，我认为最值得作为 AI Interview Trainer 长期设计原则的是：

$$
\boxed{
Question
\neq
Knowledge
}
$$

而应该是：

$$
\boxed{
Question
=
Measurement(Knowledge,\ Capability,\ Context,\ Reasoning)
}
$$

因此：

```text
知识库
不是
题库

题库
不是
知识库

题目
是
知识状态的观测工具
```

对于通用 AI 面试，可以采用：

```text
Concept
×
Angle
×
Cognitive Task
×
Assessment Target
×
Difficulty
```

对于金融领域，则进一步扩展成：

```text
Financial Concept
×
Role
×
Scenario
×
Risk
×
Decision
×
Cognitive Task
×
Difficulty
```

这样生成出来的题目才不会继续陷入“把一个知识点蒸馏成三五道差不多的问题”的困境，而是形成一个真正覆盖**知识、能力、推理路径和诊断证据**的多维 assessment space。

这也是当前 repo 最值得继续演化的方向：最终不是建设一个“拥有很多题目的题库”，而是建设一个能够回答**“一个人究竟掌握了什么、还缺什么、缺在哪一种能力上、下一步应该测什么”**的 Knowledge Assessment System。
