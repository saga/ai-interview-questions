# 从知识到题目：AI Interview Trainer 的知识分解、题库建模与金融领域实践

## 引言：真正应该构建的不是"题库"，而是"可测量的知识系统"

传统题库通常把最重要的数据结构定义成"一道题 → 一个答案"。这对考试系统已经足够，但对于一个希望持续理解用户能力、发现知识缺口、进行自适应训练的 AI Interview Trainer 来说，这个抽象层次太低了。

真正需要回答的问题不是"用户答对了哪一道题"，而是"用户掌握了什么知识、哪些概念掌握不牢"。进一步还要区分：他是不会这个概念，还是不会把概念应用到具体场景；他知道答案，但能不能解释原因；改变问题表面形式之后是否仍能答对。再往前，则需要判断哪些知识是前置条件、哪些只是相关知识，以及下一道题应该测什么、为什么。

因此，一个成熟的知识训练系统实际上要建立的是这样一条链路：`Knowledge → Skill/Competency → Concept → Assessment Target → Question → Response Evidence`。题目只是这条链最末端的一层。

这也是当前 AI Interview Trainer 最值得坚持的发展方向：**Question Bank 不应该成为系统的知识模型，Question 应该成为 Knowledge Model 上的 measurement item。**

## 一、首先区分四个经常被混为一谈的东西

### 1. Knowledge：你知道"什么"

Knowledge 是领域中的事实、概念、关系、机制、规则、方法等。在机器学习领域，Transformer、self-attention、KV Cache、RoPE、MoE、knowledge distillation 这些都属于知识对象。

但"Transformer"太大，"KV Cache"也仍然可能过大，因此不能直接把一个大主题当作一个训练单元。

### 2. Concept：知识中可以被独立讨论和测量的单元

Concept 更接近一个能够被独立解释、比较、应用、诊断的最小有意义知识单元。

以 Transformer 为例，它下面还挂着 Self-Attention（含 Q/K/V、Attention Score、Scaling、Softmax）、Positional Encoding、FFN 与 Residual Connection 等子结构。KV Cache 同样可以继续拆成"为什么存在""缓存什么""Prefill / Decode 差异""显存开销""长上下文影响"，以及 Prefix Cache / Paged KV 这类工程优化。

这里真正适合成为知识图谱节点的，往往不是"Transformer"，而是上面这种概念粒度。

### 3. Skill / Competency：你"能不能做"

Knowledge 和 Skill 并不相同。一个人可能知道"KV Cache 可以减少 autoregressive decoding 中重复的 K/V 计算"，但当给他一个真实问题——"一个 70B 模型部署在有限显存环境下，context length 从 4K 提升到 32K，为什么 KV Cache 会成为瓶颈？应该从什么方向优化？"——他可能答不上来。这意味着 Knowledge 有，而 Application Skill 不足。

因此，一个训练系统至少应区分 `Knowledge → Understanding → Application → Analysis → Evaluation → Design/Decision` 这条递进链。

这与 Revised Bloom's Taxonomy 的思想高度一致。Anderson 等人把学习目标拆成两个正交维度：知识维度包含 factual、conceptual、procedural、metacognitive 四类，认知过程维度则是 remember、understand、apply、analyze、evaluate、create。

这套二维模型非常适合用来解释"同一个知识为什么需要多道不同类型的题"。而且研究已经发现，不能简单根据题目中的动词判断认知层级；"Explain / Analyze / Evaluate"等词本身并不足以决定真正测量的认知过程，因此 assessment design 需要同时考虑知识类型和认知过程。

## 二、所以一道题实际上应该拆成几个维度

对当前 repo 来说，可以把一条 Question 理解成：

$$
Q = f(K, A, C, D, T, F)
$$

其中 K 是 Knowledge / Concept，A 是 Angle，C 是 Cognitive Task，D 是 Difficulty，T 是 Assessment Target，F 是 Format。

也就是说：Question 不是 Knowledge 的一个自然"切片"，而是 Knowledge 在某个 measurement configuration 下生成的一个 item。

同一个 Concept（`Concept = KV Cache`）可以产生下面这些题：

| 认知层级 | 示例问题 |
|---|---|
| Recall | KV Cache 的主要作用是什么？ |
| Explain | 为什么 autoregressive decoding 可以通过 KV Cache 避免重复计算？ |
| Apply | 给定序列长度和 head 数，估算 KV Cache 显存占用。 |
| Analyze | 为什么长上下文场景中 KV Cache 会成为显存瓶颈？ |
| Compare | KV Cache 与 Prefix Cache 分别解决什么问题？ |
| Tradeoff | 在显存和吞吐之间受限时，应该如何选择 KV Cache 策略？ |
| Debug | 推理服务吞吐下降且显存持续增长，可能与 KV Cache 的哪些设计有关？ |

这些题虽然都属于同一个 Concept，但它们**不是重复题**，因为测量的是不同能力。

## 三、这也是为什么"Knowledge → Question 一对一映射"会导致题库迅速失真

最常见的题库模型是让一个 Knowledge 直接对应一道 Question，于是一个概念最后只剩"什么是 KV Cache？"这样的题。这实际上把一个多维能力空间压扁成了一个点。

更合理的是让同一个 Concept 经由 Angle 展开成 Recall、Explain、Apply、Analyze、Compare、Debug、Design 等多种测量方式。因此：

$$
\text{Question Space}
= \text{Concept}
\times \text{Angle}
\times \text{Cognitive Task}
\times \text{Context}
\times \text{Difficulty}
$$

题库不是一个 list，它实际上是一个**多维测量空间**。

## 四、题目之间为什么还需要"变体"

这直接解释了当前 repo 的 Offline Variant Pool 设计为什么是合理的。

如果只有 `Concept → Question`，用户记住的是具体题面，很容易形成 recognition ≠ knowledge。例如用户见过"为什么 Transformer 使用 scaling factor 1/√d？"，即使他并没有真正理解，只要记住答案也可能答对。因此需要在 Canonical Question 之下生成 Variant A / B / C / D。

但真正高质量的 Variant 不应该只是把"为什么"改成"请解释为什么"。更好的设计是让每个变体落在不同的形态上：

| 变体 | 形态 |
|---|---|
| Canonical | 原理解释 |
| Variant A | 工程场景 |
| Variant B | 对比两个方案 |
| Variant C | 故障诊断 |
| Variant D | 新约束下的决策 |

这样 Variant 实际上是在改变 **Reasoning Path**，而不是简单改变 **Surface Text**。

这正是当前 repo 从传统"表达变体"进一步向 Assessment Variant 演进的意义。当前 schema 已允许离线变体声明 `angle / cognitiveTask / assessment`，而 Runtime Variant 被限制为 presentation variant，仅用于表达改写。

## 五、学术研究实际上已经提供了一个非常成熟的答案：Q-matrix

如果需要找一个最直接对应"题目到底测什么知识"的理论框架，最值得关注的不是简单 Knowledge Graph，而是 **Q-matrix / Cognitive Diagnosis**。

Q-matrix 的核心思想是建立 $Question \rightarrow Knowledge\ Attributes$ 的映射：

| 题目 | Attention | Softmax | Scaling | KV Cache |
|---|---|---|---|---|
| Q1 | 1 | 1 | 1 | 0 |
| Q2 | 0 | 0 | 0 | 1 |
| Q3 | 1 | 0 | 1 | 0 |
| Q4 | 1 | 1 | 1 | 1 |

一个题目可能涉及多个知识属性。这意味着：一道题不是"属于一个 topic"，而是可能测量多个 Knowledge Attributes。

Q-matrix 研究特别强调，item 与 attribute 的映射质量会直接影响认知诊断模型效果。这对当前 repo 非常重要——因为 `topic` 更像分类标签，而真正具有诊断价值的是 `question → concept(s) → required knowledge attributes → cognitive task → assessment target` 这条链路。

## 六、Q-matrix 再往前一步，就是 Cognitive Diagnosis

传统考试通常问 $Score = 78$，但 Cognitive Diagnosis Model 更关心的是下面这种刻画：

| 知识属性 | 掌握状态 |
|---|---|
| Attention | ✓ |
| KV Cache | ✓ |
| RoPE | ✗ |
| MoE Routing | ✗ |
| Quantization | ✓ |

也就是说：不是"考了多少分"，而是"哪些认知属性掌握了"。这和 AI Interview Trainer 的长期目标高度一致。

Knowledge Tracing 的综述明确讨论了 IRT、Q-matrix、多技能 item、知识状态估计等体系；其中 IRT 从"题目难度"角度建模，而 Q-matrix 则用于描述题目与技能/知识属性之间的关系。

进一步的研究已经开始把 Q-matrix、Knowledge / Skill Graph、IRT 与 Knowledge Tracing 组合起来，用于学习路径优化和多维认知诊断。2025 年的一项研究就是将 fuzzy Q-matrix、knowledge/skill graph 与 IRT 结合，用于多维认知诊断和学习路径生成；另一项同年研究则把知识/技能的层级关系与 IRT 和 knowledge tracing 结合，强调 item hierarchy 对知识追踪的重要性。

而 2026 年的研究已经进一步探索 adaptive knowledge graph + learner state + personalized learning path，也就是：

$$
Knowledge\ Graph + Learner\ State \rightarrow Next\ Learning\ Action
$$

## 七、因此，一个成熟的 Knowledge Model 至少应该有四层

对于 AI Interview Trainer，更建议采用一条从 Domain 出发、逐层收敛到 Question 的链路。

最上层是 **Domain**，其下是 **Knowledge / Concept**，概念之间通过 prerequisite、related、part-of、contrasts-with、applied-in 等关系相连。再往下是 **Capability / Cognitive Task**，对应 remember、understand、apply、analyze、evaluate、create。然后是 **Assessment Target**，即 can explain、can compare、can diagnose、can choose、can calculate、can design 这类可验证的能力声明。最底层才是 **Question**。

这里有一个特别重要的区别：

| 层 | 回答的问题 |
|---|---|
| Concept | 学什么 |
| Cognitive Task | 怎么用 |
| Assessment Target | 我们究竟要验证什么能力 |
| Question | 用什么 observable item 去测 |

这四层不应该合并。

## 八、业界实践其实也在朝这个方向发展

在职业教育和人才管理领域，一个明显趋势是从 `Job → Question` 转向 `Job → Skill → Competency → Assessment`。

例如 ESCO 将技能/能力和知识概念分别建模，并构造大规模层级体系；当前 ESCO skill pillar 包含超过 13,000 个概念，同时区分 knowledge、skills、attitudes/values 和 language skills/knowledge。

CFA Institute 在 2026 年关于金融行业 skills taxonomy 的实践文章中也明确强调：Skills taxonomy 是详细能力列表，而 skills architecture 更进一步把 skills 与 job roles、组织目标和业务结果联系起来。

也就是说，业界已经逐渐把 **Taxonomy** 和 **Architecture** 区分开来。

这对 AI Interview Trainer 的启发是：`Knowledge Taxonomy` 不等于 `Interview Question Taxonomy`。前者描述世界，后者描述"如何测量一个人对这个世界的掌握程度"。

## 九、自动题目生成研究也支持"先结构化知识，再生成题目"

Automatic Question Generation 的研究已经持续几十年。

2020 年系统综述分析了 93 篇教育题目自动生成研究，发现题目生成通常可以从 structured knowledge sources、unstructured text、domain knowledge 以及 templates 等来源产生。同时，一个长期问题是：自动生成流畅题目很容易，但控制 difficulty、cognitive level、feedback 和教育价值很难。

2024 年关于 Neural Question Generation 的综述也明确指出，好的教育题目不仅需要 fluent / relevant，还必须具有 educational value。

这说明一个非常关键的工程结论：不应该让 LLM 直接从文章生成最终题目。更合理的路径是 `Document → Knowledge Extraction → Concept Graph → Assessment Blueprint → Question Generation → Validation → Measurement Calibration`。这和当前 repo 的发展方向是一致的。

## 十、对于当前 repo，最合理的知识分解应该是什么

可以把目前的系统抽象成一条主链路：从 DOMAIN 到 KNOWLEDGE 再到 CONCEPT，概念分出 Prerequisite 与 Related 两支并汇入 Concept Graph，由 Concept Graph 产出 Assessment Blueprint，Blueprint 再同时分出 Angle、Cognitive Task、Assessment 三个维度并交于 Question；Question 分为 Canonical 与 Variant，二者产生的 Evidence 最终汇入 Learner Knowledge State。

其中几个关键环节的分工是：

**Concept Graph** 描述"世界是什么样的"；**Assessment Blueprint** 描述"我们想测什么"；**Question** 描述"如何把 measurement target 转成一个 observable task"；**Variant** 描述"改变 reasoning path / presentation，而不破坏 measurement contract"；**Learner State** 描述"这个人目前对这些知识属性掌握到什么程度"。

这样整个系统就从 **Question Bank** 升级成 **Knowledge Assessment System**。

## 十一、金融领域尤其不能直接照搬普通题库

金融是一个非常适合使用上述架构的领域，但它有一个特殊问题：金融知识高度结构化，同时又高度依赖 context、时间、制度和业务角色。

`Bond` 本身只是一个概念，而真正的金融知识还包含 Cash Flow、Coupon、Yield、Duration、Convexity、Credit Risk、Interest Rate Risk、Liquidity、Issuer、Market、Regulation 等一整套子结构。

同一个概念对不同角色的意义又不同——Retail Investor、Portfolio Manager、Risk Manager、Trader、Credit Analyst、Investment Banker、Compliance Officer、Quant、Treasury 关注的东西并不一样。

因此金融知识模型最好同时考虑：

$$
Concept \times Role \times Context \times Decision \times Risk
$$

## 十二、金融领域应该先建立"金融世界模型"，再建立题库

这里有一个非常成熟的行业参考：**FIBO — Financial Industry Business Ontology**。

FIBO 是 EDM Council 推动、并由 OMG 标准化的金融行业 ontology，用于定义金融业务领域中的对象及其关系。它覆盖金融业务实体、金融工具、证券、贷款、指标、衍生品等大量领域，并将金融领域拆解成 Financial Business & Commerce、Foundations、Indices & Indicators、Securities、Loans、Derivatives 等分支。

其价值并不在于"直接拿来当题库"，而在于提供金融世界中实体、关系和概念层次的参考 ontology。

因此，一个金融版 AI Interview Trainer 不应该从"什么是 Bond？"开始，而应该从 `金融世界 → Asset → Security → Debt Security → Bond → Coupon / Yield / Duration / Credit` 这条链开始。

## 十三、金融领域可以进一步建立五层知识体系

**Layer 1：Financial Entities**，包括 Bank、Fund、Issuer、Investor、Broker、Exchange、Central Bank、Regulator、Clearing House 等参与主体。

**Layer 2：Financial Instruments**，覆盖 Equity、Bond、Loan、Option、Future、Forward、Swap、ETF、Fund、Mortgage 等工具类型。

**Layer 3：Financial Concepts**，即 Yield、Duration、Convexity、Volatility、Liquidity、Credit Spread、Default Probability、Capital Adequacy、Leverage、VaR、Expected Shortfall 等核心概念。

**Layer 4：Financial Processes**，包括 Trade Execution、Clearing、Settlement、Collateral Management、Credit Assessment、Portfolio Construction、Risk Management、Asset Allocation、Pricing、Hedging、Regulatory Reporting 这些流程环节。

**Layer 5：Decision / Competency**。真正应该拿来训练人的，是这一层：

| 领域 | 要训练的能力 |
|---|---|
| Pricing | 能否判断价格变化 |
| Risk | 能否识别风险来源 |
| Portfolio | 能否进行资产配置 |
| Credit | 能否识别信用风险 |
| Trading | 能否选择交易策略 |
| Compliance | 能否识别违规行为 |
| Treasury | 能否管理流动性与利率风险 |

## 十四、金融知识还必须加入"时间维度"

这是金融和很多传统知识库最大的区别之一。

`Interest Rate` 不是静态概念，它同时受到 Date、Market、Currency、Central Bank Policy、Yield Curve、Macro Environment 的影响。因此金融 Knowledge Node 最好同时携带 Concept、Valid Time、Market Context 与 Jurisdiction 四个要素。

以 SOFR 为例，它的完整含义需要绑定 USD 币种、US 司法辖区、reference rate 角色、特定的 publication regime，以及特定的历史时期。

否则知识库很容易出现：概念没有错，但是答案在当前时间/市场环境已经不成立。

## 十五、金融题目不应该只有"知识题"，而应该大量使用 Decision Items

同一个 Duration 概念，可以衍生出不同层级的题：

| 层级 | 示例问题 | 定位 |
|---|---|---|
| Concept | Duration 是什么？ | 基础知识题 |
| Apply | 一个债券 duration 为 5，利率上升 50bp，价格大致如何变化？ | 应用题 |
| Analyze | 为什么两个 duration 相同的债券，在利率冲击下可能产生不同价格变化？ | 分析题 |
| Compare | Macaulay Duration 与 Modified Duration 在风险管理中的区别是什么？ | 比较题 |
| Scenario | 当前收益率曲线快速陡峭化，投资组合主要持有长久期国债，应该关注什么风险？ | 场景题 |
| Decision | 如果目标是降低利率风险，同时尽量保持 carry，应该如何调整组合？ | 决策题 |
| Debug | 风险模型报告的利率敏感度与实际 P&L 长期偏差较大，优先检查哪些环节？ | 诊断题 |

真正高级的金融题库，应该大量覆盖 Explain、Calculate、Compare、Interpret、Diagnose、Decide、Design，而不是 Define、Recall、Repeat。

## 十六、金融领域特别适合使用"Concept × Scenario × Decision"

金融知识高度依赖场景。因此一个优秀的金融 Question Generator 可以采用：

$$
Q = Concept \times Scenario \times Decision \times Role \times Difficulty
$$

例如把维度取成 Concept 为 Duration、Scenario 为 rising rate、Role 为 Portfolio Manager、Decision 为 hedge or rebalance、Difficulty 为 senior，于是得到：

> "作为一个固收投资组合经理，如果未来 6 个月利率存在持续上行风险，而组合 duration 明显高于 benchmark，你会如何调整？哪些因素会导致 duration hedging 不完全有效？"

这已经比"什么是 duration？"高了几个层次。

## 十七、金融领域还应该显式建模"错误模式"

对于金融训练而言，Misconception 非常重要。以 `Concept = Bond Price / Yield` 为例，常见的错误认知包括：

| 错误 | 描述 |
|---|---|
| 错误 1 | 利率上升 → 所有债券价格必然等比例下降 |
| 错误 2 | duration 越高 → 债券收益率越高 |
| 错误 3 | duration 完全决定价格变化 |
| 错误 4 | credit spread 与 risk-free rate 是同一个东西 |

于是题目不再只是问"正确答案是什么？"，而是要问"这个 distractor 对应哪一种错误模型？"

这实际上更接近 Cognitive Diagnostic Assessment。因此金融题库应该围绕 Concept 同时维护 Canonical understanding、Common misconceptions、Diagnostic signals 与 Assessment items，这会比单纯的 answer/explanation 更有长期价值。

## 十八、最终可以形成一个统一的数据模型

一个非常理想的金融/通用知识模型可以抽象成这样一条链路：从 Knowledge Domain 到 Concept，概念之间通过 prerequisite、related、partOf、contrast、causes、appliedTo 相连；再经 Competency 进入 Assessment Blueprint，Blueprint 上挂着 target、reasoningGoal、cognitiveTask、angle、misconception、difficulty、scenario 这些要素；由它产出 Canonical Question，分为 Choice 与 Open 两类；再向下展开 Variant Pool，包含 reasoning-path、context、comparison、debugging、decision 五类变体；最终所有作答汇成 Evidence，更新 Learner State。

这时候题库本质上已经不是一个 JSON 文件集合，它变成了：

$$
\boxed{
Knowledge\ Model
+ Assessment\ Model
+ Evidence\ Model
}
$$

## 十九、这也解释了当前 repo 下一阶段最值得做什么

当前 repo 已经解决了不少"题库工程问题"：Question schema、Concept Graph、coverage、Angle、CognitiveTask、Assessment、Variant Pool、source hash、stale detection、duplicate detection、offline oversampling、challenger 与 runtime fallback。

Offline pipeline 当前已经是 `Canonical → Oversample → Deterministic Validation → Deduplication → Quality Challenger → Top-N → Variant Pool`。这一点在架构上已经明显优于"LLM 生成两道题然后直接保存"的传统方案。

下一阶段真正应该提升的，不再是"还能不能生成更多题？"，而应该是"这些题到底覆盖了多少真正不同的 Knowledge / Cognitive Task / Reasoning Path？"

换句话说，评价系统应该逐渐从 $Question\ Coverage$ 转向：

$$
Knowledge\ Coverage
+ Competency\ Coverage
+ Diagnostic\ Coverage
$$

## 二十、最终目标：从 Question Bank 走向 Knowledge Assessment Graph

最值得坚持的长期架构可以浓缩成一句话：

> **Question 不再是系统的中心对象，Knowledge + Assessment + Evidence 才是。**

最终系统应该能够回答一整串追问：用户不会什么 → 具体 Concept 是什么 → 是 Concept 本身不会，还是 Apply / Analyze 不会 → 有哪些 prerequisite gap → 哪些 misconception 可能存在 → 应该通过什么 assessment item 验证 → 需要什么 reasoning path 的 Variant → 回答后获得什么 Evidence → 如何更新 Learner Knowledge State → 下一步训练哪个 Concept / Capability。

这比传统的"Question 1 → Wrong、Question 2 → Correct、Question 3 → Wrong"高了一个抽象层级。而这个层级才是真正适合 AI Interview Trainer 的。

## 二十一、推荐阅读与参考体系

**认知与知识分解。** Anderson & Krathwohl 的 Revised Bloom's Taxonomy 是最适合作为"Knowledge × Cognitive Process"基础框架的经典体系；后续研究也指出，知识类型与认知过程并非简单独立，不能只依赖题目动词判断认知层次。

**Cognitive Diagnosis / Q-matrix。** Q-matrix 是理解"Question → Knowledge Attribute"最直接的理论框架，其核心问题正是一个题目到底测了哪些知识属性，而 Q-matrix 的构造质量会直接影响 cognitive diagnosis。

**Knowledge Tracing / IRT。** Knowledge Tracing 研究解决"学习者的知识状态如何随着答题而变化"，IRT 则解决"题目难度、区分度等测量参数如何与作答结果关联"。两者最终可以与 Q-matrix 和 Knowledge Graph 组合。

**Automatic Question Generation。** Kurdi 等人的系统综述系统总结了教育领域的 Automatic Question Generation，并特别指出 controlled difficulty、question structure、feedback 和 evaluation 仍然是核心挑战。

**金融知识体系。** FIBO 是金融领域最值得参考的 ontology 之一，可以作为 `Financial Entity + Instrument + Relationship + Business Context` 的底层参考，而不应直接当题库。

**金融能力体系。** 欧盟与 OECD-INFE 的 Financial Competence Framework 提供了一个面向金融能力的标准化框架，用于描述成年人作出合理金融决策所需的 financial competences。CFA Institute 在 2026 年进一步强调金融行业 skills taxonomy 与 skills architecture 的价值：前者描述能力层次，后者把能力与 role、业务目标和组织需求连接起来。

## 结论

如果把整个问题压缩成一个公式，我认为最值得作为 AI Interview Trainer 长期设计原则的是：

$$
\boxed{Question \neq Knowledge}
$$

而应该是：

$$
\boxed{
Question = Measurement(Knowledge,\ Capability,\ Context,\ Reasoning)
}
$$

因此：知识库不是题库，题库也不是知识库，题目只是知识状态的观测工具。

对于通用 AI 面试，可以采用 `Concept × Angle × Cognitive Task × Assessment Target × Difficulty`；对于金融领域，则进一步扩展成 `Financial Concept × Role × Scenario × Risk × Decision × Cognitive Task × Difficulty`。

这样生成出来的题目才不会继续陷入"把一个知识点蒸馏成三五道差不多的问题"的困境，而是形成一个真正覆盖**知识、能力、推理路径和诊断证据**的多维 assessment space。

这也是当前 repo 最值得继续演化的方向：最终不是建设一个"拥有很多题目的题库"，而是建设一个能够回答**"一个人究竟掌握了什么、还缺什么、缺在哪一种能力上、下一步应该测什么"**的 Knowledge Assessment System。
