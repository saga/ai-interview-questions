# Cortex Agents：线程、上下文与可恢复执行

## 对话线程不是业务状态库

Thread 可以保存对话上下文，帮助 Agent 在多轮交互中理解用户指代和任务历史。但长期业务流程状态、审计状态、审批结果和幂等键不应只保存在对话历史里。需要跨会话恢复时，应由应用或业务数据层保存状态。

## 控制上下文增长

把用户目标、业务约束、当前步骤、工具结果和历史消息区分开。大型检索结果不要原样反复注入；应保留来源 ID、关键字段和必要证据。对可重复查询的结果使用稳定的缓存或数据表，而不是依靠模型记忆。

## 可恢复的 Agent 步骤

每个业务步骤记录 Task ID、用户身份和请求版本；当前状态和下一步允许的操作；已调用工具、输入摘要和结果 ID；重试次数、超时和错误类型；人工批准状态和业务幂等键。

工具调用失败时先判断是否已经产生副作用，再决定重试。对于创建工单、触发部署或写入业务状态的工具，要设计幂等请求 ID 和查询执行结果的方式。

## 停止条件

Agent 应有最大步骤数、单步超时、预算和明确完成条件。证据不足、工具反复失败或请求超出权限时，要停止并说明缺少什么，而不是持续调用工具直到生成一个答案。

## 检查题

1. 为什么 Thread 不能代替长期业务状态存储？
2. 工具超时后，为什么不能无条件重试写操作？
3. 哪些限制能够防止 Agent 无限规划？
