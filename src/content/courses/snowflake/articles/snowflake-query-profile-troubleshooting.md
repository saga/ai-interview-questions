# Query Profile 与查询根因诊断

## 本节要解决的问题

结合 Query History、Query Profile、扫描分区、溢写、排队和算子耗时定位查询瓶颈，并用代表性工作负载验证修复。

Snowflake 工程交付与运维。重点是让配置、执行身份、变更、运行证据和恢复过程可重复、可审查、可追踪。

本教程只对应知识点 `snowflake-query-profile-troubleshooting`。目标是理解其机制、适用边界和验证方法，不把相邻知识点合并成一个大章。

## 核心知识

### 从 Query Profile 的算子、扫描量、过滤效果、Join、排序、聚合和溢写信号形成诊断假设

诊断不能只看总耗时。应拆分编译、排队、执行和结果传输，再检查扫描量、过滤效率、Join 基数、排序/聚合、溢写和估算行数偏差。

### 区分编译时间、执行时间、仓库排队时间与资源预配时间

## 常见误区

- **误区：** 只看总耗时就能确定查询瓶颈
  **纠正：** 诊断不能只看总耗时。应拆分编译、排队、执行和结果传输，再检查扫描量、过滤效率、Join 基数、排序/聚合、溢写和估算行数偏差。
- **误区：** 认为仓库加大可以修复错误的 JOIN 粒度或高扫描量
  **纠正：** Snowflake 的存储、计算与 Cloud Services 属于不同责任边界。分别检查数据持久化、Warehouse 资源以及平台级元数据、认证与协调，不能把一个层次的设置当作另一个层次的修复手段。
- **误区：** 把 Query Profile 的视觉热点当作无需复测的优化结论
  **纠正：** 诊断不能只看总耗时。应拆分编译、排队、执行和结果传输，再检查扫描量、过滤效率、Join 基数、排序/聚合、溢写和估算行数偏差。
