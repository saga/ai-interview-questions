# 事实粒度、维度建模与连接基数

## 本节要解决的问题

周一早上，财务报表里的订单收入是 72 万，运营团队用订单明细重算却得到 102 万。两边都说自己的 SQL 没错。查了半天，问题不在 Snowflake，也不在 SUM 函数：一张订单头表和一张订单明细表被直接连在一起，订单金额随着明细行重复了。

这种问题通常在数据模型设计时就埋下了。建模先要回答一个很朴素的问题：**这张表的一行究竟代表什么？** 这个定义就是 grain（粒度）。粒度没说清楚，主键、Join 关系和指标口径都无从谈起。

## 核心知识

### 先给事实表写一句能落到业务事件上的定义

假设电商系统有三张表：

| 表 | 一行代表什么 | 典型键 | 度量 |
|---|---|---|---|
| \`FACT_ORDER\` | 一笔订单 | \`ORDER_ID\` | 订单金额 |
| \`FACT_ORDER_LINE\` | 一笔订单中的一个商品行 | \`ORDER_ID + LINE_NO\` | 行金额、数量 |
| \`FACT_PAYMENT\` | 一次支付尝试 | \`PAYMENT_ID\` | 支付金额、手续费 |

三张表都可能带有 \`ORDER_ID\`，但这不意味着它们处在同一个粒度。订单可以有多条商品明细，也可以经历多次支付、失败重试和退款。

建模时把这句话写在表说明里，并进一步确认业务键、事件时间、有效时间、重复数据和更正方式。不要先画 ER 图、先定字段，再回头猜“一行代表什么”。

### 用五行数据看清 fanout 是怎样发生的

下面是教学用样例。订单头只有三行，明细有五行：

**订单头**

| ORDER_ID | CUSTOMER_ID | ORDER_TOTAL |
|---|---|---:|
| 1001 | C01 | 300 |
| 1002 | C01 | 120 |
| 1003 | C02 | 300 |

**订单明细**

| ORDER_ID | LINE_NO | LINE_AMOUNT |
|---|---:|---:|
| 1001 | 1 | 100 |
| 1001 | 2 | 200 |
| 1002 | 1 | 120 |
| 1003 | 1 | 100 |
| 1003 | 2 | 200 |

真实订单金额是 720。明细金额加起来也是 720。直接 Join 后再求订单头金额：

~~~sql
SELECT
  SUM(o.order_total) AS order_amount,
  SUM(l.line_amount) AS line_amount,
  COUNT(*) AS joined_rows
FROM fact_order o
JOIN fact_order_line l
  ON l.order_id = o.order_id;
~~~

结果会是：

| 指标 | 结果 | 原因 |
|---|---:|---|
| \`order_amount\` | 1020 | 300、300、120、300、300 被重复相加 |
| \`line_amount\` | 720 | 每条商品明细只出现一次 |
| \`joined_rows\` | 5 | 一笔订单会展开成多条明细 |

问题不是 Join “多返回了数据”，而是查询把订单头金额带到了更细的商品行粒度。此时再写 \`SUM(DISTINCT o.order_total)\` 也不是修复：两笔真实订单都可能恰好是 300，DISTINCT 会把合法订单合并掉。

正确做法是先把两边聚合到相同的分析粒度，再连接。这里按客户汇总：

~~~sql
WITH order_by_customer AS (
  SELECT customer_id, SUM(order_total) AS order_amount
  FROM fact_order
  GROUP BY customer_id
),
line_by_customer AS (
  SELECT o.customer_id, SUM(l.line_amount) AS line_amount
  FROM fact_order_line l
  JOIN fact_order o
    ON o.order_id = l.order_id
  GROUP BY o.customer_id
)
SELECT
  c.customer_id,
  COALESCE(o.order_amount, 0) AS order_amount,
  COALESCE(l.line_amount, 0) AS line_amount
FROM dim_customer c
LEFT JOIN order_by_customer o
  ON o.customer_id = c.customer_id
LEFT JOIN line_by_customer l
  ON l.customer_id = c.customer_id;
~~~

如果报表按客户和月份展示，就要在两个 CTE 中都按 \`CUSTOMER_ID + ORDER_MONTH\` 聚合，再使用这两个键连接。**共同粒度必须来自指标需求，不能为了让 SQL 好写而随便降到客户级。**

### 维度表补充分析上下文，不替代事实表的粒度

星型模型通常以事实表为中心，连接客户、产品、地区、日期等维度。维度表描述“谁、什么、何时、在哪里”，事实表回答“发生了多少、多少次、持续多久”。

订单日期、发货日期和签收日期可以复用同一张日期维度，但它们是不同的角色日期。多个事实表也可以共享客户、产品等一致维度（Conformed Dimension）。共享维度不等于可以忽略事实表之间的粒度差异。

维度键通常使用稳定的代理键。客户搬家后，如果历史报表要显示交易发生当时的地址，就需要保留维度版本：

- **SCD Type 1**：覆盖旧属性，适合不需要保留历史的修正。
- **SCD Type 2**：新增一条版本记录，保存有效起止时间和当前标记，适合按历史时点还原属性。

Type 2 维度的 Join 不能只按自然客户号连接，还要按事实发生时间匹配有效区间；否则同一笔事实可能匹配到多个历史版本。

### 度量能不能相加，取决于它描述的业务量

订单金额通常可以沿订单、客户和月份求和。库存余额则不同：同一商品每天的期末库存不能把多个日期简单相加。常见分类是：

- **可加**：订单金额、销售数量等，可沿相关维度求和。
- **半可加**：账户余额、库存快照等，通常能按账户或商品汇总，但不能沿时间直接求和。
- **不可加**：比例、转化率、平均值等，应先汇总分子和分母，再重新计算，而不是对百分比求和或简单平均。

所以 Metric 不应只有一个 SQL 表达式。还要说明计算粒度、时间口径、过滤条件、分子分母和适用维度。

## 工程实施步骤

1. 从业务报表选一个指标，写清楚“一行代表什么”、指标公式、时间口径和允许的更正方式。
2. 对每张事实表检查业务键唯一性。若业务键并不唯一，先解释重复代表什么，不要直接加 DISTINCT。
3. 为事实表和维度表画出基数：1:1、1:N、N:M。桥接表要说明它代表的关系以及是否需要权重分摊。
4. 将参与同一指标的事实表分别聚合到目标粒度，再连接共享维度。每个 CTE 都要能单独对账。
5. 对 Type 2 维度验证有效时间区间不能重叠，并测试历史日期能否只匹配到一个版本。
6. 将度量分成可加、半可加和不可加，检查报表是否在不允许的维度上做了 SUM。
7. 选取订单多明细、多次支付、退款、跨月和客户属性变更等样本，与交易系统或已认可报表核对。
8. 最后再把稳定的逻辑表、关系、Facts、Dimensions 和 Metrics 映射到 Snowflake Semantic View。语义层不会替你修复物理表的 grain 或错误键。

## 场景分析

月末结账时，财务按订单头计算收入，销售看板按订单明细计算商品销售额。两者原本应该能对上，但上线一个“订单 + 支付 + 商品”宽表后，收入突然增长了 40%。

排查不要从调大 Warehouse 开始。先抽取一笔同时有两条商品明细、两次支付尝试和一笔退款的订单，逐步比较：

| 检查点 | 应看到什么 |
|---|---|
| 订单头 | 1 行，订单金额只记录一次 |
| 订单明细 | 2 行，每件商品各一行 |
| 支付 | 2 次尝试，需区分成功和失败 |
| 退款 | 单独识别退款事件及其业务日期 |
| 宽表 Join 后 | 明确每个度量被复制了几次 |

如果订单头金额在宽表里出现两次，先修模型或聚合路径，再讨论指标展示。若支付失败尝试也被加进实收金额，则还要修正“支付金额”的业务定义。一个 Join 问题可能同时暴露两个不同的建模错误：粒度不一致和度量口径不清。

## 常见误区

- **看到两张表有相同业务键，就认为可以直接 Join。** 先检查每张表在该键上的行数；相同字段名不代表相同粒度。
- **用 \`SUM(DISTINCT amount)\` 消除重复金额。** 两笔不同业务事件可能有相同金额，DISTINCT 会把真实数据丢掉。
- **把库存余额按日期求和。** 先确定用户要看期末余额、平均余额还是期间变化量，再选择聚合方式。
- **只按客户自然键连接 Type 2 维度。** 应按事实时间匹配有效版本，并验证每笔事实只命中一个版本。
- **认为 Semantic View 能自动发现并修复 fanout。** 先在物理模型上保证唯一键、grain 和 Join 路径正确，再声明语义关系。

## 完成标准

- [ ] 能用一句话说清每张事实表的一行代表什么。
- [ ] 能用实际样本算出 1:N Join 后哪些度量会重复。
- [ ] 能把多个事实表预聚合到业务要求的共同粒度。
- [ ] 能解释 Type 1 / Type 2 对历史报表的差异。
- [ ] 能区分可加、半可加和不可加度量，并选对聚合方式。

## 自测

1. 一笔订单有 3 条商品明细和 2 次支付尝试。订单金额、商品金额和支付金额分别应该在哪个粒度汇总？
2. 两笔订单的金额都为 300。为什么 \`SUM(DISTINCT order_total)\` 不是防止 fanout 的可靠办法？
3. 客户地址在 6 月 1 日变更，财务需要按 5 月 20 日的客户地址重算报表。Type 1 和 Type 2 哪一种能满足要求？事实表还需要怎样连接维度？
4. 库存每天保存一次期末快照。要计算 6 月末库存，应该选哪一天的数据，为什么不能把整个月的快照相加？
