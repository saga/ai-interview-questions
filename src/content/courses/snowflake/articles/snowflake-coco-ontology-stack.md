# Ontology-on-Snowflake 分层设计

## 本节要解决的问题

从关系表或 OWL 输入构建物理层、元数据层、抽象视图、语义模型和 Agent，并通过阶段门禁验证完整性。

Cortex Agents、ML 与 CoCo。明确目标、工具/模型边界、身份授权、输入输出、执行证据、评测和停止条件。

本教程只对应知识点 `snowflake-coco-ontology-stack`。目标是理解其机制、适用边界和验证方法，不把相邻知识点合并成一个大章。

## 核心知识

### 五层架构分别承载物理存储、Ontology 元数据、抽象视图、语义视图和 Cortex Agent。

Iceberg 的数据文件、快照/Manifest 元数据和 Catalog 指针属于不同层次。要明确元数据提交权、文件与快照维护责任，以及多引擎一致性和权限。

### 直接表路径优先复用现有数据；知识图谱路径需要显式节点/边模型并承担额外建模和存储成本。

日志解释发生了什么，指标观察趋势，Trace 关联跨步骤执行，告警触发响应。要把这些信号与数据新鲜度、质量、批次对账和责任人连接起来。

### 每个阶段要确认输入和设计，部署前审查 SQL，阶段完成后必须等待明确批准。

可重复交付需要把版本源、目标环境、执行身份、依赖顺序、密钥、部署计划、测试证据和回滚路径连在一起。代码合并或 SQL 执行成功都不等于上线验证完成。

### 端到端验收应核对对象完整性、样本查询、层间语义一致性和 Agent 实际行为。

业务指标必须定义分子、分母、过滤条件、时间口径、事实粒度和可加性。语义层能表达已确认的业务定义，却不能修复底层错误键、粒度或多对多关系。

## 工程实施步骤

1. 将用户目标拆成可验证步骤，定义工具输入输出、身份、权限和停止条件。
2. 记录模型/工具版本、执行轨迹、失败状态、重试次数和业务幂等键。
3. 分别评估任务结果、工具选择、证据质量、越权拒绝、恢复能力和成本。

## 场景分析

用户要求 Agent 完成包含检索、分析和工具执行的任务。请定义工具选择、权限、执行轨迹、错误恢复和完成条件。

将场景转换为明确输入、状态变化和预期输出。逐项检查本节核心要求，区分配置事实、运行证据和待验证假设。缺少权限、版本、数据样本或官方行为证据时，明确记录未知项，不用猜测补齐。

## 常见误区

- **误区：** 把五层堆栈视为必须一次性自动部署的无审批脚本。
  **纠正：** 可重复交付需要把版本源、目标环境、执行身份、依赖顺序、密钥、部署计划、测试证据和回滚路径连在一起。代码合并或 SQL 执行成功都不等于上线验证完成。
- **误区：** 误认为所有关系数据都必须复制到统一图表中。
  **纠正：** 日志解释发生了什么，指标观察趋势，Trace 关联跨步骤执行，告警触发响应。要把这些信号与数据新鲜度、质量、批次对账和责任人连接起来。
- **误区：** 把 ontology 元数据、抽象视图和语义视图当成同一类对象。
  **纠正：** Iceberg 的数据文件、快照/Manifest 元数据和 Catalog 指针属于不同层次。要明确元数据提交权、文件与快照维护责任，以及多引擎一致性和权限。
- **误区：** 只核对生成文件数量，不验证部署对象和端到端查询。
  **纠正：** 文件入口、文件解析和目标表写入必须分别验证。检查路径与文件清单、格式选项、列匹配、拒绝行、加载历史和目标行数；失败重跑前先确认之前是否已部分提交。
