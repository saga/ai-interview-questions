# Ontology-on-Snowflake 分层设计

## 本节要解决的问题

采购团队希望用一个入口回答三个问题：

- 供应商 A 最近有哪些未关闭的质量问题？
- 这些问题影响了哪些产品和采购订单？
- 如果供应商暂停供货，哪些业务环节需要先处理？

仓库里已经有供应商、产品、订单、检验和质量事件表。直接写 SQL 能回答单个问题，但每个应用都要重复理解这些表、连接键和业务规则。再加上供应商、产品和订单之间存在多对多关系，指标与权限逐渐散落在不同查询里。

这时可以考虑建立业务对象模型（Ontology）：让供应商、产品、订单、质量事件成为有稳定身份的业务对象，并显式描述它们之间的关系、属性、动作和访问规则。

但不是所有数据平台都需要完整 Ontology。若需求只是统一订单收入、客户和地区指标，一个规范的维度模型加 Semantic View 通常更直接。只有当多个应用需要围绕同一业务对象导航、组合关系、执行业务动作或共享权限时，额外的对象层才有价值。

## 核心知识

### 先判断是否真的需要 Ontology

先看应用需要共享什么：

| 需求 | 通常足够的实现 |
|---|---|
| 统一指标和维度口径 | 维度模型 + Semantic View |
| 统一查询多个逻辑表 | Semantic View 的关系、Facts、Dimensions、Metrics |
| 按业务对象查找其相关订单、产品和事件 | 稳定对象 ID + 关系映射 |
| 多个应用共用对象状态、关系和动作 | 可复用的对象模型与服务接口 |
| 需要复杂图遍历、路径推理 | 在关系模型确有困难时再引入图存储或图计算 |

判断依据不是“Ontology 更先进”，而是是否有多个消费方重复实现同一组业务对象和关系。如果只有一个报表或一个自然语言查询入口，先从 Semantic View 开始，维护成本更低。

### 业务对象必须有稳定身份

供应商的显示名称不是可靠身份。名称会变更，同名供应商也可能来自不同国家或法人实体。应选用源系统中的稳定业务键，并在接入层处理跨系统映射。

例如：

| 对象 | 稳定标识 | 关键属性 |
|---|---|---|
| 供应商 | supplier_id | 法人名称、状态、国家 |
| 产品 | product_id | SKU、产品线、生命周期 |
| 采购订单 | purchase_order_id | 订单日期、状态、金额 |
| 质量事件 | quality_event_id | 发生时间、严重级别、处理状态 |

不要把供应商名称、产品标题或一段自然语言描述当成对象 ID。跨系统存在多个编号时，用一张明确的 Identity Map 记录来源系统、来源键、规范 ID、生效时间和映射状态。

### 把物理数据、对象定义和查询语义分开

可以按职责分层，但不需要为每一层都部署一个独立服务：

| 层 | 主要内容 | 解决的问题 |
|---|---|---|
| 物理数据层 | 标准表、历史表、事件表、原始数据 | 数据从哪里来，如何保存和追溯 |
| 身份与关系层 | 规范对象 ID、对象属性、关系表、有效时间 | 哪些记录属于同一个对象，业务对象如何关联 |
| 语义查询层 | 逻辑表、关系、Facts、Dimensions、Metrics | 指标如何计算，查询路径有什么含义 |
| 应用与动作层 | API、Agent 工具、工作流、权限检查 | 应用如何读取对象、提交动作并记录结果 |

Snowflake Semantic View 属于语义查询层。它提供逻辑表、关系、Facts、Dimensions 和 Metrics；不应把它误称为完整的对象运行时，也不要把关系声明当成实际数据唯一性约束。

如果应用只需要统一查询，前三层中的物理数据和语义查询可能已经够用。对象层可以先用关系表和视图实现，不必一开始就引入图数据库、OWL 推理机或复杂本体服务。

### 用关系表表达对象之间的业务关系

一个供应商可能供应多个产品，一个产品也可能有多个供应商；采购订单包含多条订单行，每条订单行指向一个产品和一个供应商。

关系表可以表达这些连接：

~~~sql
CREATE TABLE supplier_product (
  supplier_id VARCHAR NOT NULL,
  product_id VARCHAR NOT NULL,
  valid_from DATE NOT NULL,
  valid_to DATE,
  relationship_status VARCHAR NOT NULL,
  source_system VARCHAR NOT NULL,
  source_key VARCHAR NOT NULL
);

CREATE TABLE quality_event (
  quality_event_id VARCHAR NOT NULL,
  supplier_id VARCHAR NOT NULL,
  product_id VARCHAR,
  purchase_order_id VARCHAR,
  occurred_at TIMESTAMP_TZ NOT NULL,
  severity VARCHAR NOT NULL,
  status VARCHAR NOT NULL
);
~~~

这只是物理结构示例，标准表的 NOT NULL 会执行，但 PRIMARY KEY / UNIQUE / FOREIGN KEY 等声明不能替代实际唯一性与引用完整性检查。关系表需要独立测试重复映射、有效期重叠、孤儿记录和来源键冲突。

如果业务需要“某供应商影响哪些产品、这些产品关联哪些订单、订单对应哪些质量事件”，这些关系可以由 SQL 递归查询、应用查询或图计算完成。只有在路径遍历成为主要负载、关系数量和层级让 SQL 难以维护时，再考虑专门的图技术。

### 对象属性、业务状态和动作不要混在一起

一个对象模型至少要分清：

- **属性**：供应商名称、国家、等级等描述性信息。
- **关系**：供应商供应哪些产品，订单包含哪些产品。
- **状态**：供应商是否暂停、质量事件是否关闭。
- **动作**：创建复核任务、冻结新订单、请求供应商整改。

查询对象与修改业务状态是两类操作。Agent 可以查找、汇总和提出动作建议，但不能仅因为模型生成了一个“暂停供应商”的动作，就绕过授权和审批。动作应通过受控 API 或工作流执行，校验调用人、对象状态、前置条件、幂等键，并写入审计记录。

### 五层设计是一张职责图，不是五套基础设施

下面的图描述数据与请求如何经过各层。实际部署时，身份映射、关系表和元数据可以先放在同一个 Snowflake 数据库中；只有当访问模式、数据所有权或扩展需求确实不同，才拆分组件。

~~~mermaid
flowchart TB
  A["业务应用 / Agent"] --> B["对象 API 与动作校验"]
  B --> C["对象身份、属性与关系"]
  C --> D["Semantic View / SQL 查询语义"]
  D --> E["Snowflake 标准表、事件表、历史表"]
  F["源系统"] --> E
  F --> C
  B --> G["审计、工作流与审批记录"]
  C --> G
~~~

数据从源系统进入物理层，经过身份和关系映射，供查询语义层使用。应用需要修改业务状态时，不直接改底层关系表，而是通过动作接口执行并记录结果。

## 工程实施步骤

1. 收集两个以上真实消费场景，记录它们重复使用的对象、关系、属性和指标。只有一个查询场景时，先做 Semantic View。
2. 为核心对象选择稳定 ID，制定跨系统映射规则；先处理同名、重复、合并和拆分记录。
3. 用关系表记录多对多关系和有效时间；定义关系方向、业务含义、来源和失效规则。
4. 将稳定的查询模型映射为 Semantic View，分别定义逻辑表、关系、Facts、Dimensions 和 Metrics。
5. 为每个对象建立唯一性、关系完整性、有效期和历史回放测试。
6. 若需要业务动作，单独定义动作接口、授权规则、幂等键、状态迁移和审计记录。
7. 选一个应用先上线，测量查询复用率、重复建模减少量、维护成本和权限问题；没有明确收益的对象不继续抽象。
8. 当关系遍历成为瓶颈时，再比较递归 SQL、物化路径、图技术或专门对象服务，不要提前为所有可能性建设平台。

## 场景分析

质量团队要查看供应商 A 的风险。系统需要找到 A 当前供应的产品、这些产品最近 90 天的质量事件、受影响的采购订单，并按严重级别汇总。

先固定“当前供应关系”的定义：supplier_product.valid_from 已生效，valid_to 为空或晚于当前业务日期，relationship_status 为 ACTIVE。然后按 supplier_id 找到产品，再通过 product_id 和订单行连接采购订单，最后把质量事件按事件自身的 ID 计数，避免订单行 Join 后重复计算同一个事件。

结果页面至少要能展开到原始质量事件和采购订单，说明每个汇总数字来自哪些对象。若供应关系的有效期有重叠，系统应显示数据质量问题，而不是悄悄把同一产品的风险重复归给供应商。

如果另一个应用只是要按地区统计采购金额，不需要沿对象关系逐层浏览，直接复用采购金额 Metric 即可。它不需要为了“统一架构”而调用整套对象 API。

## 常见误区

- **一开始就把所有表转换成图节点和边。** 先识别应用真正需要共享的业务对象；简单指标查询通常用维度模型和 Semantic View 就够。
- **把名称当作对象身份。** 名称会变化和重复，稳定 ID 与跨系统映射需要单独治理。
- **把 Semantic View 当成完整 Ontology 运行时。** 它负责查询语义和关系路径，不自动提供对象身份合并、业务动作和审批工作流。
- **认为关系声明能保证数据关系正确。** 标准表上的部分约束不强制执行，重复关系和孤儿记录要靠数据质量测试。
- **让 Agent 直接更新底层对象表。** 业务动作应经过授权、状态迁移、幂等与审计。
- **把五层图变成五套微服务。** 先用表、视图和少量 API 实现边界，出现实际负载或所有权问题再拆分。

## 完成标准

- [ ] 能说明当前需求是否真的需要 Ontology，而不只是 Semantic View。
- [ ] 能为核心对象选定稳定身份，并处理跨系统映射。
- [ ] 能用关系表表达多对多关系和有效时间。
- [ ] 能区分物理数据、对象关系、查询语义与业务动作。
- [ ] 能设计对象关系质量检查和动作审计。
- [ ] 能解释什么时候引入图技术，什么时候保留关系模型更合适。

## 自测

1. 两个系统分别用不同供应商编号代表同一个法人实体。对象层应怎样保留来源编号并映射到规范 ID？
2. 一个供应商供应多个产品，一个产品又由多个供应商供应。为什么不能把 supplier_id 直接塞进 product 表当成唯一归属？
3. 只有一个报表要按供应商地区统计采购额。为什么 Semantic View 可能比完整 Ontology 更合适？
4. Agent 建议暂停供应商供货时，动作接口应检查哪些状态、权限和审计信息？
