# 文本分类、摘要与信息抽取

## 本节要解决的问题

把非结构化文本转换成业务流程能消费的分类标签、摘要或字段。分类回答“属于哪一类”，摘要回答“主要内容是什么”，抽取回答“某个字段的值是什么”。三种任务的输出契约和质量指标不同，不应只通过一段通用 Prompt 要求模型完成所有工作。

## 核心知识

### 分类是从预定义类别中选择标签

AI_CLASSIFY 面向文本分类，可以指定允许的类别集合，并将输入映射到其中的类别。适合工单路由、评论主题、投诉原因、风险标签和文档类型识别。类别集合要尽量互斥，定义边界清晰，并保留 Other/Unknown 或人工复核路径。

分类结果不能直接视为业务事实。需要用人工标注的代表性数据评估 Macro-F1、Precision、Recall 和类别混淆；少数类不能只看整体 Accuracy。若某些类别的误判代价更高，应定义不同门槛和升级规则。

### 摘要是压缩要点，不是补全缺失事实

AI_SUMMARIZE 用于缩短文本、保留主要信息，适合客服记录、报告、长邮件和会议材料。摘要目标应明确：受众是谁、保留哪些字段、需要多长、是否保留时间/金额/责任人等关键事实。

摘要可能遗漏限定条件或把不确定语气改成确定结论。对合同、财务和合规文本，应保留原文引用或证据位置，并针对数字、日期、主体和否定语句建立校验。

### 信息抽取要定义字段，不能只要求“找出重要信息”

AI_EXTRACT 适合按 Schema 提取实体、列表和表格，AI_PARSE_DOCUMENT 适合先解析文件并保留版面上下文。若输入已经是纯文本且只需要几个字段，可以评估 AI_EXTRACT 或结构化 AI_COMPLETE；若要从复杂 PDF、扫描件或表格中提取字段，先解析文档往往更合适。

输出字段应定义类型、必填与缺失语义。抽取不到的值应标记为空/未知，不能让模型猜测补齐。字段合法性和业务规则要在 SQL/程序中进行确定性校验。

## 工程实施步骤

1. 对每个文本任务写清输入类型、目标输出、允许类别或字段、语言、敏感信息和失败动作。
2. 固定分类标签和边界定义，准备覆盖常见、相似、混合、少数类和未知情况的标注样本。
3. 分类任务使用 AI_CLASSIFY 并评估类别级 Precision/Recall；对低质量类别检查标注定义和训练/评估样本，而不只调整 Prompt。
4. 摘要任务定义长度、受众和必须保留的事实字段；使用数字、日期、否定句和长文本样本验证遗漏风险。
5. 抽取任务定义 JSON Schema/字段契约，明确类型、必填、允许缺失和列表顺序；文档类输入先判断是否需 AI_PARSE_DOCUMENT。
6. 将模型候选结果写入 staging，保留原文、输出、模型/提示版本、请求 ID 和来源定位。
7. 执行确定性检查：类别是否在允许集合内、日期/金额是否可解析、实体是否存在、汇总是否对账。
8. 对低置信、未知类别、缺字段或证据位置不一致的记录转人工复核。
9. 用独立评测集比较不同模型和 Prompt，分别统计分类、摘要和字段抽取指标，不合并成一个平均分。
10. 记录每千条输入的 token、延迟、错误重试、人工复核和更正成本，决定是否值得扩大调用规模。

示例：对工单先分类，再根据类别进入相应处理队列。

~~~sql
SELECT
  TICKET_ID,
  AI_CLASSIFY(
    TICKET_TEXT,
    ['billing', 'delivery', 'account_access', 'product_issue', 'other']
  ) AS ISSUE_CATEGORY
FROM RAW.SUPPORT_TICKETS;
~~~

分类结果应与人工标注集对比；不能将模型标签作为唯一的赔偿、冻结账户或合规决策依据。

## 场景分析

客服每天收到计费、配送、账户登录和产品质量问题。当前一个 AI_COMPLETE Prompt 同时生成类别、摘要和处理建议，输出格式有时缺字段，客服系统也无法判断分类错误。

拆分流程：先用 AI_CLASSIFY 为工单选择类别；再用 AI_SUMMARIZE 生成内部摘要；需要提取订单号、日期或金额时使用明确字段 Schema；复杂投诉建议才调用通用模型。将每一步输出存入 staging，并分别验证类别、摘要事实和字段抽取结果。

验收应按类别统计混淆矩阵，按字段统计准确率，并对摘要检查金额、日期、主体和否定语句。涉及退款或账户操作的建议必须走业务规则和授权流程，不能因为摘要与分类成功就自动执行。

## 常见误区

- **分类、摘要和抽取完全相同。** 它们有不同的目标输出和评估指标。
- **只看整体分类准确率。** 少数类错误可能被多数类掩盖，需要查看每类 Precision/Recall。
- **要求摘要“简短”而不说明必须保留哪些事实。** 这会让金额、期限和责任人等信息被压缩掉。
- **把抽取不到的字段自动补成推测值。** 应保留缺失状态并进入复核。
- **把 JSON 可解析当作字段正确。** 结构校验与业务校验是两个独立步骤。
- **所有文本任务都用同一个大模型。** 专用函数、字段 Schema 和确定性校验通常更容易控制成本与错误范围。

## 完成标准

- [ ] 能区分分类、摘要与字段抽取的目标和输出契约。
- [ ] 能为分类任务设计可评估的类别集合。
- [ ] 能为摘要定义受众、长度和必须保留的事实。
- [ ] 能为抽取定义 Schema、缺失语义和业务校验。
- [ ] 能分别评估类别质量、摘要事实保留和字段准确率。

## 自测

1. 工单分类的整体 Accuracy 很高，但少数类投诉漏分严重，应该检查哪些指标？
2. 一份合同摘要遗漏了提前终止条款，如何改进摘要目标和校验？
3. 抽取字段缺失时，为什么不应让模型默认猜一个值？
4. 何时需要先调用 AI_PARSE_DOCUMENT，再做 AI_EXTRACT？
5. 为什么不应将分类、摘要和抽取的质量合并成一个整体分数？
