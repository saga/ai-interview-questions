# Raw、Conformed 与 Curated 数据分层

## 本节要解决的问题

用分层模型明确数据从源系统进入平台后，每一层保留什么、承担什么质量责任、如何被下游消费。Raw、Conformed 和 Curated 是一种数据工程组织模式，不是 Snowflake 内置的三种表类型或必须采用的固定架构。

## 核心知识

### Raw 层保留可追溯的源数据和摄取事实

Raw 的目标是保留来源、到达时间、批次、文件名/事件 ID、原始业务键以及必要的原始字段。它让团队能够重放、解释源端变化和定位转换错误。Raw 并不意味着不设权限或无限期保留；敏感字段需要分类、访问控制和生命周期管理。

不同源系统可能有不同结构和更新语义。Raw 层应保留必要的源系统上下文，避免刚进入平台就把字段重命名、去重或覆盖历史，从而失去问题调查和回放能力。

### Conformed 层统一实体、键和业务规则

Conformed 将来自不同来源的数据整理成统一的业务实体和编码体系。例如统一客户主数据、产品编码、时区、币种、状态枚举和事件时间。它需要解决主键映射、重复源记录、迟到/更正数据和跨源冲突。

Conformed 不只是把列名改成统一命名。它应显式保存来源映射、主数据规则、数据质量结果和必要的历史版本；不同系统对同一实体有冲突时，要有业务 owner 决定权威值或保留多源属性。

### Curated 层面向业务消费提供稳定契约

Curated 可以包含星型模型、数据集市、主题汇总、语义视图和受控共享对象。其重点是定义消费者能依赖的粒度、指标、刷新时效、质量门槛和版本兼容策略。

同一套 Raw/Conformed 数据可生成多个 Curated 产品。不要为每个报表机械复制完整数据链路；优先复用稳定的实体、维度和业务规则，再按消费场景建立适当的数据产品。

### 分层边界应解决真实的组织问题

分层并不是为了增加数据库数量或建立固定三套数据副本。若系统规模较小、来源有限且只有单一消费场景，过度分层会增加维护和刷新成本。只有当重放、跨源标准化、团队 ownership、审计或多个消费模型的需求足够明确时，才需要把边界分开。

## 工程实施步骤

1. 盘点数据源、数据 owner、数据敏感等级、输入方式、更新频率、重放需求和消费场景。
2. 先决定 Raw 是否需要保留源文件、原始事件或变更日志，并定义批次 ID、来源键、到达时间和保留周期。
3. 为 Conformed 定义主数据键、实体匹配规则、代码映射、时间/币种标准、更新冲突处理和历史追踪策略。
4. 为 Curated 列出消费者、指标定义、粒度、刷新目标、质量门槛和访问角色。
5. 将质量门禁放在数据转换边界：Raw 检查摄取完整性；Conformed 检查实体和标准化；Curated 检查指标、汇总和消费契约。
6. 通过 Snowflake Schema、Role、Tag、Masking Policy、Row Access Policy 等对象能力实现权限，不要依赖层级名称本身代表安全边界。
7. 设计从源数据重放到 Curated 重建的路径，明确增量转换、历史回补和失败批次如何恢复。
8. 对每层记录 owner、刷新状态、上游依赖、数据质量结果和血缘信息，便于定位影响范围。
9. 通过实际消费者验证：同一指标在不同报表中的口径一致，数据延迟满足要求，权限隔离有效，重放不会产生重复结果。

## 场景分析

公司有 CRM、ERP 和电商订单三套客户信息。CRM 使用邮箱标识，ERP 使用客户号，电商系统使用会员 ID。财务、客服和营销需要不同的客户分析视图。

Raw 保留三套源记录及其来源键；Conformed 建立客户实体映射与冲突规则，保留各源 ID 及有效时间；Curated 为财务提供收入和客户维度模型，为营销提供会员分群数据，为客服提供合并后的客户视图。不要在 Raw 直接把三套 ID 覆盖成一个客户号，否则出现身份合并错误时很难回溯。

如果实际只有一个系统和一个下游报表，可能不需要完整的三层独立模型；可以先在同一数据库/Schema 内用清晰对象和责任约定实现，等跨源与多消费者需求真实出现再拆分。

## 常见误区

- 把 Raw 定义成无治理的数据垃圾区。原始数据也要有访问控制、保留策略和敏感数据治理。
- 把 Conformed 等同于改字段名。它要处理实体映射、主数据冲突、键和历史语义。
- Curated 只为每张报表复制一份数据。应优先复用稳定业务实体和定义，避免出现多个互相矛盾的指标。
- 把三层当作 Snowflake 强制对象类型。它是组织数据工程的架构模式，物理上可通过数据库、Schema、表和视图实现。
- 认为分层越多越成熟。需要按重放、治理、协作和消费收益决定复杂度。

## 完成标准

- [ ] 能说明 Raw、Conformed、Curated 各层的输入、输出和责任。
- [ ] 能区分源数据保留、主数据标准化和业务消费模型。
- [ ] 能设计跨源实体映射及冲突处理。
- [ ] 能在不同层设置对应的数据质量和访问治理。
- [ ] 能判断什么时候不需要完整三层架构。

## 自测

1. 为什么 Raw 层应保留来源键和到达时间，而不是只保留转换后的客户 ID？
2. 两个源系统对客户姓名和地址存在冲突，应该在哪一层定义统一规则？谁负责裁决？
3. Curated 的收入指标在两个报表中不同，应该从哪些数据契约与转换边界排查？
4. 一个小型项目只有一个数据源和一份报表，强行拆三套物理数据库可能带来什么成本？
