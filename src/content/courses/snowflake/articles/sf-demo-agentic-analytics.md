# Agentic Analytics 端到端分析

## 本节要解决的问题

运营负责人问：“华东地区本周退货率为什么上升？影响最大的产品有哪些，是否需要暂停补货？”

这个问题不能只靠一个 SQL，也不能让 Agent 随便查几张表后直接下结论。它至少包含四件事：确定“退货率”的业务口径、检索退货原因和运营说明、计算地区与产品维度的变化、把数据事实和可能原因分开表达。

Agentic Analytics 的价值是协调这些步骤，而不是把每一步都交给语言模型猜。指标查询应由受治理的语义模型定义，文档证据应有来源和时间，工具执行应有权限与结果校验，最终结论要说明哪些是事实、哪些仍是假设。

## 核心知识

### 先把用户问题拆成可验证的子问题

可以把问题拆成：

| 子问题 | 需要的数据或证据 | 输出 |
|---|---|---|
| 退货率是否真的上升 | 订单、退货事实、业务日期 | 本周与基线的退货率 |
| 哪些产品贡献最大 | 产品维度、订单与退货明细 | 产品贡献排序 |
| 是否集中在某类原因 | 退货原因、质检记录、客户反馈 | 原因分布与样本 |
| 是否需要暂停补货 | 库存、在途采购、供应商和业务规则 | 风险清单与建议，不自动执行 |

先确认分子和分母。例如退货率可能按退货订单数 / 已发货订单数，也可能按退货件数 / 销售件数。分母不同，结论可能完全不同。还要确认退货按申请日、批准日还是入库日计入本周。

如果用户没有说明口径，Agent 应先查询已批准的 Metric 定义；如果语义模型里没有对应定义，就向业务人员澄清，而不是自行挑一个公式。

### 把语义指标查询和文档检索分开

结构化指标查询适合 Semantic View。它可以定义逻辑表、关系、Facts、Dimensions 和 Metrics，让“本周退货率”沿同一业务口径计算。Agent 不应把金额、订单数和退货数量混在一条未经验证的 SQL 里临时计算。

非结构化证据则来自产品质量记录、客户反馈和运营公告。检索结果要保留文档 ID、版本、发布时间和引用片段。搜索到“包装破损”相关文档，只能说明存在相关记录，不能直接证明它导致了本周退货率上升。

一个简化的请求流可以是：

~~~mermaid
flowchart TD
  A["用户问题"] --> B["口径澄清与任务拆分"]
  B --> C["Semantic View 指标查询"]
  B --> D["Cortex Search 文档检索"]
  C --> E["结果校验与时间对齐"]
  D --> F["引用与版本检查"]
  E --> G["合并证据"]
  F --> G
  G --> H["原因分析与不确定性说明"]
  H --> I["报告与建议"]
~~~

结构化指标和文档证据需要分别验证，再按相同地区、产品和时间窗口合并。不要因为两个结果都提到“华东”就默认它们使用同一业务日期或同一产品标识。

### 每个工具都要有清楚的输入、输出和权限边界

建议把可调用工具拆成窄接口：

| 工具 | 输入 | 输出 | 限制 |
|---|---|---|---|
| 查询指标 | 已批准的 Metric、地区、时间范围 | 聚合结果、查询 ID | 只读、限定对象和行级权限 |
| 搜索资料 | 查询文本、允许的文档范围 | 文档 ID、版本、引用片段 | 继承文档访问权限 |
| 查询样本 | 产品 ID、业务日期 | 脱敏样本行或统计 | 限制行数和敏感字段 |
| 生成报告 | 已校验的指标与证据 | 结论、引用和待确认项 | 不得自行补造数据 |
| 创建业务动作 | 经过确认的动作参数 | 工作流 ID | 需要授权和人工确认 |

工具返回的文本和文档内容是数据，不是新的系统指令。Agent 不能因为检索到一段“忽略之前的规则”就改变权限或工具行为。工具执行身份应由服务端确定，不能直接采用用户问题或检索文档里提供的 Role 名称。

### 计划完成不代表业务问题已经回答

Agent 可能成功调用查询工具，但结果仍可能有问题：

- 指标查询返回 0 行，可能是过滤条件错误，不代表退货率为零。
- 检索到过期的质量公告，可能不能解释当前周的问题。
- 产品维度的连接发生 fanout，导致贡献排序重复计数。
- 订单按创建时间、退货按批准时间统计，两个时间窗口无法直接比较。

每次工具调用后都要检查执行状态、行数、时间范围、查询 ID 和关键控制总额。结果异常时应停止后续推断，说明缺少什么证据，而不是继续生成一份看似完整的报告。

### 最终报告要把事实、推断和行动分开

一份可复核报告至少区分：

1. **观察到的事实**：指标值、对比基线、样本数量、数据更新时间。
2. **支持证据**：文档 ID、版本、引用片段、关联查询 ID。
3. **推断**：哪些产品或原因可能与变化有关，支持程度如何。
4. **不确定性**：样本不足、口径差异、数据延迟或未覆盖的原因。
5. **建议动作**：需要谁确认，执行前需要哪些条件。

“退货率上升 2.1 个百分点”可以是数据事实；“主要由于包装破损”只有在原因标注和样本分析支持时才成立；“暂停某供应商补货”是业务动作，需要相应责任人确认。

## 工程实施步骤

1. 为业务问题建立任务模板，要求地区、时间范围、比较基线、指标口径和输出格式明确。
2. 将指标查询限制在已批准的 Semantic View 和 Metric；保存语义模型版本、查询文本和 Query ID。
3. 将文档检索限制在允许的索引和用户权限范围；保存来源 ID、文档版本和引用片段。
4. 统一地区、产品 ID、业务日期和时间范围；不一致时先做映射或要求澄清。
5. 检查查询结果的行数、NULL、重复键、金额/数量控制总额和刷新时间。
6. 对检索证据做引用检查，确认文档仍有效，引用文本确实支持所写结论。
7. 生成报告时把事实、推断、未知项和建议动作分开，拒绝为缺失数据补造原因。
8. 对关键建议建立人工确认流程；Agent 不直接暂停供货、修改订单或变更数据权限。
9. 记录每次工具调用、输入摘要、执行身份、返回状态、Query ID、重试和最终报告版本。
10. 用固定问题集回归事实正确性、引用支持、拒答、权限拒绝、延迟和成本。

## 场景分析

本周华东退货率从 4.2% 升到 6.3%。Agent 查询到两份证据：产品 A 的包装质检记录提到封口问题；产品 B 的客户反馈提到尺寸不符。若只看文档数量，可能会把包装问题判断为主要原因。

正确的分析要先看产品维度的退货量和销售量，再计算每个产品对总体退货率变化的贡献；然后检查原因标注是否覆盖全部退货，样本是否集中在同一批次。两份文档只支持“存在这两类问题”，不能单独证明哪一种是主要原因。

报告可以列出产品 A 和 B 的退货变化、各自原因样本数量、对应文档和数据更新时间。若原因字段缺失率较高，就应将“主要原因尚不能确定”作为结论，而不是让 Agent 用自然语言把空缺补齐。

## 常见误区

- **让 Agent 自己决定退货率公式。** 指标定义应来自已批准的语义模型或业务确认。
- **把检索命中当成因果证明。** 文档相似度和事件关联都不能单独证明原因。
- **把不同日期口径的结果直接合并。** 先统一业务时间、时区和刷新时间。
- **用一个万能 SQL 工具处理所有操作。** 工具接口应限定对象、输入、返回和权限。
- **把工具调用成功当成分析完成。** 还要检查返回结果、数据质量、来源版本和对账。
- **让 Agent 自动执行高影响业务动作。** 暂停供应商、取消订单或修改权限应走受控工作流和人工确认。

## 完成标准

- [ ] 能将业务问题拆成指标、文档证据和待确认事项。
- [ ] 能解释为什么结构化指标与非结构化证据需要分别验证。
- [ ] 能为工具定义输入、输出、权限和停止条件。
- [ ] 能识别时间口径、Join 粒度和来源版本不一致造成的错误。
- [ ] 能把事实、推断、不确定性和业务动作分开呈现。
- [ ] 能设计固定问题集评测事实正确性、引用、权限、延迟和成本。

## 自测

1. 退货率可以按退货订单数 / 已发货订单数，也可以按退货件数 / 销售件数。Agent 应怎样处理口径不明确的问题？
2. Semantic View 查询显示产品 A 退货量上升，文档检索找到一份包装问题报告。为什么还不能直接说包装问题导致了退货上升？
3. 指标按订单创建日期统计，退货按批准日期统计。把两个结果合并前要先确认什么？
4. 检索结果返回一段要求 Agent 忽略权限的文本。为什么它不能改变工具的执行策略？
5. 什么情况下 Agent 应停止分析并报告证据不足，而不是继续补全结论？
