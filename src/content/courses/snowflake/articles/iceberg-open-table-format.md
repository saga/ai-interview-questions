# Apache Iceberg 与开放 Lakehouse 架构

## 本节要解决的问题

理解 Iceberg 表格式、元数据/快照、对象存储与 Catalog/引擎协作。

Iceberg / Lakehouse。理解数据文件、表元数据、Catalog、写入协调、计算引擎和维护责任。

本教程只对应知识点 `iceberg-open-table-format`。目标是理解其机制、适用边界和验证方法，不把相邻知识点合并成一个大章。

## 核心知识

### 解释数据文件、metadata/snapshot 与 Catalog 边界

文件入口、文件解析和目标表写入必须分别验证。检查路径与文件清单、格式选项、列匹配、拒绝行、加载历史和目标行数；失败重跑前先确认之前是否已部分提交。

### 依据存储控制权、跨引擎访问和事务能力选择管理模式

Iceberg 的数据文件、快照/Manifest 元数据和 Catalog 指针属于不同层次。要明确元数据提交权、文件与快照维护责任，以及多引擎一致性和权限。

### 考虑 Catalog 一致性、权限与引擎支持差异

权限判断沿用户、当前激活角色、角色继承、对象权限和所有权追踪，并检查 Database、Schema 与目标对象的使用权限。

## 工程实施步骤

1. 盘点 Catalog 类型、元数据写入者、对象存储路径、区域和读写引擎。
2. 明确 Schema/Partition Evolution、并发提交、文件维护和权限传播责任。
3. 通过跨引擎读写、快照一致性、数据对账和恢复演练验收。

## 场景分析

同一份 Iceberg 数据需要由 Snowflake 和另一个引擎读取或写入。请说明 Catalog、对象存储、写入权、维护任务和一致性验证如何分工。

将场景转换为明确输入、状态变化和预期输出。逐项检查本节核心要求，区分配置事实、运行证据和待验证假设。缺少权限、版本、数据样本或官方行为证据时，明确记录未知项，不用猜测补齐。

## 常见误区

- **误区：** 把 Iceberg 当另一种 Parquet 编码
  **纠正：** Iceberg 的数据文件、快照/Manifest 元数据和 Catalog 指针属于不同层次。要明确元数据提交权、文件与快照维护责任，以及多引擎一致性和权限。
- **误区：** 认为开放格式意味着所有引擎语义一致
  **纠正：** Iceberg 的数据文件、快照/Manifest 元数据和 Catalog 指针属于不同层次。要明确元数据提交权、文件与快照维护责任，以及多引擎一致性和权限。
- **误区：** 忽略 Catalog 和存储权限
  **纠正：** 权限判断沿用户、当前激活角色、角色继承、对象权限和所有权追踪，并检查 Database、Schema 与目标对象的使用权限。
