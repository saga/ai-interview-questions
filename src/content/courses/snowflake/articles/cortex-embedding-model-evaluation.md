# 检索表示质量、召回评估与查询集设计

## 本节要解决的问题

内部知识库上线后，用户问“如何恢复被误删的订单记录”，系统返回了三篇介绍 Time Travel 的文档，却漏掉真正说明保留期和恢复步骤的操作手册。换了一个 embedding 模型后，离线相似度分数提高了，实际用户却更难找到操作文档。

问题在于：向量距离不是检索质量本身。模型只把文本映射到表示空间；最终检索效果还受文档切分、查询分布、关键词、过滤条件、排序和数据新鲜度影响。评估必须从用户问题和相关证据出发，而不是从模型名称或一组相似度分数出发。

## 核心知识

### 先定义什么结果才算“找到了”

以运维知识库为例，同一个问题可能需要不同类型的证据：

- “Time Travel 能恢复多久以前的数据？”需要保留期和版本边界。
- “如何恢复一张被误删的表？”需要可执行的恢复步骤。
- “SQLSTATE 2043 是什么错误？”需要准确命中错误码文档。

对每条查询，先标注相关文档及相关程度。不要把“内容主题相似”自动标成相关：一篇介绍 Time Travel 原理的文档可能有助于理解，却不一定能回答实际恢复步骤。

一个实用的查询集可以分成：

| 查询类型 | 样例 | 主要检验 |
|---|---|---|
| 自然语言问题 | 如何恢复误删的订单表？ | 语义召回 |
| 产品名/术语 | Time Travel retention | 关键词与语义匹配 |
| 错误码/标识符 | SQLSTATE 2043 | 精确文本检索 |
| 同义表达 | warehouse 被暂停 / 仓库 suspend | 术语归一化 |
| 长尾问题 | 某个旧版本的参数限制 | 长尾覆盖 |
| 多语言混合 | 日文描述 + SQL 函数名 | 语言与标识符混合 |
| 访问受限内容 | 财务制度、客户合同 | 权限过滤 |

每条查询要保存预期相关文档、标注理由、语言、业务类别和敏感权限范围。标注可以有 0/1/2 等级，例如不相关、部分相关、直接回答；重要业务查询最好由实际使用者或领域人员复核。

### 用 Recall@K、MRR 和 nDCG 看检索的不同问题

假设某条查询有 4 篇已标注的相关文档，系统返回前 5 条，其中命中 3 篇：

- Recall@5 = 3 / 4 = 0.75，表示相关文档中有 75% 被找回。
- Precision@5 = 3 / 5 = 0.60，表示前 5 条中有 60% 是相关结果。
- MRR 关注第一条相关结果排在第几位；第一条相关结果排第 2，倒数排名就是 1/2。
- nDCG 同时考虑排序位置和相关等级，直接回答的文档应排在“只是相关”的文档之前。

不要只盯 Recall。把所有相关文档都找回来，但前 10 条大多无关，用户仍然要翻很久。反过来，只返回一篇高度相关文档，Precision 可能很好，却可能遗漏关键的恢复步骤和限制。

可以先用一个小脚本计算 Recall@K 和 MRR：

~~~python
def recall_at_k(relevant_ids: set[str], ranked_ids: list[str], k: int) -> float:
    if not relevant_ids:
        return 0.0
    hits = set(ranked_ids[:k]) & relevant_ids
    return len(hits) / len(relevant_ids)


def reciprocal_rank(relevant_ids: set[str], ranked_ids: list[str]) -> float:
    for rank, doc_id in enumerate(ranked_ids, start=1):
        if doc_id in relevant_ids:
            return 1.0 / rank
    return 0.0
~~~

生产评测要对整个查询集求均值，并按查询类型、语言、权限范围、热门/长尾分组。单一总体平均值可能掩盖某一类用户的明显退化。

### Embedding、关键词、重排分别解决不同问题

向量检索擅长找到语义相近但措辞不同的内容；关键词检索擅长命中精确术语、错误码和对象名称。混合检索能兼顾两者，重排器再对候选结果进行排序。

Cortex Search 默认结合向量相似度、文本匹配和 reranking 计算相关性，并允许对组件权重、数值属性和时间属性进行调整。调参前要先判断错误发生在哪一层：

1. 相关文档根本不在候选集合中：优先检查数据接入、文档切分、embedding 表示和召回深度。
2. 候选集合里有正确文档，但排位靠后：检查文本匹配、向量权重和 reranking。
3. 前几条文档正确，答案仍然错误：检查上下文截断、引用定位和生成阶段，不要继续盲目调 embedding。
4. 用户看到了无权访问的文档：这是权限过滤缺陷，不是排序问题，必须先修安全边界。

### 数据新鲜度和权限过滤必须单独评估

Cortex Search 的内容来自服务定义中的源查询；源数据发生变化后，服务会按其 refresh 机制更新。Primary Key 可用于标识源查询结果中的行，并支持只处理变化记录的优化刷新路径。它不是业务文档的永久 ID 方案，仍要确认键稳定且唯一。

评估集至少加入三类变化：

- 文档更新：旧版本被新版本替代，确认旧段落不再排在前面。
- 文档删除或失效：确认被撤销的内容不会继续作为答案依据。
- 权限变化：用户 A 可以看到的文档，用户 B 不应通过检索、重排或引用得到。

检索效果不能靠牺牲权限换取。过滤条件应在检索服务或可信服务端执行，并用不同角色的测试身份做负向验证。

## 工程实施步骤

1. 从真实搜索日志、客服问题和业务人员访谈收集查询；脱敏后按问题类型分层，不只挑容易命中的热门问题。
2. 为每条查询标注相关文档、相关等级、答案所需证据和权限范围；存在争议的标签交由领域人员复核。
3. 固定文档切分、元数据、过滤条件和索引版本，建立可重复的基线。
4. 分别运行关键词检索、向量检索和混合检索，计算 Recall@K、Precision@K、MRR 和 nDCG。
5. 保存候选集与最终排序，区分“没召回到”和“召回后排错了”，避免把所有问题都归因于 embedding。
6. 每次更换模型、切分策略或权重时，使用同一测试集进行版本化比较；同时检查延迟、吞吐和 embedding/refresh 成本。
7. 更新或删除文档后，检查刷新完成时间、源记录数量和旧版本是否还可检索。
8. 使用不同 Role 和用户身份验证权限过滤，确认无权文档不会出现在结果、引用或日志回显中。
9. 抽样人工检查高影响问题，记录错误类型、修复措施和回归用例。

## 场景分析

员工搜索“供应商合同到期前多久要发起续签”。知识库有合同管理规范、采购操作手册和几份旧版合同模板。向量检索返回了一篇内容相似的旧合同，关键词检索则找到当前规范中的“续约提醒周期”。

先确认当前生效的规范是唯一直接回答的来源，旧合同模板只能作背景材料。查询集应同时包含“续签提前多久”“合同到期提醒”“renewal notice period”等变体，并将旧版合同标为过期证据。评测不仅看规范有没有进入 Top 5，还要看它是否排在旧模板之前。

如果规范内容更新后仍有旧版本出现在结果中，就应检查源查询、Primary Key 和 refresh 状态；如果普通员工搜索结果包含法务限制文档，则先修权限过滤，不能通过调低该文档的排序分数来掩盖问题。

## 常见误区

- **用 embedding cosine similarity 直接代表答案正确率。** 相似度只能说明表示空间接近，不能证明文档回答了用户问题。
- **只用热门问题建评测集。** 长尾、缩写、错误码和多语言查询往往更能暴露召回缺口。
- **只看 Recall@K。** 还要看 Precision、排序位置、答案引用和实际任务完成情况。
- **召回失败就换更大的模型。** 先检查切分、源数据、关键词召回和过滤条件。
- **把索引刷新延迟当成 embedding 模型问题。** 先确认源查询和 refresh 是否完成。
- **把权限过滤当成排序偏好。** 无权文档必须被排除，不能只是排名靠后。

## 完成标准

- [ ] 能构建覆盖热门、长尾、精确术语和多语言的查询集。
- [ ] 能解释 Recall@K、Precision@K、MRR 和 nDCG 的用途。
- [ ] 能区分向量召回、关键词匹配和 reranking 的问题。
- [ ] 能通过版本化测试比较 embedding 或检索配置的变化。
- [ ] 能验证索引更新、文档失效和权限过滤。
- [ ] 能把检索质量、延迟、成本和最终答案质量分开衡量。

## 自测

1. 已知有 4 篇相关文档，Top 5 命中 3 篇，Recall@5 是多少？它能说明前 5 条的排序质量吗？
2. 错误码查询总是找不到正确文档，但自然语言问题表现正常。应该优先检查向量模型，还是关键词匹配？
3. 正确文档已经进入候选集却排在第 8 位，应该检查召回阶段还是 reranking？
4. 文档刚更新，搜索结果仍返回旧版本。应检查哪些源查询、主键和 refresh 证据？
5. 普通员工能搜索到法务限定文档。为什么不能只通过调整排序分数处理？
