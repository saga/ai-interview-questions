# PostgreSQL 系统目录、日志与监控

## 本节要解决的问题

使用 pg_catalog、information_schema、pg_stat_*、日志和扩展指标观察对象、查询、锁、I/O 与数据库健康状况。

PostgreSQL 数据库工程。依据 PostgreSQL 自身的事务、MVCC、WAL、索引、优化器和后台维护语义分析问题，不将 Snowflake 机制套用到 PostgreSQL。

本教程只对应知识点 `postgresql-catalogs-logging-monitoring`。目标是理解其机制、适用边界和验证方法，不把相邻知识点合并成一个大章。

## 核心知识

### 区分结构元数据目录、标准 information_schema 与运行统计视图

Iceberg 的数据文件、快照/Manifest 元数据和 Catalog 指针属于不同层次。要明确元数据提交权、文件与快照维护责任，以及多引擎一致性和权限。

### 查询 pg_stat_activity、pg_stat_user_tables、pg_stat_user_indexes 等诊断信息

诊断不能只看总耗时。应拆分编译、排队、执行和结果传输，再检查扫描量、过滤效率、Join 基数、排序/聚合、溢写和估算行数偏差。

### 设置有用的日志类别、慢查询阈值、日志关联字段及保留策略

日志解释发生了什么，指标观察趋势，Trace 关联跨步骤执行，告警触发响应。要把这些信号与数据新鲜度、质量、批次对账和责任人连接起来。

## 工程实施步骤

1. 复现问题并记录版本、当前数据库、Role、SQL、参数和时间范围。
2. 结合 EXPLAIN、pg_stat_*、锁视图和日志定位执行、I/O、连接或事务瓶颈。
3. 在受控窗口验证变更，比较结果正确性、锁影响、资源占用和恢复方式。

## 场景分析

订单服务出现查询变慢、连接数上升或事务阻塞。请使用 PostgreSQL 执行计划、统计视图和事务信息定位问题，不要先通过加资源或终止会话掩盖根因。

将场景转换为明确输入、状态变化和预期输出。逐项检查本节核心要求，区分配置事实、运行证据和待验证假设。缺少权限、版本、数据样本或官方行为证据时，明确记录未知项，不用猜测补齐。

## 常见误区

- **误区：** 把累计统计值误读成当前瞬时值或每条查询的耗时
  **纠正：** 日志解释发生了什么，指标观察趋势，Trace 关联跨步骤执行，告警触发响应。要把这些信号与数据新鲜度、质量、批次对账和责任人连接起来。
- **误区：** 认为日志越详细越好而不评估 I/O、存储和敏感信息风险
  **纠正：** 日志解释发生了什么，指标观察趋势，Trace 关联跨步骤执行，告警触发响应。要把这些信号与数据新鲜度、质量、批次对账和责任人连接起来。
- **误区：** 认为一个 cache hit ratio 指标足以解释所有性能问题
  **纠正：** 先用执行计划和运行证据识别扫描、过滤、缓存、Join 或排队瓶颈，再考虑聚类、索引、加速服务或重写。优化要对比延迟、扫描量和费用。
