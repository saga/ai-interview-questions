# Dynamic Tables 生产选型与诊断

## 本节要解决的问题

根据 SQL 转换、延迟、过程控制、测试与可移植性需求选择 Dynamic Tables、Materialized Views、Streams/Tasks 或 dbt。

数据工程。将输入、摄取、转换、状态推进、目标写入和下游可见性分开观察；执行成功必须结合质量、重放能力和端到端延迟。

本教程只对应知识点 `snowflake-coco-dynamic-tables`。目标是理解其机制、适用边界和验证方法，不把相邻知识点合并成一个大章。

## 核心知识

### Dynamic Tables 以声明式 SELECT 和 TARGET_LAG 管理多步骤 SQL 转换的新鲜度目标。

新鲜度目标不是固定运行周期或无条件 SLA。应结合刷新模式、依赖变化、资源消耗和实际刷新历史判断是否满足业务要求。

### TARGET_LAG 是目标而不是无条件固定刷新周期或业务 SLA，必须观测实际延迟。

新鲜度目标不是固定运行周期或无条件 SLA。应结合刷新模式、依赖变化、资源消耗和实际刷新历史判断是否满足业务要求。

### 多层管道通常由叶子层声明时间目标，中间层用 DOWNSTREAM 继承下游新鲜度需求。

Stream 暴露的是自上次消费位置以来的变更视图，消费进度与事务提交相关。需要明确消费事务、目标幂等键和失败恢复流程，不能把它当无限期完整变更日志。

### 需要过程控制、副作用或极低延迟时评估 Streams/Tasks；需要测试框架或跨仓库可移植性时评估 dbt。

Snowflake 的存储、计算与 Cloud Services 属于不同责任边界。分别检查数据持久化、Warehouse 资源以及平台级元数据、认证与协调，不能把一个层次的设置当作另一个层次的修复手段。

## 工程实施步骤

1. 记录源系统、文件/事件形态、业务键、事件时间、到达时间和批次标识。

## 常见误区

- **误区：** 把 TARGET_LAG 当成保证每次刷新都按固定间隔完成的 SLA。
  **纠正：** 新鲜度目标不是固定运行周期或无条件 SLA。应结合刷新模式、依赖变化、资源消耗和实际刷新历史判断是否满足业务要求。
- **误区：** 认为 Dynamic Tables、Materialized Views、Tasks 和 dbt 可以互相完全替代。
  **纠正：** 调度成功只说明执行器完成触发，不代表业务数据已正确交付。还要检查依赖、执行身份、重叠运行、失败重试、下游可见性和数据质量。
- **误区：** 只监控任务成功与否，不监控刷新模式、实际延迟和成本变化。
  **纠正：** 新鲜度目标不是固定运行周期或无条件 SLA。应结合刷新模式、依赖变化、资源消耗和实际刷新历史判断是否满足业务要求。
- **误区：** 在整个多层管道给每个中间层设置互相独立的时间目标。
  **纠正：** 新鲜度目标不是固定运行周期或无条件 SLA。应结合刷新模式、依赖变化、资源消耗和实际刷新历史判断是否满足业务要求。
