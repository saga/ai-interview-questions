# Snowflake Feature Store 特征管理

## 本节要解决的问题

信用卡风控团队训练一个交易欺诈模型。训练数据里有 customer_id、交易金额和交易结果；模型还需要“客户最近 7 天成功交易次数”“最近 7 天拒付次数”等历史特征。

最初的做法是在训练 SQL 中临时计算这些字段，线上推理又由服务代码重新实现一遍。两套逻辑逐渐不一致：训练时统计最近 7 天，线上却只查最近 24 小时；训练数据使用了交易发生之后才到达的拒付结果，离线指标很好，上线后效果明显下降。

Feature Store 解决的是特征定义、实体关联、版本、刷新和训练/推理复用问题。它不会自动判断特征有没有业务意义，也不会替团队消除未来信息泄漏。时间语义和训练样本的观察时点仍然需要设计。

## 核心知识

### Entity 定义特征属于谁，Feature View 定义如何计算

实体（Entity）是特征关联的业务对象，例如 CUSTOMER、ACCOUNT 或 DEVICE。它通过 join key 将来源数据关联到同一个实体。实体不是某张物理表的别名；一个实体可以被多个 Feature View 复用。

Feature View 描述一组特征的生成查询、关联实体、时间列和刷新配置。以客户为例：

| 对象 | 例子 | 作用 |
|---|---|---|
| Entity | CUSTOMER，键为 CUSTOMER_ID | 确定特征关联的客户 |
| Feature View | CUSTOMER_TXN_7D | 计算客户近期交易特征 |
| Feature View Version | v1 | 固定特征定义版本 |
| 特征列 | TXN_COUNT_7D、DECLINE_COUNT_7D | 模型实际使用的输入 |

一个客户可以有多条交易记录，但一份客户级特征快照在同一时点应只有一个客户键。若数据粒度是“客户 × 特征时间”，就不能只用 CUSTOMER_ID 作为唯一粒度而忽略时间列。

### 特征必须按模型做判断时已经可见的数据计算

假设交易在 11 月 10 日 10:00 到达，欺诈标签在 11 月 12 日才确认。模型在 11 月 10 日做决策时，不可能知道 11 月 12 日的拒付结果。

因此，特征要定义两个时间概念：

- 事件时间：业务事件实际发生的时间。
- 特征可用时间：该信息进入系统、可被模型使用的时间。

若只按事件时间回看，延迟到达的记录可能被错误地放进历史特征。风控模型需要根据实际可用时间定义截止点，确保训练样本只看到当时已可用的数据。

以交易 t 为例，“最近 7 天成功交易额”应只包含在 t 的决策时点之前已经可用的交易，排除当前交易之后的记录，也不能把事后确认的拒付标签放进特征。

### Feature View 的时间列和训练样本时间轴共同决定 point-in-time correctness

训练数据通常有一张 spine：每行对应一个实体在某个预测时点的样本，以及该样本的 label。Feature Store 可以根据 spine 的时间列和 Feature View 的时间列，为每个训练样本匹配当时可用的特征。

示意结构：

| CUSTOMER_ID | EVENT_TS | LABEL |
|---|---|---:|
| C01 | 2026-11-10 10:00 | 0 |
| C02 | 2026-11-10 10:15 | 1 |

特征快照：

| CUSTOMER_ID | FEATURE_TS | TXN_COUNT_7D |
|---|---|---:|
| C01 | 2026-11-10 09:00 | 4 |
| C01 | 2026-11-10 11:00 | 5 |
| C02 | 2026-11-10 09:30 | 8 |

对于 C01 在 10:00 的训练样本，应匹配 09:00 的特征快照，不应取 11:00 的值。后者包含预测时点之后的信息。

使用 Snowpark Feature Store API 生成训练数据时，time-series Feature View 需要时间列；训练样本通过 spine_timestamp_col 指定观察时点：

~~~python
training_set = feature_store.generate_training_set(
    spine_df=training_spine,
    features=[registered_customer_features],
    spine_timestamp_col="EVENT_TS",
    spine_label_cols=["LABEL"],
)
~~~

生成后仍要抽查样本：选择几位客户和预测时点，独立 SQL 重算当时应该可见的特征，并与训练集逐项对账。API 调用成功并不证明时间语义正确。

### 版本、刷新与历史保留是不同问题

Feature View 注册后带有版本标识，定义变更应发布新版本并记录训练任务使用的版本。这样才能解释模型 v3 为什么使用了不同的特征定义。

刷新模式决定特征数据如何更新。增量可维护的查询可以降低重复计算；若查询不能增量维护，可能需要 FULL refresh，刷新延迟和 Warehouse 成本会明显不同。不能仅凭配置了 refresh frequency 就认定数据一定按时更新，仍要监控实际刷新状态和最后成功时间。

历史保留也要单独设计。只保留最新特征值不足以重建过去某个预测时点的输入；需要完整历史快照时，应评估 append-only Feature View 或独立历史快照方案。Snowflake 的 append-only 模式可以保留每次刷新产生的特征快照，并供训练集按 spine 时间做 ASOF 匹配，但要考虑存储量、刷新频率和备份来源。

## 工程实施步骤

1. 先定义模型预测时点和标签确认时点，明确哪些字段在预测时可用，哪些字段会在事后产生。
2. 为 CUSTOMER、ACCOUNT、DEVICE 等实体选定稳定 join key，检查空键、重复键和跨系统映射。
3. 为每组特征明确粒度、计算窗口、事件时间、可用时间和空值语义；不要把不同实体粒度混在一个 Feature View。
4. 将特征查询实现为 Snowpark DataFrame 或 SQL，确认 Feature View 中包含实体 join key；时间序列特征还要提供时间列。
5. 注册 Feature View 并使用明确版本；在版本变更时记录变更原因、输入列、输出列和影响模型。
6. 为训练样本建立包含 entity、预测时间和 label 的 spine，使用 spine_timestamp_col 生成训练数据。
7. 用独立 SQL 复算抽样训练行，检查 ASOF 匹配到的快照不晚于预测时点，且没有未来标签或未来事件进入特征。
8. 对刷新延迟、行数、键唯一性、NULL 比例、特征分布和最后成功时间设置监控。
9. 线上推理复用相同的实体键和特征定义；若启用在线 Feature Group/Store，确认它与训练所用特征集合和版本一致。
10. 将特征定义版本、训练集版本、模型版本和部署版本关联记录，确保可以重现模型输入。

## 场景分析

客户 C01 在 10:00 发起一笔 500 元交易。系统在 10:00:01 收到交易，在 10:04 才收到一笔 09:30 的历史交易，在第二天才收到这笔交易是否拒付的标签。

模型在 10:00:01 决策时，不能使用 10:04 才到达的历史记录，也不能使用第二天才确认的拒付标签。若训练 SQL 只按 EVENT_TS 过滤，10:04 到达的迟到交易可能被回填进 C01 的 10:00:01 训练特征，造成训练与线上可见数据不一致。

解决前要决定“可用时间”是否进入特征数据模型。若它影响模型在某一时点能否看到记录，就必须保留并参与筛选。之后使用同一套规则生成训练样本，再对线上请求执行相同特征逻辑。抽样对账应同时检查事件时间和可用时间，不能只核对 customer_id。

## 常见误区

- **把 Entity 当成物理表。** Entity 定义业务键和复用边界；物理数据源可以来自多张表。
- **认为 Feature View 注册后就自动保证特征正确。** 它固定计算定义，不替你校验业务含义、时间窗口或训练标签。
- **只按事件时间做历史回看。** 延迟到达的数据可能在当时尚不可见，需评估可用时间。
- **只保留最新特征快照，却要求重建多年以前的训练输入。** 历史训练需要相应的历史快照或可重建来源。
- **把刷新频率当作新鲜度 SLA。** 还要看实际刷新时长、失败和最后成功时间。
- **认为训练和线上使用相似 SQL 就能避免 skew。** 应复用同一特征定义和版本，并对离线训练行与线上特征返回做抽样对账。

## 完成标准

- [ ] 能区分 Entity、Feature View、版本和特征列。
- [ ] 能为特征定义实体键、粒度、事件时间和可用时间。
- [ ] 能解释 spine_timestamp_col 在历史训练数据生成中的作用。
- [ ] 能识别迟到数据和事后标签造成的未来信息泄漏。
- [ ] 能说明最新快照与历史快照对训练重现的差异。
- [ ] 能监控刷新、质量、特征分布和训练/推理一致性。

## 自测

1. C01 的训练样本时点是 10:00，10:04 才到达一笔 EVENT_TS 为 09:30 的交易。仅按 EVENT_TS 筛选会产生什么问题？还需要哪个时间字段？
2. spine 中同一客户有 10:00 和 11:00 两个预测样本，为什么不能对两个样本都使用 11:00 的最新特征值？
3. 某 Feature View 的查询不支持增量维护，配置的刷新周期却很短。上线前要验证哪些刷新和成本指标？
4. 训练阶段使用 Feature View v1，线上已切换为 v2。即使列名相同，为什么也不能假定训练/推理一致？
