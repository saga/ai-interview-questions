# 微分区、缓存与查询优化服务

## 微分区与裁剪

Snowflake 在加载数据时自动组织微分区，并维护列级统计元数据。优化器可以据此判断某些微分区是否可能包含查询所需的数据，从而跳过不相关的数据范围，这就是 micro-partition pruning。

分区裁剪依赖谓词、数据分布和元数据。对时间范围、常见过滤列和连接键的组织方式会影响裁剪机会。不要把微分区理解成用户手工创建的传统索引，也不要仅通过增加集群数解决扫描量过大的问题。

## Clustering 的适用边界

Clustering Key 可以帮助高规模、过滤模式稳定且自然数据组织不理想的表改善微分区重叠情况。它并非每张表都需要；自动聚类会消耗 Credits，也需要观察查询收益、DML 模式、数据规模和维护成本。

先通过 Query Profile 判断扫描是否为瓶颈，再看微分区扫描比例、分区重叠和常用谓词。对于小表、低频表或查询模式不稳定的表，手工维护聚类往往得不偿失。

## 缓存不是一种东西

Snowflake 有不同层次的缓存和元数据优化，例如结果缓存、Warehouse 本地缓存和元数据相关优化。它们命中条件与生命周期并不相同。Warehouse 暂停可能影响本地缓存保留，不代表持久化数据丢失；结果缓存是否可复用则取决于查询和数据状态等条件。

性能基准测试必须说明缓存状态、Warehouse 规模、并发、查询文本、数据变化和运行次数，否则很容易把缓存命中误判成 SQL 优化收益。

## 其他查询优化服务

| 能力 | 更适合解决的问题 | 需要验证 |
|---|---|---|
| Search Optimization Service | 高选择性点查或特定访问模式 | 服务成本与查询延迟 |
| Query Acceleration Service | 部分可加速的扫描密集型查询 | 查询类型、加速比例、费用 |
| Materialized View | 高频重复的可物化查询结果 | 维护成本与查询收益 |
| Warehouse Resize | 单次查询计算资源不足 | 算子耗时和 Credits |
| Multi-cluster | 并发排队 | 排队时间和吞吐量 |

## 用 Query Profile 找瓶颈

先区分扫描、Join、聚合、排序、数据交换和排队耗时。若扫描量大，检查过滤谓词和分区裁剪；若 Join 膨胀，检查键唯一性与粒度；若排队，检查并发和 Warehouse 配置；若单算子计算时间高，再评估 SQL、Warehouse 和加速服务。
