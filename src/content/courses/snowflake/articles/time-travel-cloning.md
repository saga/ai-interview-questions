# Time Travel、零拷贝克隆与数据恢复窗口

## 本节要解决的问题

正确使用 Time Travel 查询历史状态、恢复误删对象和创建隔离测试副本，并理解保留期、Fail-safe 和长期业务历史存储的边界。Time Travel 是有时间窗口的恢复能力，不是长期归档系统。

## 核心知识

### Time Travel 能力受数据保留期限制

Snowflake 在数据被修改或对象被删除后，可以在对象配置的数据保留期内访问历史状态。可用于历史查询、创建历史时点的克隆和恢复被删除对象。保留期通过 \`DATA_RETENTION_TIME_IN_DAYS\` 等对象参数控制，实际可配置范围取决于账户 Edition 和对象类型。

Standard Edition 的默认保留期为 1 天，允许配置为 0 或恢复默认值；Enterprise Edition 及更高版本对永久表可配置更长保留期，最长可达 90 天。临时表和 transient 对象有不同的限制，应在设计时按对象类型核对。

保留期结束后，历史数据进入 Fail-safe 生命周期。Fail-safe 不是用户可查询的历史层，也不应作为日常恢复和业务归档方案。

### Zero-copy Clone 初始共享微分区

克隆表、Schema 或 Database 时，Snowflake 可以让新对象初始共享原对象已有的微分区，因此创建测试副本通常不需要立即复制全部数据。之后原对象和克隆对象的更新彼此独立；新写入或修改产生的微分区会形成独立存储并计入相应生命周期的存储成本。

所以“零拷贝”描述的是克隆创建时的存储共享方式，不意味着克隆永远没有额外存储成本，也不等于克隆对象会与原对象持续同步。

### 业务历史需要独立的数据保留设计

Time Travel 面向有限窗口内的恢复和历史访问；多年审计、财务追溯、有效时间分析和跨系统对账通常需要单独的历史模型、归档存储和保留策略。业务历史还需要明确修订、迟到数据、删除、权限和法规保留要求。

## 工程实施步骤

1. **确定恢复目标。** 区分误删对象恢复、某个时间点查询、测试环境克隆和多年业务历史留存。不同目标不要共用一个保留策略。
2. **盘点对象类型和保留参数。** 检查永久、临时和 transient 对象的保留能力及账户 Edition；用 SHOW/DESCRIBE 和对象参数确认实际配置。
3. **在恢复前记录时间点。** 保存事故发现时间、预计误操作时间、对象全限定名、影响范围和预期恢复边界。
4. **先在隔离环境验证。** 使用 Time Travel 查询或 Clone 还原目标时间点，检查行数、关键业务汇总、Schema、依赖视图和下游任务。
5. **评估恢复影响。** 判断恢复整个表是否会覆盖事故后合法写入；必要时先提取历史差异，再通过受控 DML 合并回生产。
6. **监控克隆生命周期。** 记录克隆用途、Owner、创建时间、预计销毁时间和测试结束后的清理动作；长期保留的克隆可能持续产生独立数据存储。
7. **单独设计长期历史。** 按业务主键、有效时间、事件时间、版本和来源记录构建历史表或归档；定义回补、对账、访问与保留期限。
8. **演练恢复。** 定期演示误删对象恢复、时间点查询和克隆清理，验证操作人员、角色权限和恢复窗口。

示例：查询某个时间点的表状态，并基于该时间点创建隔离副本。时间戳应替换为已确认的事故时间。

~~~sql
SELECT *
FROM PROD.SALES.ORDERS
  AT (TIMESTAMP => '2026-11-28 09:30:00'::TIMESTAMP);

CREATE TABLE DEV.SALES.ORDERS_RECOVERY
  CLONE PROD.SALES.ORDERS
  AT (TIMESTAMP => '2026-11-28 09:30:00'::TIMESTAMP);
~~~

## 场景分析

生产部署脚本误执行 DELETE，十分钟后才被发现。团队希望恢复订单表，但这十分钟内仍有正常订单进入系统。

直接把历史表整体覆盖回生产可能丢失事故后新增的合法订单。先在确认的时间点创建隔离克隆，比较克隆与当前生产表的业务键和状态，识别被误删的数据。然后在经过验证的补偿脚本中只恢复缺失记录，并处理唯一键冲突、后续状态更新和下游影响。

验收时比较恢复前后的订单数量、金额汇总、关键状态和下游数据；同时记录操作人、时间点、脚本版本及回滚方案。如果目标是长期审计历史，就应使用独立历史表或归档方案，而不是依赖 Time Travel 窗口。

## 常见误区

- **把 Time Travel 当永久历史仓库。** 它受对象保留期和 Edition 限制，超出窗口不能继续用普通 Time Travel 查询或克隆。
- **把 Fail-safe 当成用户可随时查询的备份。** Fail-safe 不替代可操作的备份和恢复流程。
- **认为 Zero-copy Clone 永远不增加存储。** 原对象和克隆对象后续修改会产生各自的微分区。
- **恢复时直接覆盖生产表。** 事故之后可能已有合法写入，应先隔离恢复并合并差异。
- **只做克隆而不清理。** 测试克隆要有 Owner、保留期限和清理策略。
