# PostgreSQL VACUUM、Autovacuum 与膨胀

## 本节要解决的问题

理解 MVCC 死元组清理、统计信息更新、可见性映射和事务 ID 回卷风险，诊断并调整日常维护而避免高风险重写。

PostgreSQL 数据库工程。依据 PostgreSQL 自身的事务、MVCC、WAL、索引、优化器和后台维护语义分析问题，不将 Snowflake 机制套用到 PostgreSQL。

本教程只对应知识点 `postgresql-vacuum-bloat`。目标是理解其机制、适用边界和验证方法，不把相邻知识点合并成一个大章。

## 核心知识

### 解释 UPDATE/DELETE 可能产生死元组以及 VACUUM 的作用

VACUUM 清理不再可见的行版本并维护可见性/统计信息；普通 VACUUM 通常释放内部可复用空间，不等于立即缩小操作系统文件。长事务和复制槽可能阻碍清理。

### 区分普通 VACUUM、VACUUM ANALYZE 与 VACUUM FULL 的锁和空间行为

并发问题应结合事务边界、快照、锁等待和错误码分析。先定位阻塞链及事务持有时间，再决定取消语句、终止会话或调整设计；重试前确认幂等性。

### 监控 autovacuum、表/索引膨胀、统计信息和 transaction ID wraparound 风险

先用执行计划和运行证据识别扫描、过滤、缓存、Join 或排队瓶颈，再考虑聚类、索引、加速服务或重写。优化要对比延迟、扫描量和费用。

## 常见误区

- **误区：** 认为普通 VACUUM 通常会立刻将文件大小归还操作系统
  **纠正：** 文件入口、文件解析和目标表写入必须分别验证。检查路径与文件清单、格式选项、列匹配、拒绝行、加载历史和目标行数；失败重跑前先确认之前是否已部分提交。
- **误区：** 认为 VACUUM FULL 可无阻塞地并行运行
  **纠正：** VACUUM 清理不再可见的行版本并维护可见性/统计信息；普通 VACUUM 通常释放内部可复用空间，不等于立即缩小操作系统文件。长事务和复制槽可能阻碍清理。
- **误区：** 关闭 autovacuum 后不会出现可见性或事务 ID 风险
  **纠正：** 并发问题应结合事务边界、快照、锁等待和错误码分析。先定位阻塞链及事务持有时间，再决定取消语句、终止会话或调整设计；重试前确认幂等性。
