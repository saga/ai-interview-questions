整体上，这个设计已经**比较成熟**，而且你已经主动控制了很多 over-design 风险。现在真正值得做的，不是再加能力，而是**砍掉几个“提前为 Phase 3/4 准备”的结构，同时修正 2～3 个边界问题**。

我会把它调整成一句话：

> **Domain 决策是核心，LLM 只是插件；Learner Memory 是核心状态；Agent 只存在于“需要连续对话”的场景。**

# 1. 最大的问题：现在其实有一点“架构超前”

目前有三套相对复杂的东西同时存在：

```text
Interview Engine
      │
      ├── Adaptive Strategy
      │
      ├── Concept Graph
      │
      └── pi-agent-core
             │
             └── future follow-up loop
```

再加上：

```text
Learner Memory
      │
      └── Coach / Recommendation
```

对于 **100 道题的个人 AI 面试教练 MVP**，已经接近一个“小型 learning platform”的架构了。

我建议明确分成：

### MVP 真正需要

```text
Question Bank
     ↓
Interview Engine
     ↓
Evaluation
     ↓
Learner Profile
     ↓
Next Recommendation
```

### Adaptive 是第二层

```text
Learner Profile
     ↓
Adaptive Strategy
     ↓
Next Question
```

### Agent 是第三层

```text
Interview Session
     ↓
Agent
     ↓
Follow-up / Challenge / Clarification
```

也就是说：

**不要让 Agent、Adaptive、Knowledge Graph 三者在 MVP 中互相耦合。**

# 2. 我最建议砍掉：10 类 Graph Edge

现在：

```text
prerequisite
part_of
extends
alternative
tradeoff
contrasts
related_to
technique
deep_dive
challenge
```

这个明显有一点 over-design。

因为你的系统真正使用 graph 做决策的地方其实只有：

```text
prerequisite
related_to
```

Adaptive 需要：

```text
deep-dive
→ 同 topic / prerequisite descendant

gap-probe
→ prerequisite

broaden
→ related topic
```

所以第一版完全可以：

```json
{
  "edges": [
    { "from": "tool-calling", "to": "mcp", "type": "prerequisite" },
    { "from": "mcp", "to": "agent-routing", "type": "related" }
  ]
}
```

甚至我会建议：

```text
Graph

prerequisite
related
```

就够了。

以后真的出现：

```text
tradeoff
alternative
contrasts
```

再增加。

### 更重要的是

你现在用 `@dagrejs/graphlib` 做：

```text
isAcyclic
topsort
prerequisiteClosure
```

技术上没问题，但对于你这个规模，我甚至会考虑**不用 graphlib**。

100 个 topic，几十到几百条 edge：

```ts
Map<TopicId, TopicId[]>
```

就可以完成：

```ts
getPrerequisites()
getRelatedTopics()
getClosure()
topologicalSort()
```

Graphlib 最大的价值其实是**通用图 API**，而你的 domain 实际上只有一个非常简单的 prerequisite DAG。

所以：

> **conceptGraph 可以保留，但不要让 graph library 成为架构核心。**

# 3. Adaptive Strategy 现在已经够了，不要再 Agent 化

这一部分：

```text

```

我认为非常合理。

尤其是：

```text

    ↓

    ↓
```

你文档里已经写了：

> Contradiction Probe 与 LLM 策略 Agent 是后续演进方向

我建议甚至把这个从架构设计中降级成：

```text

```

不要让它看起来像当前 architecture 的一部分。

# 4. pi-agent-core 其实可以再收缩

这是我认为第二个最值得调整的地方。

现在：

```text
InterviewAgent
   ↓
pi-agent-core
   ↓
pi-ai
```

但你目前 Agent 做的事情实际上是：

```text
prompt()
↓
stream
↓
拼接 text
↓
parseEvaluation()
↓
EvaluationResult
```

这其实**不需要 Agent**。

如果当前没有：

```text
面试官：
你提到了 MCP，为什么不用 function calling？

用户：
因为……

面试官：
那如果 tool schema 变化呢？

用户：
……
```

这种真正的多轮状态交互，那么：

```ts
pi-ai → evaluate()
```

已经足够。

---

### 普通训练

```text

        ↓
      pi-ai
```

### 真正的模拟面试

```text

       ↓
InterviewAgent
       ↓
pi-agent-core
       ↓
pi-ai
```

也就是说：

```text

 └── pi-ai

Mock Interview
 └── pi-agent-core
```

而不是：

```text
所有开放题
   ↓
pi-agent-core
```

这会让架构非常干净。

# 6. 有一个比“架构复杂”更重要的问题：Variant 的答案安全性

这里我觉得需要修改。

你现在写：

> 选择题：options 长度须一致、answer 索引在 [0,len)

这个**不够安全**。

例如原题：

```text
Q: MCP 是什么？

A. Model Context Protocol
B. Model Control Process
C. ...
D. ...
```

LLM 生成：

```text
A. Model Control Process
B. Model Context Protocol
C. ...
D. ...
```

如果：

```text
answer = 0
```

就出事故了。

---

## 更简单可靠的办法

不要让 LLM 修改 choice options。

也就是：

```text
Canonical Question
      │
      ├── question stem → LLM rewrite
      │
      ├── options ────── unchanged
      │
      └── answer ─────── unchanged
```

例如：

```json
{
  "question": "在一个多工具 Agent 中……",
  "options": [...原题...],
  "answer": [1]
}
```

LLM 只负责：

```json
{
  "question": "如果一个 Agent 同时拥有 20 个工具……"
}
```

这样你所谓：

> LLM 只改表达

才真正成立。

# 7. Open question 的 validate 也太弱

你现在：

```text
开放题：
题干非空即可
```

实际上这里风险比 choice 更高。

例如 canonical：

> 为什么 Agent 应该使用 structured tool calling？

LLM 可能生成：

> 为什么 Agent 应该使用 MCP？

两个问题相关，但**不是同一道题**。

所以至少应该有：

```json
{
  "sourceQuestionId": "agent-042",
  "question": "...",
  "preservedTopics": ["structured-output", "tool-calling"]
}
```

然后 validation：

```text
sourceQuestionId 必须存在
topic 必须保持
question 非空
question 不能泄漏答案
```

不过这里**不要为了安全再搞一个 LLM judge**。

MVP：

```text
topic/tags 不允许改变
referenceAnswer 不允许改变
```

已经足够。

# 8. `EvaluationResult` 有一个小矛盾

你写：

> 综合分由 `aggregateOverall` 计算；LLM 也可直出 overall（优先使用）。

我建议不要这样。

否则：

```text

40 + 20 + 20 + 20 = 83

LLM：

```

到底哪个是真实分？

应该固定：

```text

             ↓

             ↓
overall
```

也就是：

> **LLM 不拥有最终分数，Domain 拥有最终分数。**

这和你最前面的原则：

> LLM 是 enhancement layer

是一致的。

# 10. Learner Memory 方向非常对，但可以再简单

你现在：

```text

```

已经比较丰富。

我会保留：

```ts
TopicStats {
  attempts
  avgScore
  mastery
  trend
  weaknesses
}
```

但 `mastery = avgScore × confidence factor` 可以先简单一点。

例如：

```text

```

然后：

```text

→ low confidence

→ normal
```

UI 可以显示：

```text

↑ improving
```

而不是让 mastery 算法本身变成一个研究项目。

```text
                  │   Application   │
```

## 最重要的一点

你这个项目现在其实已经找到了一个**非常好的核心架构原则**：

```text
                ┌────────────────────┐
                │   Question Bank    │
                │  Source of Truth   │
                └─────────┬──────────┘
                          │
                          ▼
                 ┌────────────────┐
                 │ Interview      │
                 │ Domain         │
                 │                │
                 │ Quiz           │
                 │ Adaptive       │
                 │ Learner        │
                 └───────┬────────┘
                         │
              ┌──────────┴──────────┐
              ▼                     ▼
          ┌────────┐          ┌────────────┐
          │ pi-ai  │          │ pi-agent   │
          │enhance │          │ conversation│
          └────────┘          └────────────┘
```

**Domain 决定“训练什么、怎么评分、下一题是什么、用户哪里薄弱”；LLM 只负责“生成表达、评价开放答案、进行真正的对话”。**

这比继续增加 Agent、Graph、Memory 的智能程度更重要。

如果按这个原则继续收敛，我认为你现在的设计已经**不需要再引入新的框架**了；下一步的重点应该从“架构能力”转到**题库质量 + Learner Memory 的推荐效果 + LLM 评分质量**。这三者才真正决定这个产品好不好用。
