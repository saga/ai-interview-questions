## 3. P1：建议在生产前优先处理

### P1-1：Cloudflare 代理存在 protocol-relative URL host override，可能变成 SSRF / 任意 HTTPS 转发

**证据**

- `server/index.js:35-39`：把 `/api/ai` 前缀剥掉后直接执行 `new URL(stripped, 'https://api.cloudflare.com')`。
- `worker/index.ts:24-36`：同样直接把剥掉的 path 交给 `new URL()`。
- 已实测：

```text
new URL('//example.com/p', 'https://api.cloudflare.com')
=> https://example.com/p
```

因此请求 `/api/ai//example.com/p` 时，`stripped` 以 `//` 开头，会覆盖原本固定的 `api.cloudflare.com` 主机。代理同时转发请求头，可能把它变成公开 SSRF / open relay；Node 服务默认监听所有接口，部署在公网或局域网时风险更高。

**影响**

- 攻击者可利用代理访问任意 HTTPS 主机，而不是只能访问 Cloudflare。
- Node 代理还原样转发 `Authorization` 等请求头；Worker 也属于公开入口。
- 这不是单纯的 CORS 问题，而是目标主机约束失效。

**建议**

- 先拒绝剥前缀后以 `//` 开头的路径，并规范化为单一 `/`。
- 构造 URL 后强制断言 `url.protocol === 'https:' && url.hostname === 'api.cloudflare.com'`，不满足立即返回 400。
- 代理增加 body 大小上限、超时/AbortSignal、速率限制；Node 生产部署限制监听地址或增加鉴权。
- 为 Node 与 Worker 各加一个 `//attacker.example` 回归测试。

### P1-2：Agent 结束流程不是幂等的，可能重复落库或结束后又恢复草稿

**证据**

- `src/hooks/useAgentInterview.ts:142-157`：`finalize()` 没有 `finalized` 守卫；它直接调用 `onComplete(record)`，但 `onComplete` 类型是同步 `void`。
- `src/hooks/useAgentInterview.ts:205-209`、`369-373`：收到 `finished` 时先 `void deleteAgentSession()` 再 `finalize()`。
- `src/agent/interviewAgent.ts:226-233`、`:248-259`、`:273-282`：达到上限、工具结束、`agent_end`/兜底收尾都可能触发结束回调；`finishInterview` 工具本身又会设置 `session.status = 'finished'`。
- `src/hooks/useAgentInterview.ts:286-305`：提交完成后无条件 `void persistDraft()`；如果结束路径没有同步把 `session.status` 设成 `finished`，该调用会把已完成会话重新写回草稿。
- `src/hooks/useAgentInterview.ts:308-314`：`endEarly()` 直接 `finalize()`，没有统一设置 finished 状态或删除草稿。

**影响**

- 同一场面试可能触发两次 `onComplete`，导致 Learner Memory 重复累计。
- 完成后草稿可能被再次保存，刷新页面仍显示可续面。
- 结束条件来自多个路径，当前不是单一、幂等的状态机。

**建议**

- 抽出唯一的 `finishSession(reason)`：使用 `finishedRef`/session status 做幂等保护；先停止 Agent，再等待持久化成功，最后删除草稿并切到 done。
- 所有结束路径（`finishInterview`、达到上限、题库耗尽、用户提前结束、fatal error）统一走它。
- `onComplete` 改为 `Promise<void>` 并由 `finalize` await；持久化失败时保留草稿并提供重试，而不是先显示成功。
- 结束后的任何 `persistDraft` 都必须被拒绝。

### P1-3：真实 id 直传绕过了去重保护；搜索结果又没有排除已交付题

**证据**

- `src/agent/tools.ts:171-172`：`byId.get(params.id)` 命中真实 id 后直接继续，没有检查 `isDelivered(session, q.id)`。
- `isDelivered()` 只用于 topic 兜底和纠错候选，不保护 direct-id 分支。
- `src/agent/tools.ts:123-137`：`searchQuestions` 每次从 `pool.slice(0, limit)` 返回固定的前 N 道题，没有 `exclude delivered`、cursor 或随机/分页。

**触发场景**

- Agent 再次调用一个已经作答/评分/当前正在展示的真实 id。
- Agent 每轮默认搜索前 10 道，前几道被考过后仍返回同一批候选。

**影响**

- 相同 question id 可能重新生成变体、覆盖答案/评分，`questions` UI 列表虽然按 id 去重，但会话状态发生覆盖。
- Agent 可能在前 N 道题耗尽后反复搜索同一列表，进入重复出题或纠错循环；兜底引擎只能在某些路径接管。

**建议**

- direct id 命中已交付题时返回明确 `already_delivered`，不要再次设置 `currentQuestion`。
- `searchQuestions` 默认过滤已交付题，或提供稳定的 `offset/cursor`；候选应至少保证有一批未交付题。
- 加测试覆盖：当前题、已作答、`evaluations[id] = null`、搜索前 N 已耗尽四种情况。

### P1-4：pi-agent-core 默认并行执行工具，但工具共享可变 session

**证据**

- 已安装依赖 `node_modules/@earendil-works/pi-agent-core/dist/agent.js` 明确显示：`runtimeOptions.toolExecution ?? "parallel"`。
- `src/agent/interviewAgent.ts:127-135` 构造 `Agent` 时没有设置 `toolExecution: 'sequential'`。
- `src/agent/tools.ts` 的工具会读写同一对象：`currentQuestion`、`answers`、`evaluations`、`lastSearchIds`、`status`、`log`。

**影响**

- 同一 assistant message 中若产生多个工具调用，`searchQuestions`、`getQuestion`、`evaluateAnswer`、`finishInterview` 可能竞态。
- 两个 `getQuestion` 可以互相覆盖当前题；`finishInterview` 可能和另一个变更工具并行执行；`lastSearchIds` 可能被后一个搜索覆盖。
- 现有单测主要是单工具串行脚本，无法捕获此问题。

**建议**

- Agent 全局设置 `toolExecution: 'sequential'`。
- 额外在工具层做 session finished guard，并限制每个 turn 最多一个会改变面试状态的工具。
- 加一个多 tool-call 回归测试，确认只会交付一道题且结束后不会再写状态。

### P1-5：LLM 评估异常可能被降级成合法的 0 分

**证据**

- `src/ai/pi.ts:136-156` 只取 `res.content` 的 text，没有检查 `res.stopReason === 'error'` / `errorMessage`。
- `src/ai/evaluate.ts:107-118`：空文本直接构造成 `overall: 0`、`feedback: '未作答。'`。
- `src/ai/evaluate.ts:120-156`：JSON 能解析但结构残缺时，`safeParse` 失败后使用 `{}`，四个维度全部按 level 0 继续聚合。
- `src/application/interviewEngine.ts:125-136` 只有 Promise reject 才会 catch 成 `null`；已经返回 0 的情况不会进入失败分支。
- 现有 `src/ai/evaluate.test.ts:91-97` 还把残缺 JSON → 缺失维度 0 分固定为正确行为。

**影响**

- 网络/鉴权/Provider 异常会污染 `overallScore`、topic mastery、weakness 与后续推荐。
- 模型返回半截 JSON 与候选人真正未作答被混成同一种 0 分。

**建议**

- 在 pi adapter 先检查 stop reason；transport/provider error 应抛出带类型的错误。
- 对结构校验失败不要静默 `{}`；返回 typed evaluation failure 或 `null`，并记录可诊断原因。
- 仅用户明确提交空答案时才使用“未作答”的 0 分内部结果；未评分结果不进入 Learner Memory。
- 先改测试契约，再改实现，避免旧测试阻挡正确修复。

### P1-6：Variant 的 presentation format 与当前 Session format 脱节

**证据**

- `src/application/sessionEvaluator.ts:59-71`：`finalizeQuestion()` 只把 `sq.question` 传入 `provider.generateVariant()`，没有传 `sq.format`。

### P1-7：Variant semantic gate 允许“解析里提到概念”替代“题目实际考察概念”

**证据**

- `src/domain/variant.ts:26-62`：`hasConceptEvidence` 把 `question + options + explanation` 拼成一个文本，只要任一 anchor/token 命中就返回 true。
- `src/domain/variant.ts:124-128`：注释明确是“任一明显证据”即可通过。
- `VARIANT_SYSTEM` 的要求却是 `requiredConcepts` 必须实际被考察，而不仅仅在解析中出现。

**影响**

- 变体题干/选项已经漂移到别的知识点，但生成的 explanation 仍然把原概念写进去时，仍可能通过 gate。
- 多个 required points 只命中一个就放行，Knowledge Contract 实际被弱化为“有一点相关词”。

**建议**

- assessment evidence 只从题干与选项计算，不把 explanation 作为知识保留证据。
- 对 required points 做可解释覆盖率（例如至少覆盖合理比例），而不是 any-match；长句允许 token/fuzzy paraphrase，但要记录命中项。
- 将 semantic gate 的失败原因/命中概念写入测试与日志，便于离线审查。

### P1-8：候选人答案可注入 Agent 控制流和评分 prompt

**证据**

- `src/agent/interviewAgent.ts:291-302`：答案原样追加为 `UserMessage`，没有数据围栏或“不把内容当指令”的来源声明。
- `src/ai/chromeAgent.ts:91-113`：Chrome replay 将它渲染成 `User: ...`，并同时渲染类似 `Assistant tool ...` 的历史文本；伪造工具轨迹的答案会和真实 transcript 外观接近。

**影响**

- 恶意或误写的答案可能诱导 Agent 提前结束、调用错误工具、泄露信息或改变评分。
- 评分结果可能影响持久化 Learner Memory，形成长期污染。

- 设定输入大小上限并在 UI 明确提示超长处理策略。

### P1-9：Native Agent 没有 context budget；Chrome 与评分路径对同一答案处理不一致

**证据**

- `src/agent/interviewAgent.ts:297-302`：每次提交都 append 原始答案，未配置 `transformContext` 或 compaction；`persistDraft()` 还把完整 messages 写入 IndexedDB。
- `src/ai/chromeAgent.ts:84-118`：Chrome 只保留最近 10 条消息，每条静默截断到 900 字符。
- `src/components/quiz/QuestionCard.tsx:167-193`：普通开放题 TextArea/CodeEditor 没有输入长度预算。
- 评估路径 `evaluateOpenAnswer` 接收完整回答，而 Chrome Agent 决策可能只看到被截断的回答。

**影响**

- 长代码/长文本会让 native Agent 的每轮输入和草稿持续膨胀，触及模型 context window 或增加成本。

**建议**

- 为 answer、tool result、transcript 统一定义 token/字符预算；超限时显式提示或做确定性摘要，不要静默截断。
- Native path 加 bounded context transform；持久化只保存可恢复的必要状态，不无限保存历史。
- Chrome 与 native 使用同一份“当前状态摘要”，而不是各自实现不同的 history 截断。

- `src/hooks/useAgentInterview.ts:166-174` 与 `:203`、`:279`、`:298` 多处 fire-and-forget `saveAgentSession`，没有串行队列或版本比较。

**影响**

- restart/unmount 后旧 Agent 仍可能继续请求、触发旧 handlers、更新已离开的界面；90 秒 watchdog 也可能晚到。
- 多个草稿保存同时进行时，较旧快照可能后完成并覆盖较新快照，刷新后丢失最后进度。

**建议**

- `dispose()` 语义应包含 abort + clearWatchdog + unsubscribe；所有 UI cleanup 都只调用这一处。
- 草稿保存使用串行 promise queue 或 compare-and-swap（只接受更大的 revision/updatedAt）。
- 保存失败要进入可见错误/重试状态，而不是静默 fire-and-forget。

## 4. P2：需要治理，但不阻塞当前功能

### P2-1：题库与文档版本漂移，且未跟踪题库改变了当前运行事实

- `package.json` 已是 React 19 / antd 6.6.2，但 `README.md:5`、`docs/ARCHITECTURE.md:5` 仍写 React 18。
- README/架构文档写 1084 题、1078 双形态；当前校验（包含未跟踪 JSON）得到 1098 题，双形态比例也已变化。
- 当前分支有未跟踪的题库文件和 draft，说明“当前运行数据”和“可追溯提交数据”不一致。
- 建议把题库导入、临时 draft、文档更新放进明确的提交边界；题库规模尽量由脚本生成/校验，不在 README 手写易漂移数字。

### P2-2：Hook/异步状态机测试缺口明显

- `src/hooks/` 没有针对 `useTrainingSession` / `useAgentInterview` 的测试。
- 当前 413 个测试主要覆盖 domain、工具和适配层，关键的 React 时序（重复提交、结束竞态、恢复失败、保存失败、restart/unmount）没有直接守卫。
- 建议增加 hook/application integration tests，优先覆盖本报告 P1-2、P1-12。

### P2-3：Capability table 多数只是声明，尚未形成真正的 runtime policy

- `src/ai/capabilities.ts` 声明 `toolCalls`、`thinking`、`contextCaching`、`multiRound`。
- 实际调用路径主要只使用 `jsonMode`；`toolCalls`、`thinking`、`contextCaching`、`multiRound` 没有统一的运行时分流/校验。
- 这会让文档与能力表给人“已协商”的错觉。要么接通能力表，要么把它降级为 metadata，避免假抽象。

### P2-4：LLM 评估契约还有两个长期质量问题

- `src/ai/evaluate.ts:28-33` 对所有开放题都要求 `architecture` 维度；概念解释题不一定适合用架构质量评价，可能引入系统性偏差。
- `missingConcepts` 被模型输出并被 `parseEvaluation` 保留，但 `sessionFromQuiz()` 和 Learner 聚合只消费 `gaps`，没有把 `missingConcepts` 接入长期画像；如果它是正式契约，应明确落库/消费，否则应从输出契约删掉或标明实验字段。

### P2-5：公开代理缺少运维护栏

- `server/index.js:47-65` 读取并缓冲完整 request body、完整 upstream body，没有大小限制、超时、速率限制或 streaming response。
- `worker/index.ts` 虽然保留流式 body，但同样没有目标请求超时、调用配额或 abuse protection。
- 该服务若只在本机使用问题较小；若部署公网，应与 P1-1 一起修。

### P2-6：前端产物偏大

- 本次构建出现多个大 chunk：主 index 约 4.07 MB，Monaco editor API 约 2.65 MB，TypeScript worker 约 6.91 MB，并触发 Vite 的 500 kB 警告。
- 设置页/代码编辑器已有部分懒加载，但仍有较大基础包进入产物。建议查看 Rollup/Rolldown 分包、Monaco language worker 按需加载和首屏依赖边界。

### P2-7：题库质量门禁目前显示大量历史债务

- `question:audit`：349 个 P2；`lint:length`：254 题选项长度比超过 1.8×；`lint:bias`：122 题 strong 长度暗示。
- 单选 591 / 多选 507，单选 53.8%，仍明显偏离项目规定的多选占多数（目标单选 ≤33.3%）。
- 这些不是本轮代码引入的运行时 bug，但会降低训练测量质量；建议按新增题优先、历史题渐进改写，不要为了门禁一次性大批量自动改写。

### P2-8：Copilot 对话历史无预算

- `src/components/copilot/CopilotSidebar.tsx:148-218` 将完整 `messages` history 每次发送给模型，没有消息数量/字符/token 上限或摘要。
- 长时间打开 Copilot 会导致请求体、成本和延迟线性增长。建议与 Agent context 使用统一预算策略。

### P2-9：提交历史不可追溯

- 最近多个提交 message 为 `adddd`、`dddd`、`ddd` 等无语义文本，当前内容虽然可运行，但架构决策、题库变更和依赖升级难以审计。
- 由于这些提交已经在共享 `origin/main`，不建议在并行会话活跃时 force-push 重写；后续分支空闲时再统一治理，或者从现在开始使用语义化提交信息。

## 7. 最终结论

本项目的基本方向是对的：**知识/题库是事实源，Domain 负责确定性逻辑，LLM 只做变体、评分与不确定决策，Agent 通过工具推进流程**。现在最需要的不是增加更多 prompt 规则，而是把已经写进架构原则的状态和安全不变量真正下沉为代码护栏：

- 不能重复交付同一题；
- 不能并行修改共享 session；
- 不能把 Provider 异常当成 0 分；
- 不能在结束后继续保存或重复落库；
- 不能让代理 URL 绕过固定上游；
- 不能让长/恶意用户输入无边界进入模型上下文。

在完成第一批修复前，建议把 Agent 面试和公开代理视为“可用但不宜无护栏公开”的状态；完成后再继续优化 prompt、缓存和题库质量。
