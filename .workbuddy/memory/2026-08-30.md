## Cloudflare 部署命令坑（Pages vs Workers）
- 本项目是 Cloudflare **Pages** 项目：`wrangler.toml` 含 `pages_build_output_dir = "dist"`，无 `main` Worker 入口。
- 部署平台若把 Deploy command 配成 `npx wrangler deploy`（**Workers** 模式），会报 `Missing entry-point to Worker script or to assets directory`；Wrangler 也会警告 "run wrangler deploy on a Pages project, wrangler pages deploy should be used instead"。
- **正确命令**：`npx wrangler pages deploy dist`（仓库 `npm run deploy` 已是对的写法）。`pages_build_output_dir` 已设时，也可把 Deploy command 留空让 Pages 自动发布 `dist/`。
- 教训：`wrangler deploy` ≠ `wrangler pages deploy`。Pages 项目必须用 `pages deploy`。该命令是在 Cloudflare Pages 控制台 / 部署工具里配的，不在仓库文件中（仓库里 `package.json` 的 deploy 脚本已正确）。

## Cloudflare Workers AI 报 "Provider is not configured" 修复
- 症状：配置好 cloudflare-workers-ai（apiKey + accountId + 模型 `@cf/moonshotai/kimi-k2.6`）后调用仍报 `⚠️ 模型调用失败：Provider is not configured: cloudflare-workers-ai`。报错文案来自 `CopilotSidebar.tsx:74`，根因在 pi-ai 鉴权解析。
- 根因：`src/ai/pi.ts` 的 `callLLM` 与 `CopilotSidebar.tsx` 都调用 `models.complete(model, ctx, entry.apiKey.trim() ? { apiKey: entry.apiKey } : {})`。一旦传 `apiKey` 作为 override，pi-ai 的 `resolveProviderAuthWithSignal`（`auth/resolve.js:33`）会走「合成 credential」分支，构造 `{ type:'api_key', key: overrides.apiKey, env: overrides.env }`，而 `overrides.env` 为 `undefined` → 直接丢弃了内存 CredentialStore（`createCredentialStore`）里存好的 `CLOUDFLARE_ACCOUNT_ID`，导致 `resolveCloudflareEnv` 拿不到 accountId 返回 undefined → applyAuth 抛错。
- 关键细节：Cloudflare 的 accountId 只存在于 CredentialStore 的 `env`，且 cloudflare 模型 baseUrl 模板 `.../accounts/{CLOUDFLARE_ACCOUNT_ID}/ai/v1` 依赖该 env 填充。其他 provider（deepseek/openrouter/google/local）无此 env 依赖，所以之前没暴露。
- 修复：两处都改为 `models.complete(model, ctx, {})`，鉴权完全交给 CredentialStore（已按 provider 注入 apiKey/accountId）。`runtime.ts` 的 Agent 主流程本就用 `streamSimple` 不传 override，所以面试主流程之前就能调通，受损的是变体生成/开放题评分/挑战题（provider.ts→callLLM）和 Copilot 侧栏。
- 验证：写临时脚本拦截 fetch（不发真实请求），确认修复后请求 URL 为 `.../accounts/<accountId>/ai/v1/chat/completions`，accountId 正确模板化；apiKey 经 openai-completions 客户端 SDK 自动加 Authorization 头（与 deepseek 等一致）。typecheck 通过，ai+agent 测试 89 个全过。

## Cloudflare 浏览器直连报 "Connection error."（CORS）
- 现象：修好 "Provider is not configured" 后改报 `⚠️ 模型调用失败：Connection error.`。文案来自底层 OpenAI SDK 的 `APIConnectionError`（fetch 网络层失败）。
- 根因（已 curl 验证）：本项目是纯前端 SPA，无后端代理，AI 请求由浏览器直打 `api.cloudflare.com`。Cloudflare REST API **不返回 CORS 头**（OPTIONS 405 无 `access-control-allow-origin`；带 Origin 的 POST 401 也无 ACAO）→ 浏览器跨域拦截 fetch → "Connection error."。服务端 curl 不受 CORS 限制故能通（返回 401 鉴权错）。
- 决策：用户选 **AI Gateway** 方案。AI Gateway 地址（`https://gateway.ai.cloudflare.com/v1/<account_id>/<gateway_id>/workers-ai`）支持浏览器 CORS（控制台开启后）。
- 代码改动：
  1. `src/ai/pi.ts` 的 `getModel` 改为接收 `entry`，当 `entry.baseUrl` 非空时用它覆盖模型目录默认 baseUrl（去掉尾部斜杠）。
  2. 三个调用点（pi.ts `callLLM`、CopilotSidebar.tsx、agent/runtime.ts）改传 `getModel(models, entry)`。
  3. `SettingsPanel.tsx` 重新对 `cloudflare-workers-ai` 显示 Base URL 输入框（与 `local` 一起），placeholder 提示填 AI Gateway 地址（开启 CORS）。
- 鉴权：`cloudflareWorkersAIProvider` 用 `Authorization: Bearer <token>`，AI Gateway 接受该头（也支持 `cf-aig-authorization`）。accountId 仍需填写（auth.resolve 要求 apiKey+accountId 双字段，否则 "Provider is not configured"），但 gateway URL 已含 accountId 于路径、env 占位符不再使用。
- 用户侧操作：Cloudflare 控制台建 AI Gateway + 开启 CORS → 把 gateway URL 填进 Cloudflare 引擎的 Base URL → 保留 apiKey/accountId → 浏览器硬刷新。
- ⚠️ 安全：用户最早在对话里贴了真实 Cloudflare API Token，建议去控制台轮换/吊销。
- typecheck 通过，ai+agent+copilot 测试 89 个全过。

## build 失败修复（tsc -b 报 Cannot find name 'location'）
- 现象：`npm run build`(= `tsc -b && vite build`)报 `src/ai/pi.ts: Cannot find name 'location'`。`tsc -p tsconfig.app.json --noEmit` 单独编译 src 却通过——说明是 build 模式（app+node 两个项目）才触发。
