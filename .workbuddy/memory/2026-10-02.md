## 排查「#/agent 点击按钮没有反应」→ 修复（ADR-088）

用户报 `https://ai-interview-questions.dal.workers.dev/#/agent` 点按钮没反应。

### 排查过程（先证据、后结论）

1. **先确认按钮本身没坏。** 用 CDP 驱动本机 Chrome（`--headless=new` + `--remote-browser` 那套 flag）
   加载部署站点：按钮 `disabled=false`，点击后 `phase` 正常进入 running。
   **结论：不是按钮的问题，页面确实切过去了。**
2. **再排除「配置未就绪」闸。** `configReady` 用默认配置时为 true（`sample-config.json` 默认
   `chrome.enabled = true`，且 chrome 引擎无需 apiKey 即视为合法）；`profileReady` 由
   `useTrainingSession` 的加载 effect 保证会置真。两者都不是原因。
3. **看它到底卡在哪。** 点击后每 10s 快照，持续 220s：
   - 0–80s：一直停在「面试官正在选题…」，**0 条控制台输出、0 个网络请求**（说明根本没走到 LLM 调用）；
   - **~90s**：突然出现第一道题，之后正常。
   90s 这个数字直指 `interviewAgent.ts` 的 `WATCHDOG_MS = 90_000`。
4. **定位真凶。** 在页面里直接探 `LanguageModel`：Chrome 154 下 `typeof LanguageModel === 'function'`，
   但 `await LanguageModel.availability()` 返回 **`'downloadable'`**（on-device 模型没下载）。
   而 `chromeComplete` 的预检**只拦 `unavailable`**，于是放行 → `LanguageModel.create()` 挂起等
   数 GB 模型下载，既不 resolve 也不遵守 abort → 只能等看门狗。

### 修复

`chromeComplete` 改为**只有 `available` 才建 session**；`downloadable` / `downloading` 直接拒绝，
文案额外提示「先在 Chrome 中完成内置模型下载」。

**实测对比**（同一套脚本、全新 profile、默认配置）：修复前 ~90s 出题 → 修复后 **≤3s**。

### 关键教训

- **「点了没反应」未必是按钮问题，先分清「没触发」和「触发了但卡住」。**
  判据：看 `phase` / state 有没有变、控制台有没有输出、有没有网络请求。三者全静默 = 卡在
  某个 await 里，不是事件没绑上。
- **`availability()` 是个四值枚举（available / downloadable / downloading / unavailable），
  「非 unavailable 即可用」是错的判据。** `downloadable` / `downloading` 恰恰是最会长时挂起的
  状态——`create()` 会等模型下载完，且不遵守 abort。
- **默认配置里 `chrome.enabled = true`，所以这是默认路径，不是边缘 case。** 绝大多数用户没下载过
  Chrome 内置模型，装完就点必然撞上。
- 调试这类「静默挂起」时，**长窗口观察（>2 分钟）比短窗口有用**：只看前 25s 会误判成「永久卡死」，
  实际是 90s 后被看门狗救回。数字对上了（90s = `WATCHDOG_MS`）就基本能锁定代码位置。
- **没顺手改的地方**：`chromeAgent` 刻意把失败编码成 error 事件（不抛出）以便确定性护栏接管，
  代价是 Agent 主循环的引擎降级链对 chrome 入口实际不生效。这是已记录的设计取舍，改动需单独讨论，
  已写进 ADR-088 的「未改」。

## 去掉 Agent 面试页重复的「面试官思考中…」

忙碌态下同一句话渲染两遍：状态标签 + 遮罩转圈的 `tip`，两者出现条件完全相同
（`(busy || submitting) && !awaitingFeedback`）。

**保留状态标签，去掉转圈的 `tip`**（改裸 `<Spin />`）：状态行需要常驻槽位（三态互斥），
遮罩转圈本身已经是「在忙」的信号，不必复述原因。

**验证手法（可复用）**：忙碌态只持续几百毫秒，轮询抓不到。改用
**MutationObserver 在点击前安装**，逐次 DOM 变化记录「文案在 body 文本里出现的次数」，事后取最大值。
实测：旧写法 `×2` 且 `spinTip="面试官思考中…"`，新写法 `×1` 且 `spinTip=""`。

**★ 关键一步：先跑变异确认计数器非恒真。** 这种「次数应为 1」的断言很容易恒真（选择器没匹配到、
统计写错都会让它「通过」）。临时把旧写法还原、重新构建、再跑一次，确认确实报 `×2`，然后才恢复。
**否定式断言必须先证明它能失败。**

另外记一笔：`面试官思考中` 在 bundle 里仍有 2 处，第二处来自 `CopilotSidebar.tsx` 的侧栏
（另一个面板，默认不打开）——**按字面量 grep 计数不能直接当「同屏重复」的证据**，
要确认它们是否在同一屏。

## 「推理决策」显示裸工具调用 JSON（`{"tool":"getUserWeaknesses","args":{}}`）

用户报：卡片里出现这段 JSON，以「面试官推理」气泡样式渲染，零信息量且不该给用户看。

### ★ 根因：pi-agent-core 调 streamFn 时 **不传 systemPrompt / tools**

`agent-loop.js` 的 `streamAssistantResponse` 传的是
`normalizeContext({ messages: llmMessages })`，而 pi-ai 的 `normalizeContext`
把 systemPrompt + tools **折进开头的 system 消息**后**只返回 `{ messages }`**。

用最小 Agent 复现（`state.tools` 注入 + `initialState.systemPrompt`）打印实参：
```
streamFn context keys: [ 'messages' ]
context.tools = undefined        ← 关键
context.systemPrompt = undefined ← 关键
  [0] role=system content='SYSTEM PROMPT HERE'  toolsAdded=undefined
  [1] role=system content=''                    toolsAdded=2 tools: getUserWeaknesses,getQuestion
```
**工具定义在 `messages[1].toolsAdded` 里，system prompt 在 `messages[0].content` 里。**

→ `driveStream` 的 `new Set((context.tools ?? []).map(t => t.name))` 恒为空集合
→ `parseToolCall` 的 `allowed.has(name)` 永远为假 → `emitText(stream, raw)`
→ 工具调用协议原文被当 assistant 文本，`useAgentInterview` 收进 transcript → 渲染成推理气泡。

**连带发现（比显示问题更严重）**：`system` 只拼出了 `CHROME_TOOL_PROTOCOL`
（`context.systemPrompt ?? ''` 为空），**整段安全层 / 契约层一直没发给 Chrome**；
`buildUserPrompt` 的工具清单渲染成 `(no tools available)`。
而 `renderMessages` **没有 `system` 分支**，system 消息被静默跳过——两侧都没进 prompt。

### 修法

- 新增 `resolvePrompt(context)`：用 pi-ai 官方 replay helper
  `getCurrentSystemPrompt(messages)` / `getCurrentTools(messages)` 还原，
  保留 `context.* ??` 优先（上游改回直接传参就自动跟随）。
- 抽出 `src/ai/toolCallJson.ts`（`extractJsonObject` / `toolCallName` / `looksLikeToolCall`），
  解析层与展示层共用一份判据。
- `driveStream` 区分两类失败：**不像**工具调用 → 仍 `emitText`；**像**但不可用 → 发 **error**。
  原来「一律回落成文本」正是泄漏通道。
- `useAgentInterview` 落 transcript 前用同一判据过滤（展示层最后防线）。
- 补 `getWeakAngles` / `getCoverageGaps` 的中文标签（真实工具却漏在 `TOOL_LABELS` 外）。

### 验证

- `tsc`（app+node）+ `npm run build` 通过；全量 **888 passed / 888**（66 文件，+17 用例 / +1 文件）。
- **★ 新增用例先做变异验证**：把三处改回读 `context.*` → 新增用例**失败 4 项**；还原后全绿。
  （又一次印证「否定式/回归断言必须先证明它能失败」。）
- `chromeAgent.test.ts` 新增 `makeRuntimeContext()`，**显式复刻真实运行时形状**——
  原 `makeContext()` 显式带 `tools:`，正是这个 bug 逃过整套测试的原因。
- 已知限制：沙箱内 Chrome 内置模型是 `downloadable`（未下载），**无法真实端到端**；
  验证止于以 stub `LanguageModel` 喂入**实测得到的**真实 context 形状。

### 复用要点

- **给 streamFn 写适配层时，别信 `context.tools` / `context.systemPrompt`**——
  它们在 pi-agent-core 1.0.0 下恒为 undefined，要从 `context.messages` 的 system 消息里取。
  pi-ai 已导出 `getCurrentTools` / `getCurrentSystemPrompt` 专门干这件事，别自己解析 `toolsAdded`。
- 单元测试里「显式传全参数」的 context 是**理想形状**，与运行时形状不一致会掩盖整类 bug。
  给外部框架写适配层时，测试夹具应复刻**框架真实传入**的形状。
