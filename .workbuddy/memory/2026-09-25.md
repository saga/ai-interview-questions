## 逐题反馈「收口轮」：3 个 P0 + Agent/Copilot 合并 runtime（ADR-084）

用户逐文件复查后指出 3 个 P0 + 1 个结构性问题，本轮全部改完。

### ★ 最重要的一条经验：runtime 状态与 UI 投影必须分开持有

三个 P0 全是同一个根因的不同表现——**把「UI 投影」当成了「运行时状态」**：

1. **standard 模式误弹反馈卡**：`afterEvaluation` 在 standard 下也会触发 `onEvaluation`
   （评分总得发生），而 UI 用 `feedback !== null` 推断「已暂停」。于是「评分完成 → 下一题交付」
   的窗口里（开放题下数秒）弹出反馈卡、题目只读、提交按钮消失。
   → 修正：运行时**显式下发** `awaitingFeedback` 参数，且**先置 `session.status` 再通知回调**
   （否则回调里读到的 status 还是旧的）。hook 另立 `awaitingFeedback` state 作暂停态真源。
   **注意**：用户建议的改法（在 `onEvaluation` 里读 `session.status`）本身是错的——
   当时 `afterEvaluation` 是先调回调、后置 status，读到的是 `'running'`。
2. **刷新后「让 Copilot 详细解释」消失**：只恢复了 `feedback`（投影），漏了 `lastEvaluation`
   （原始评分），而该入口条件是 `lastEvaluation` 非空。
3. **刷新后节奏 UI 错**：没把 `session.feedbackMode` 同步回 React state。

### 核心设计（下次改动前务必先读）

- **暂停点必须放在共享内部缝 `afterEvaluation()`**，不能放在 `evaluateAnswer` 工具里。
  判分有三条路径：`choiceAdvance`（选择题确定性 `gradeChoice`）、`fallbackAdvance`
  （`evaluateSessionQuestion`）、LLM 循环（`evaluateAnswer` 工具）。**只有第三条经过该工具**，
  塞进工具里会让选择题和降级路径静默地不暂停。三条路径现在都收敛到 `afterEvaluation()`。
- **不要用 `agent.abort()` 实现暂停**：运行时会按 `stopReason === 'aborted'` 归类为异常，
  打出 `model_error` 遥测 + 用户看到「模型返回错误」。正确做法是 `finishTurn` 钩子返回
  `{ action: 'end' }` 让模型停在正常轮次边界，并用 `beforeToolCall` 拦掉等待期的
  `getQuestion` / `evaluateAnswer`。已有测试锁住「暂停态 `errors` 为空」。
- **`evaluation === null` 不产生反馈**：否则「评分失败」会被投影成「0 分」，是伪造数据。
- `finishTurn` 返回 `undefined`（不是 `{ action: 'continue' }`）以保留默认调度，避免多一次 provider 请求。

### ★ 教训：断言必须**能失败**（本次抓到 1 个假通过用例）

`learner.test.ts` 原写 `expect(JSON.stringify(profile)).not.toContain(' 答案不正确，请参见解析')`
——**串首多了一个空格**，而 JSON 里数组元素没有前导空格，所以这条断言**永远为真**。
去掉空格后立刻变红：那个假 gap 确实进了 `profile`。

真因不在聚合层（`sessionFromQuiz` 已把选择题的 `gaps` 清空），而是**新加的 `evaluation` 字段**
原样留存了判分器原文——这是刻意的（历史回放要复用实时反馈卡）。
故正确的断言粒度是**只锁聚合信号**，而非整份 profile：

```ts
const profile = updateLearner(emptyProfile(), rec);
expect(JSON.stringify(profile.topicStats)).not.toContain('答案不正确，请参见解析');
expect(JSON.stringify(profile.misconceptionHits)).not.toContain('答案不正确，请参见解析');
```

推论：**「整份对象序列化后不含某串」是很差的断言**——它把「聚合结果」与「忠实原始记录」两种语义
混在一起，且极易被一个多余空格变成永真。要断言什么，就精确指到那个字段。

### ★ 守卫要按「状态」冻结，不要按「工具名」枚举

P0：`beforeToolCall` 原先只拦 `getQuestion` / `evaluateAnswer`。但
`toolExecution: 'sequential'` ⇒ **同一条 assistant 消息可带多个 tool call**，而 `finishTurn`
只在**整轮工具全部执行完**之后才调用。于是模型一轮返回 `evaluateAnswer + finishInterview` 时，
`evaluateAnswer` 置 `awaiting_feedback`、`finishInterview` 紧随其后**无人看守**，直接把状态推到
`finished` —— 用户跳过反馈卡、直接看到「面试已结束」。

改法：`if (session.status === 'awaiting_feedback') return { block: true }`，**不再判断工具名**。
判据是**状态语义**（暂停态下模型本就不该做任何动作），所以「全部冻结」既是最严的守卫，
也是唯一**不需要随工具集演进而维护**的守卫。停在「把 `finishInterview` 也加进黑名单」＝
下次新增工具（`skipQuestion` / `requestHint`…）原样重现。

**通用教训：黑名单式守卫的维护成本随被守卫集合增长，按状态冻结不会。**

### ★ React state 读不到「当下」，重入闸必须用 ref

`busy` 是 state，事件回调里读到的是**本次渲染时**的旧值——覆盖不了「点击发生在 setState 之后、
重渲染之前」的窗口。`useAgentInterview` 新增 `busyRef` 同步镜像（所有写入统一走 `setBusyBoth`），
暴露 `agentBusy()` 给 `submit` / `jumpToNextQuestion` 入口 `return`。
（`submittingRef` / `continuingRef` 本来就是 ref，所以只有 `busy` 有这个问题。）

两个 UI 入口共用 runtime ⇒ **UI 的 `disabled` 只是提示，不是契约**。`Sender` 的 `disabled`
当时还是字面量 `false`。两层都要做。

### ★ 重入闸必须留逃生口，且不能拦在错的时机上（评审稿在这里是错的）

评审稿建议用 `agentInterview.busy` 拦 `continueAfterFeedback`、并在 `handleSend` 里一律拦。
两条都会造成新 bug，本轮**刻意没照做**，并在代码里写了注释说明原因：

1. **`end_interview` 不能拦**。`finalize()` 会先 `abort()` 再收尾，它是用户主动中止的**逃生口**；
   拦掉 = 把用户锁死在暂停态。
2. **`continueAfterFeedback` 不能用 `busy` 拦**。`awaiting_feedback` 是在 `afterEvaluation`
   **内部**置的，而 `busy` 要到 `agent_end` 才清 ⇒ 用户提交后立刻点「继续」会被**无声吞掉**。
   它的幂等性已由 `continuingRef` + 运行时 `status !== 'awaiting_feedback'` 检查保证。

**通用教训：加「忙判断」前先问「这个忙碌标志与我要保护的状态，生命周期是否一致」。**
不一致时忙判断不是保护，是丢事件。

### ★ 「假成功」比报错更糟：`finalize()` 必须 await `onComplete`

`onComplete` 是 IndexedDB 写入（Promise）。同步调用 ⇒ 写入失败变成 unhandled rejection，
而 UI 已经显示「已保存」。改 `async finalize()` + `try/catch`（失败 `setError`），
两个调用点改 `void finalize()`。

### 存储边界：按「该字段被谁消费」决定校验强度（修正上一轮的结论）

**上一轮我在 MEMORY.md 里写的「session 行刻意不套完整 schema」是过度简化的，本轮修正。**

旧口径只查 `Array.isArray(row.questionResults)` ⇒ `{ questionResults: [{}] }` 能过 ⇒
`result.topic` 是 undefined 被写进 `topicPracticeSessions`，脏形状流进进度页与历史回放。

但**整行套 `sessionRecordSchema` 也会误伤**：该 schema 传递性要求
`questionResults[].evaluation`（完整 `EvaluationResult`）与 `questions`（原题快照），
而这些都是**历史回放才读**的字段。第一次写成严格校验，直接弄坏了
`sessionFromQuiz → updateLearner → save → load` 端到端测试——旧快照形状过时，整行被丢。

正确口径：**`parseSessionRow` 三段式**——严格 → 逐条摘掉不过的 `evaluation`（其余题目评分保留）
→ 整行摘掉 `questions` / `answers` → 仍不过才丢行。

判据是**该字段被谁消费**：
- 核心字段（`overall` / `questionResults` 骨架）被**进度聚合**消费 → 坏了必须丢行；
- 回放快照只在 `SessionReplayDrawer` 读 → 坏了只降级（该组件本就支持退化成「分数 + 解析」视图）。

**为一条过时快照丢掉用户整段历史，代价远大于回放视图降级。**
「不可信边界」不等于「全部严格」——要按消费方分级。

### ★ 评审稿引用的代码 ≠ 文件里的代码时，以文件为准

第 4 项说 `CONTINUE_PATTERN` 仍是前缀匹配并建议加 `$`。**它早在上一轮（ADR-083 收口）
就已经是整句匹配**，末尾保留指代填充（`跳过这道题`）/ 难度修饰（`下一题难一点`）/ 语气词的可选组，
`CONTINUE_EXPLAIN_PATTERN` 也已在位。按稿子的朴素 `$` 写法改会**弄坏**既有的
`detectCommand('下一题难一点')?.difficulty === 'hard'`。

评审稿给的文件路径与代码片段是**线索**，不是事实。落地前必须回文件核对；不一致时要**报告差异**，
而不是照稿执行。

### 其余三项

- `agentSession.status`：`z.string().min(1)` → `z.enum(['running','awaiting_feedback','finished'])`。
  宽泛字符串会把手改的任意值判为合法，续面时恢复出运行时无法理解的状态，后续所有
  `status === '...'` 判断全部落空（症状：「草稿看起来能恢复、但行为莫名其妙」）。
  **不**连带改 `getActiveAgentSession` 的 `!== 'finished'`：宽值比 `'finished'` 失败方向偏保守
  （未知状态当成可恢复），改它没收益。
- `CopilotSidebar`：监听 `phase: running → done`，清空侧栏 `ConversationSession` / `chatQuestion` /
  上下文，**保留** `mode: 'interview'` + `endedAt`（让侧栏显示「面试已结束」，而非静默退回普通问答）。
- `interviewContext.ts` 顶部注释仍在描述「两个独立 runtime」→ 改为描述 ADR-084 的单一 runtime 现状。
  **注释过期会让后来者按错误的心智模型改代码。**

## 测试瘦身 · 第三轮（16 个文件，−83 例：928 → 845）

用户要求「再删掉 80 个不重要的、低优先级的、测试点不重要的 unit test」。删了 **83**，
−591 / +6 行，失败数不变（仍为那 3 个 `local.test.ts`）。全量 **842 passed / 845**，typecheck 通过。

### 判据：什么叫「测点不重要」

前两轮捞的是**重复**，这一轮捞的是**测点本身没价值**。五类：

1. **被更强用例完全包含** —— `toEqual` 被 `toEqual + length > 0` 包含；空结果的平凡补集
   （`Case 2：全部掌握 → gaps 为 []`）；`undefined` 与省略参数等价（同一代码路径）。
2. **只复述 schema / 框架** —— Zod 的 required / `min(1)` / enum 拒绝；
   `Array.isArray` 类型检查（`providers 不是数组`、`顶层缺 providers`、`空链`）。
3. **恒真或纯否定** —— 注入 `() => 0` 的 rng 再断言「两次调用相同」；
   `VARIANT_SYSTEM` 不含旧措辞；单条 `not.toContain`。
4. **名实不符** —— 标题承诺 A、断言里只测 B。
   实例：`collectTopicRefs 去重并保留首次出现的 category`，断言里**根本没有 category**；
   `证据面仍只看题干：概念只出现在选项里 → 记 warning`，断言的是与上一条**完全相同**的 warning；
   `fuzzball 短语级兜底对长文本有效`，只断言 `.ok === true`（对任何结构合法的变体都为真）。
5. **平凡透传 / 空入参 / 常量自证** —— `parseChatAnswer(openQ, x) === x`；
   `findNearIdenticalPaths([]) === []`；`REASONING_PATH_SIMILARITY_THRESHOLD === 82`；
   `toBe(calculateProficiency(...))` 这种「断言实现调用了它调用的那个 helper」的接线自证。

### ★ 删除块的工具与两个坑

用一次性 Python 脚本做精确块删除：每条 old 串先 `assert s.count(old) == 1` 再 `replace(old, '')`，
**比逐条手改可靠**（错一处就整体不写盘）。两个坑都踩到了：

1. **old 串同时以 `\n` 开头并以 `\n` 结尾 → 会吃掉前后两个分隔换行**，
   把上一块的 `});` 和下一块的 `it(` 粘成一行 `});  it(`。
   本轮出现 2 处（`learner.test.ts` / `variant.test.ts`）。**语法仍合法、测试仍绿**，
   所以只有肉眼或专门 grep 才发现。
   → 正确写法：old 串**不以 `\n` 开头**，只以 `\n\n` 结尾（保留前一个空行）。
2. **被删块是 describe 的最后一项时，old 串不能带尾部空行**（那里直接跟 `});`），
   否则 `count == 0` 匹配失败。本轮 `settings.test.ts` 因此漏掉了 describe 的收尾 `});`，
   文件解析失败（`PARSE_ERROR: Expected } but found EOF`），是**全量测试**报出来的。
   → **删完必须跑一次全量，不能只看 diff。**

### 删完必须扫的三件事

1. **死导入**：写了个 `deadimports.py` —— 逐个具名导入数「在整个文件里出现几次」，
   出现 1 次即只在 import 行里（= 死导入）。本轮清掉 4 个
   （`variantFingerprint` / `calculateProficiency` / `getAngleStat` / `collectTopicRefs`；
   后续又清掉 `findNearIdenticalPaths` / `isReasoningGoalWellFormed` / `REASONING_PATH_SIMILARITY_THRESHOLD`）。
   注意 `tsconfig` **没有开 `noUnusedLocals`**，tsc 不会报。
2. **括号配平**：见上面坑 2。
3. **全量测试**：见上面坑 2。

### 明确保留（看着像低价值、其实不能删）

- `断言相反 ≠ 逻辑互补`：`isReasoningPathSubstantiallyDifferent`（签名 `AssessmentInference`，
  单阈值看 `reasoningGoal`）与 `isReasoningPathTooSimilar`（签名 `ReasoningPath`，
  `targetDice + goalDice` 双阈值）——两组用例**全留**。
- `evaluations` 与 `answers` 两条「已交付」判定不能合（`评分为 null…也算已考察` /
  `已作答但尚未评分…也算已考察`）。
- **显式否定契约**：`答错时 gaps === []`（选择题不伪造 gap）、`未标注 misconceptionMap 不产误解信号`
  这类「不许凭空造数据」的断言是产品语义，不属纯否定。
- `questionSlotLimit` 的口径表：虽是平凡纯函数，但它是**唯一**直接测该导出的地方，
  `current_question` 分支的端到端用例只断言 `length <= limit`，覆盖不到「放开」语义。

三轮下来 949 → 845（累计 −104）。**「重复」和「测点无价值」这两类都基本捞干了**，
再往下要动就得砍真实覆盖面，不建议继续机械删。

## 评审收口第三轮：6 项（5 改 1 测试覆盖），ADR-086

外部评审基于 **HEAD `6109723` 的静态检查**（未跑 Vitest）给出 6 项：2 个 P0/P0.5 + 3 个 P1 + 1 项
「测试覆盖退化」。逐条核实后 **5 项属实**（2 项成因/范围与稿子有出入），1 项是测试要求。
全量 **868 passed / 871**（845 → 871，+26；文件 62 → 65，+3）。typecheck 通过。

### ★ 交付即建键：注释写了、代码没做

`types.ts` 的注释写着「`evaluations[id]` 在题目交付给用户时即建键」，而 `getQuestion` /
`fallbackNextQuestion` **只写 `session.currentQuestion`**。于是「已交付但未作答」的题在交付那刻
**不存在**（`countDelivered` 数 evaluations 键数、`isDelivered` 也只看 answers/evaluations/currentQuestion）：

- `MAX_AGENT_QUESTIONS` 可被无限绕过（Agent 反复 `getQuestion` 换题、从不评分 ⇒ 计数恒为 0）；
- 换题后上一道未作答的题**彻底消失** ⇒ 防重复出题、题目历史、自适应全部失准。

改法：`markDelivered(session, id)`（`evaluations[id] ??= null`，幂等、不覆盖真实评分），两个交付点调用。

### ★★ 加交付标记会**反转**一个既有推断（稿子没提，不做就是新 P0）

`ensureQuestionDelivered` 用「`evaluations` 里有没有键」推断「用户答没答」。加了标记后
每道刚交付的题都有键 ⇒ 被误判成「已处理」⇒ **覆盖当前题再交付一道新的**，用户眼睁睁看着题被换掉。

- 判据改为 `session.answers`（用户是否已提交）。
- `skip()` 必须**显式 `session.currentQuestion = null`**：它原先靠写 `evaluations[id] = null`
  放行守卫，而交付标记本身就是 null ⇒ 写它等于没写 ⇒ **跳过静默失效**。
- 顺带把 `advanceDeterministic` / `ensureQuestionDelivered` 里第三份计数实现
  `new Set([...answers, ...evaluations]).size` 统一到 `countDelivered`。
- `endEarly` 判据改 `countDelivered === 0`：旧口径把「已交付未作答」的用户**挡在面试里出不去**。

**通用教训：给某个字段增加一种新语义之前，先 grep 谁在用它做推断——「键存在」这种推断尤其脆。**

### ★ 收尾顺序：稿子说「同步调用」，实际是「顺序反了」

稿子称 `onComplete` 是同步调用、失败变 unhandled rejection。**不成立**——`finalize()` 早已
`await onComplete(record)` + `try/catch`。真正的缺陷是**顺序**：
`void flushPersist().then(() => deleteAgentSession(...))` 在 `await onComplete` **之前**发出，
且 `finalizedRef` 在函数开头就置位 ⇒ 落库失败时草稿已删、重试闸已关，成绩永久丢失。

改法：抽出 `agent/finalizeSession.ts`（注入 IO，固化「先 persist，成功后才 flushDraft → deleteDraft」），
`finalizedRef` 拆成 `finalizingRef`（重入闸）/ `finalizedRef`（终局完成，仅成功后置位）。

**★ 顺序类契约一定要抽成可测模块**：调换顺序后一切照常运行，只在落库失败时静默丢数据——
人工评审几乎不可见，抽出来才能用「调用顺序断言」钉死。

配套：新增 `finalizing` / `saveError` / `retryFinalize`；`saveError` 非 null 时结果页与
Copilot 侧栏**不得**再显示「已记入学习档案 / 已写入学习记录」（那是骗用户），改显示原因 + 重试；
`restart()` 在 `saveError` 非 null 时**不删草稿**。

### ★ 「延长本题时间」：归零会自我清理，所以延长必须**重新装载**

归零时 `clearInterval`（否则每秒空转），而 `extendQuestionTime` 只重置 ref/state ⇒ 显示永久停在
180、再也不走动。抽成 `agent/questionTimer.ts`，`extend` 改为 `start()`（内部先 `stop()` 再 `setInterval`）。

### ★ 画像提交串行化：基准**不能**重新 `loadLearner()`

`updateLearner` 是读-改-写，`doSubmit` 与 `handleAgentComplete` 并发时后完成者整体覆盖。
`saveLearner` 的 Dexie 事务只保证**单次写入原子**，覆盖不了跨调用的读-改-写。

新增 `application/learnerCommit.ts`：队列串行「读基准 → 变换 → 落库 → 回写基准」，
**基准在临界区内读**、成功后**同步回写**（不等 React 重渲染）。

**关键取舍**：基准**绝不**用 `loadLearner()` 重新读库——它**不是 `saveLearner` 的逆运算**：
会用**默认** proficiency 配置重算 `mastery`（`storage/learner.ts` 的 `calculateProficiency` 没传 config）、
按 `SESSION_CAP` 截断、丢弃校验不过的行。拿它当基准会**静默改写用户的掌握度**。
→ **「从库里重新读一份」不等于「拿到权威基准」：先确认读路径是写路径的逆运算。**

配套：`useTrainingSession` 的 `profileRef` 渲染期同步改为「仅在 state 真的变化时赋值」——
无条件 `profileRef.current = profile ?? emptyProfile()` 会把队列刚同步写入的结果覆盖回旧快照。

`learnerCapability.commitSession` 实际**零调用方**（稿子当成活跃风险面），未删，只加警示注释。

### ★ 画像闸设在会话层（与 ADR-085 同源）

`App.tsx` 传 `profile ?? emptyProfile()`，`CopilotSidebar` 渲染在 `loadingProfile` 闸**之外** ⇒
画像加载期间可从侧栏开局，整场面试建立在空画像上，且空画像被写进草稿、续面后继续生效。

`useAgentInterview` 的 `profile` 放宽为 `LearnerProfile | null`，`startInner` 入口 `if (!profile) return`，
暴露 `profileReady`；`App.tsx` 去掉 `?? emptyProfile()`；两个入口各自禁用/说明。
**闸设在状态上而非逐入口拦**（逐入口必然漏一个）。

### ★ 没有 React 测试环境时，用「抽纯模块」代替「装测试框架」

本项目 **61 个测试文件全是纯函数 / node 环境**（无 `@testing-library/react`、无 `jsdom`/`happy-dom`），
稿子要的「finalize 保存失败不删草稿 / timer 延长 / 画像闸」根本无法在 hook 层断言。

选择：**把非纯逻辑抽成零依赖可注入模块**，而不是新增整套 React 测试依赖（成本 = 依赖 + 环境配置 +
fake timer × IndexedDB × mock runtime 的脆弱组合）。落点：
`finalizeSession.ts` / `questionTimer.ts` / `learnerCommit.ts` 三个模块 + 真实交付路径的
`tools.test.ts` / `interviewAgent.test.ts`。

**★ 新用例必须用变异测试证明「能失败」**：临时改回旧行为，逐条确认变红。本轮 6 个变异
（`questionTimer.start` 只在首次装载 / `finalizeSession` 顺序反转 / 去掉 `learnerCommit` 的 `tail.then` /
删两处 `markDelivered` / `skip()` 只写 evaluations）**全部被捕获**。
**加测试不算数，能失败的测试才算数。**

### 其它

- 顺手修：`useAgentInterview` 的 `profileRef` 渲染期无条件赋值会把**续面回读到的草稿 profile 快照**
  清成 null（草稿从此落不下去）→ 改为仅在拿到画像时同步。
- 3 项 `local.test.ts` 的 `deepseek-v4-flash` 失败**已随 `6109723` 进入 HEAD**
  （ADR-085 当时记为「工作区未提交」，已在新 ADR 里更正）。即 **HEAD 本身就带 3 项失败**。

  一场已结束的面试——数据没丢但语义混乱），要真正做需在草稿上持久化「待保存」标记。
