# 编写独立知识点教程

## 边界

- 一个 KnowledgeNode 对应一篇独立主教程，教程 ID 和文件名绑定该节点 ID。
- 不合并 KnowledgeNode，不通过 topic 继承或共享正文补覆盖率。
- 综合工程教程用于跨节点串联，不能替代各节点主教程。
- 教程必须教会学习者机制、判断或操作，不是简单扩写 summary，也不是把题目解析复制成文章。

## 编写前

1. 阅读 KnowledgeNode 的 summary、required、misconceptions、angles 和前置关系。
2. 阅读相邻节点教程，明确本节点的知识边界，避免重复。
3. 使用真实教学来源；产品行为、API、限制、版本和数字必须能追溯到官方文档或原始材料。
4. 写出 2–4 个可检查的学习结果，描述学习者能解释、判断、实施或诊断什么。

## 正文要求

按知识点选择适合的组织方式，不强制套用同一段落模板。通常应包含：

- 背景：解释这个知识点解决什么工程问题。
- 核心机制：解释机制、适用边界和前提。
- 例子：至少一个与本知识点直接相关的示例；适用时使用 SQL、配置、伪代码或数据流。
- 工程判断：给出实施、验证或排障方法，不能用无关的通用步骤填充。
- 误区：说明真实误解为什么发生，以及在哪些条件下会造成错误结果。
- 主动回忆：要求学习者脱离正文解释核心机制或完成关键步骤。
- 迁移练习：给出不同于正文示例的新场景，要求应用所学知识。
- 来源：提供直接支持本节内容的原始来源和具体章节。

每篇教程必须有独立场景、示例和自测。不要把一个 Warehouse 场景复制到无关知识点，也不要反复使用同一个通用解释段落。

## 教学与考核

- 教程回答“应该学会什么、为什么、如何应用”。
- 题目测量学习结果，不只是复述教材句子。
- 每道新题必须声明 KnowledgeNode、cognitiveTask 和 source。
- 阅读完成不等于掌握；掌握必须来自专项训练或工程任务的评估证据。

## 验收

- ID、文件名和 KnowledgeNode.id 一致。
- 正文与节点 summary / required / misconceptions 一致。
- 场景、示例、自测和工程步骤针对该知识点。
- 关键技术事实可定位到真实来源；未核验来源明确标注。
- 运行内容审计：

```bash
npm run learning:content-audit -- --strict --base <base-commit>
```

重复段落审计是阻断信号，不是自动改写建议。先定位模板或内容复用来源，再围绕节点的具体目标重新编写。
