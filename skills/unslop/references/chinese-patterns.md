# 中文技术内容表达参考

本文件是 `skills/unslop/SKILL.md` 的例子库。示例用于识别问题，不是全局禁词表。判断依据始终是上下文、信息价值和技术语义。

## 1. 常见空转表达

| 常见写法 | 优先考虑 | 说明 |
|---|---|---|
| 在当今数字化转型不断深入的背景下 | 直接说明本文讨论的系统或问题 | 行业背景如果不影响技术判断，就删掉 |
| 值得注意的是 / 需要指出的是 | 直接写需要注意的事实 | 真正的例外或限制可以直接用“例外是”“限制在于” |
| 不难发现 / 显而易见 | 直接给出观察结果和依据 | 不要替读者宣布结论显而易见 |
| 综上所述 / 总而言之 / 由此可见 | 删除，或写出具体结论 | 如果结论有决策意义，必须说明条件 |
| 下面我们深入探讨 / 让我们一起看看 | 直接进入机制或问题 | 不用旁白介绍接下来要做什么 |
| 具有重要意义 / 发挥关键作用 | 说明具体影响对象和结果 | 例如说明它减少了哪类争用、支持了什么查询或改变了哪个运维责任 |
| 全面赋能 / 打造生态 / 引领变革 | 用具体能力、接口和行为替代 | 营销宣传原文或直接引述除外 |
| 业界普遍认为 / 研究表明 | 给出可定位来源，或删除归因 | 不要用模糊群体替代证据 |

## 2. 需要结合语境的句式

**“不是……而是……”**

适合纠正常见概念混淆，例如“Stream 保存的是 Offset，不是源表的完整副本”。如果每个章节都用这种句式制造强调，改成直接陈述机制。

**“不仅……更……”**

当第二项确实扩大或修正第一项时可以保留。若只是把同一件事写成两次递进，删掉一层。

**“首先……其次……最后……”**

操作步骤、事务顺序和依赖关系需要顺序编号时保留。若只是每段用来起头，或并不存在严格顺序，直接按实际逻辑组织。

**“随着……发展……”**

如果产品版本、流量增长或数据规模变化是问题前提，就明确写出变化及其影响；若只是泛泛背景，删除。

**“闭环、抓手、底座、赋能、生态、端到端”**

这些词并非一律错误。“闭环”必须有反馈路径，“端到端”必须明确起点和终点，“底座”必须对应具体基础设施或平台能力；否则改成具体对象与动作。

**“高效、灵活、强大、全面、无缝、显著”**

只有在说明衡量对象和证据时才有信息量。比如“加载时间从 20 分钟降到 3 分钟”比“显著提升加载效率”更清楚；没有测量依据时，不得编造数字，可写清楚具体机制但不声称效果幅度。

## 3. 技术文章常见问题

- 把“背景、意义、价值、趋势”写成数段，却没有解释机制。
- 每个小节都按“定义 → 优势 → 挑战 → 总结”展开，内容却没有对应的不同层次。
- 大量使用“该技术、该方案、该能力、这一模式”，读者需要反复回看才能知道指代对象。
- 用“提升性能、降低成本、增强安全性”概括结论，没有指出影响因素、适用条件或观测指标。
- 一段先说一遍观点，下一段用“换句话说”重复，再在结尾复述一次。
- 标题写“未来展望”“核心价值”，正文实际讨论的是版本兼容、刷新延迟或成本核算。
- 每节硬凑三个优点、三个挑战、三个建议，导致真实重要性和篇幅不匹配。

处理方式：保留有用的定义、对比、例子和步骤；把泛化结论落到具体机制、限制、运行证据或实际决策条件上。

## 4. 题目和解析的表达问题

| 问题 | 识别方式 | 处理方式 |
|---|---|---|
| 模板题干 | 连续多题都以“某企业正在……你应该……”起头，企业背景也不影响答案 | 改用真实的目标、约束、故障现象或数据证据；不要只替换公司名 |
| 假场景 | 写了角色、行业、规模和时间，但删掉后答案完全不变 | 删除装饰性背景，或加入真正影响判断的条件 |
| 空泛问题 | “在实际工作中应如何处理”“哪项最合适”没有决策边界 | 补足目标、约束、验收条件；无法补足时重新定义考点 |
| 记忆题包装 | 题目只问产品缩写、功能名或某篇文章说了什么 | 按知识规范判断是否有必要；优先考察机制、使用条件和边界 |
| 稻草人干扰项 | 一项明显违反常识，或用“完全不测试、无视安全”等极端做法凑数 | 改为真实误区、适用条件错配、相邻概念混淆或范围错误 |
| 解析复述 | 解析只是重复答案或写“正确选项为 A、C” | 解释判断依据、前提和误区；保持简洁 |
| 固定结尾 | 每道题都以“因此应综合考虑业务需求和技术约束”结尾 | 说明这道题具体需要比较的约束，不套用通用顾问话术 |

本表不覆盖答案唯一性、Concept Scope、选项层级和知识映射；这些仍由 `docs/question-content-spec.md` 裁决。

## 5. 不要误删的中文技术表达

以下表达可能是必要内容，不能单凭形式修改：

- “不支持 / 不保证 / 不应 / 必须”及其适用范围；
- “至少、至多、仅、默认、通常、可能、除非”等限定；
- “不是 A，而是 B”这种明确纠错；
- 同一个技术名词在多个段落中的重复。技术文档应保持术语一致，不追求文学式同义替换；
- “首先、然后、最后”表达真实的执行顺序；
- 表格、清单、编号步骤、学习目标、检查问题；
- 对比式句子、被动句、长句和括号中的边界条件；
- 引文、代码、命令、产品名称、API 名称、版本、字段和配置键。

## 6. 复核示例

**原句**

“在当今数据驱动的时代，数据治理作为企业数字化转型的重要抓手，不仅能够全面赋能数据资产价值释放，更能够构建端到端的数据治理闭环，从而为企业高质量发展提供坚实底座。”

**建议**

“数据治理需要明确数据所有者、访问策略、质量规则和异常处理责任。治理结果应能追溯到数据集、业务定义和实际使用方。”

修改后的写法把抽象收益换成了具体治理对象。只有在原材料确实描述了这些责任和机制时才能这样改；如果来源没有提供这些事实，就不能将其作为事实补写。

**原句**

“为什么要使用 Multi-cluster Warehouse？因为它可以全面提升系统性能。”

**建议**

“Multi-cluster Warehouse 主要用于承接并发查询。若瓶颈来自单条查询的扫描量或执行计划，增加集群未必能缩短该查询的运行时间。”

改写保留了必要对比，同时把适用边界写清楚。

**原句**

“正确答案是 A、C。A、C 正确，B、D 错误。”

**建议**

“选择 A 和 C。A 满足题目给出的隔离要求；C 处理了重试后的重复应用。B 把查询排队误当成单条查询算力不足，D 则忽略了目标端幂等性。”

答案解释必须与题库中的实际答案和题目约束一致，不能从表达模板推导技术事实。
