# Verify Question Correctness

## Purpose

This skill verifies whether an interview question is technically, logically,
mathematically, and factually correct.

It is a correctness-verification layer.

It is NOT a question-generation skill.
It is NOT a wording-polishing skill.
It is NOT a duplicate detector.
It is NOT a replacement for `questionChallenger`.

The goal is to detect errors that structural validation and ordinary
question-quality heuristics cannot reliably detect, including:

- wrong answer keys
- mathematically false claims
- technically false claims
- invalid assumptions
- impossible premises
- missing conditions that change the answer
- multiple valid choices in a single-choice question
- no valid choices in a multiple-choice question
- explanations that contradict the actual theory
- complexity claims that are wrong
- causal claims with reversed direction
- implementation details that depend on version/configuration
- outdated claims about models, APIs, libraries, or frameworks
- statements that are only conditionally true but are presented as universal
- subtle distractors that are actually correct
- distractors that are incorrect for the wrong reason
- internally inconsistent question premises

The skill must prefer uncertainty over fabricated certainty.

---

# 1. Core Principles

## 1.1 Answer-key independence

Never verify a question by reading the stored answer key first and then
reasoning toward it.

The verification process MUST attempt to solve the question independently
before comparing the result against the stored answer.

Correct order:

1. Read question and options.
2. Identify what is being asked.
3. Extract relevant claims and assumptions.
4. Solve independently.
5. Verify each option independently.
6. Determine the independently supported answer set.
7. Compare with the stored answer key.
8. Inspect explanation.
9. Produce verdict.

Incorrect order:

1. Read answer key.
2. Assume answer is correct.
3. Find evidence supporting the answer.
4. Ignore contradictory evidence.

This rule is mandatory.

---

## 1.2 Every option is independently testable

For choice questions, every option must be independently evaluated.

Use:

- `SUPPORTED`
- `REFUTED`
- `CONDITIONAL`
- `INSUFFICIENT`
- `CONFLICTING`

Never use "wrong" merely because an option is not the stored answer.

For example:

```text
A: SUPPORTED
B: REFUTED
C: CONDITIONAL
D: REFUTED
````

means the question may be invalid as a single-choice question because C
could become correct under a reasonable interpretation.

---

## 1.3 Do not force binary truth

Many technical statements depend on:

* version
* implementation
* assumptions
* architecture
* parameter regime
* data distribution
* task definition
* training objective
* inference setting
* deployment environment

Therefore:

```text
true / false
```

is insufficient for verification.

Prefer:

```text
SUPPORTED
REFUTED
CONDITIONAL
INSUFFICIENT
CONFLICTING
```

A `CONDITIONAL` claim is not automatically wrong.

The verifier must determine whether the question explicitly provides the
conditions required for the claim.

---

## 1.4 Evidence before confidence

Confidence is not evidence.

A model saying:

> "This looks correct."

is not evidence.

A citation, derivation, specification, theorem, experiment, source code,
or reproducible calculation is evidence.

The report must distinguish:

```text
reasoning
evidence
confidence
```

These are separate fields.

---

## 1.5 Support AND refutation

When evidence retrieval is necessary, search for both:

* evidence supporting the claim
* evidence contradicting the claim

Do not construct a one-sided confirmation search.

For disputed or surprising claims, explicitly attempt:

```text
claim + evidence
claim + counterexample
claim + limitation
claim + exception
claim + misconception
```

If only supporting evidence is found, do not automatically call the claim
verified.

---

## 1.6 Source hierarchy

Prefer evidence in this order:

### Tier 1 — Primary authoritative evidence

* original academic paper
* official specification
* official API documentation
* official framework documentation
* official model card
* official technical report
* source code of the implementation being discussed
* standards document
* formal theorem / textbook source for established mathematics

### Tier 2 — Strong technical sources

* peer-reviewed paper
* major conference publication
* authoritative university material
* official engineering documentation from a recognized organization

### Tier 3 — Secondary technical sources

* high-quality technical articles
* reputable engineering documentation
* expert technical explanations

### Tier 4 — Discovery-only sources

* forums
* Reddit
* Stack Overflow
* social media
* random blogs
* SEO articles

Tier 4 may be used to discover a lead.

It must not be the sole basis for a high-confidence P0 correctness verdict.

# 2. Scope

This skill verifies four major dimensions.

## 2.1 Factual correctness

Examples:

* "Transformer self-attention is O(n²)."
* "LoRA updates all base-model parameters."
* "Batch normalization always improves generalization."
* "RAG guarantees hallucination-free answers."

The verifier must determine whether such statements are actually true,
conditionally true, misleading, or false.

---

## 2.2 Mathematical correctness

Examples:

* equations
* inequalities
* gradients
* probability statements
* asymptotic complexity
* optimization claims
* matrix properties
* statistical claims
* theorem conditions
* counterexamples

Mathematical claims require explicit derivation or authoritative evidence.

When practical, calculate rather than merely recall.

For example:

```text
Claim:
"For matrix M, property X implies rank(M) = r."

Verification:
1. Write the relevant definition.
2. Derive the implication.
3. Check boundary cases.
4. Attempt a counterexample.
5. Verify against authoritative sources.
```

---

## 2.3 Logical correctness

Verify:

* premises
* conclusion
* quantifiers
* implication direction
* necessary vs sufficient conditions
* correlation vs causation
* universal vs existential claims
* hidden assumptions
* counterexamples
* contradiction between question and explanation

Watch especially for words such as:

```text
always
never
guaranteed
only
must
cannot
necessarily
sufficient
necessary
equivalent
optimal
best
exactly
all
none
```

These words increase verification risk.

---

## 2.4 Technical / implementation correctness

Verify:

* framework behavior
* API behavior
* default configuration
* version-dependent behavior
* model capabilities
* library semantics
* deployment behavior
* performance claims
* implementation details

For current software / models / APIs, do NOT rely on stale model knowledge.

Use current authoritative documentation.

# 3. Verification Workflow

The canonical workflow is:

```text
Question
   ↓
1. Preflight
   ↓
2. Claim extraction
   ↓
3. Independent solve
   ↓
4. Assumption analysis
   ↓
5. Option-by-option verification
   ↓
6. Answer-set derivation
   ↓
7. Evidence retrieval
   ↓
8. Logic / mathematical audit
   ↓
9. Explanation verification
   ↓
10. Adjudication
   ↓
11. Final verdict
```

Do not skip independent solving.

Do not allow evidence retrieval to replace reasoning.

Do not allow reasoning to replace evidence when the claim requires
external verification.

---

# 4. Stage 1 — Preflight

Before semantic verification, inspect:

* question format
* question text
* options
* stored answers
* explanation
* topic
* angle
* cognitiveTask
* concepts
* assessment
* source metadata
* difficulty

Determine the risk profile.

Risk categories:

```text
mathematics
statistics
theory
algorithm
complexity
ML theory
LLM behavior
model behavior
framework/API behavior
security
distributed systems
architecture
historical fact
general technical fact
```

---

# 5. Stage 2 — Claim Extraction

Extract all material claims.

A question can contain multiple claims.

Example:

```text
Question:
"LoRA freezes the base model, trains low-rank matrices, and therefore
always reduces both training memory and inference latency."

Claims:

C1:
The base model parameters are frozen.

C2:
LoRA trains low-rank matrices.

C3:
LoRA reduces training memory.

C4:
LoRA always reduces inference latency.
```

Do not verify the entire question as one indivisible statement.

Every material claim should have its own verification result.

---

# 6. Claim Types

Classify every claim as one or more of:

```text
DEFINITION
FACT
THEOREM
EQUATION
ALGORITHM
COMPLEXITY
CAUSAL
COMPARATIVE
EMPIRICAL
IMPLEMENTATION
API
VERSION_DEPENDENT
BEST_PRACTICE
ARCHITECTURAL
PREDICTION
```

Examples:

```text
"Gradient descent updates parameters in the negative gradient direction."
→ DEFINITION / ALGORITHM

"Attention complexity is quadratic in sequence length."
→ COMPLEXITY

"Framework X supports feature Y."
→ IMPLEMENTATION / API

"Technique A is better than technique B."
→ COMPARATIVE / EMPIRICAL
```

---

# 7. Stage 3 — Independent Solve

Solve the question before looking at the stored answer.

For choice questions:

```text
independentAnswerSet = solve(question, options)
```

For open questions:

```text
independentExpectedAnswer = derive_expected_answer(question)
```

The solution must include reasoning sufficient to explain why the answer
follows.

For difficult questions, explicitly consider:

```text
What would make the apparent answer wrong?
What assumption does the answer depend on?
Can I construct a counterexample?
```

---

# 8. Stage 4 — Assumption Analysis

Determine whether the question is sufficiently constrained.

Look for missing assumptions involving:

* input domain
* data distribution
* model architecture
* training objective
* optimization regime
* parameter values
* randomization
* implementation
* software version
* hardware
* numerical precision
* asymptotic regime
* task definition

Example:

```text
"Algorithm A is faster than Algorithm B."

Potential missing assumptions:
- input size
- hardware
- implementation
- asymptotic vs empirical comparison
- batch size
```

The correct verdict may be:

```text
CONDITIONAL
```

rather than:

```text
SUPPORTED
```

If those missing assumptions affect the expected answer, the question
should normally be marked `REVIEW`.

---

# 9. Stage 5 — Option Verification

For every option:

```text
A → classify
B → classify
C → classify
D → classify
```

Each option must include:

```text
status
reason
key_claims
evidence
confidence
```

Example:

```json
{
  "option": 2,
  "status": "REFUTED",
  "reason": "The claim confuses parameter count with activation memory.",
  "confidence": 0.94
}
```

---

# 10. Multiple-choice Rules

## Single choice

Expected:

```text
exactly one SUPPORTED option
```

Potential invalid states:

```text
0 supported
2+ supported
1 supported + another CONDITIONAL option that is valid under
the question's stated assumptions
```

These should normally be `P0` or `P1`.

---

## Multiple choice

Expected:

```text
all and only the independently supported options
```

Compare:

```text
storedAnswerSet
vs
verifiedAnswerSet
```

A mismatch is a major correctness problem.

---

# 11. Stage 6 — Evidence Retrieval

Evidence retrieval is required when:

* claim is disputed
* model knowledge may be stale
* implementation/version matters
* mathematical claim is non-trivial
* paper-specific result is claimed
* API behavior is claimed
* quantitative number is given
* claim uses absolute wording
* verifier confidence is low
* independent solvers disagree

For stable and elementary facts, external retrieval may be unnecessary.

---

# 12. Current / Time-sensitive Claims

Use current authoritative sources for:

* model capabilities
* model context length
* API semantics
* framework features
* software defaults
* package behavior
* product limitations
* benchmark results
* current best practices
* recent research claims

Always record:

```text
source
URL
title
checkedAt
version/date if applicable
```

Never treat a cached model memory of an API as authoritative when current
documentation is available.

---

# 13. Evidence Search Strategy

For each uncertain claim:

### Pass A — Direct support

Search for evidence that the claim is true.

### Pass B — Refutation

Search for:

```text
counterexample
limitation
exception
failure case
incorrect assumption
```

### Pass C — Scope

Determine whether the claim is:

```text
universal
conditional
empirical
implementation-specific
version-specific
```

### Pass D — Primary-source verification

Replace secondary evidence with the strongest available primary source.

---

# 14. Mathematical Verification

For mathematical claims:

1. Restate the claim formally.
2. Identify definitions.
3. Check assumptions.
4. Derive the result.
5. Check edge cases.
6. Search for counterexamples.
7. Compare against an authoritative source.

Never accept a mathematical statement merely because it sounds familiar.

Especially verify:

* equality claims
* rank claims
* convergence claims
* complexity claims
* probability bounds
* optimization guarantees
* theorem conditions
* "if and only if" statements

For a universal claim:

```text
"For all x, P(x)"
```

attempt to construct:

```text
x where P(x) is false
```

A single valid counterexample refutes a universal claim.

---

# 15. Complexity Verification

For complexity questions verify:

* input dimensions
* dominant operation
* number of layers
* sequence length
* hidden dimension
* vocabulary size
* training vs inference
* dense vs sparse
* asymptotic vs empirical complexity

Do not confuse:

```text
parameter count
memory complexity
compute complexity
latency
throughput
```

These are different properties.

---

# 16. ML / AI Technical Claims

Explicitly distinguish:

```text
theoretical property
empirical observation
engineering heuristic
implementation detail
benchmark result
marketing claim
```

Examples of dangerous claims:

```text
"Technique X always improves accuracy."
"RAG eliminates hallucinations."
"Chain-of-thought improves every reasoning task."
"Model X is better than model Y."
"Quantization always reduces latency."
```

These require careful qualification.

---

# 17. Explanation Verification

The explanation must be checked independently from the answer key.

Verify:

```text
question
answer
explanation
```

are mutually consistent.

Look for:

* explanation proves a different answer
* explanation contradicts an option
* explanation uses an incorrect theorem
* explanation says "because X" where X is false
* explanation explains only one part of a multiple-choice answer
* explanation silently adds assumptions not present in the question

A correct answer with a materially false explanation is still a correctness
issue.

---

# 18. Detecting Answer-Key Anchoring

The verifier MUST NOT use:

```text
stored answer → explanation → reasoning
```

as its default workflow.

Instead:

```text
question
→ independent solve
→ independent option evaluation
→ evidence
→ compare stored answer
```

When using multiple verifier agents/models, give them the question without
the stored answer whenever practical.

---

# 19. Independent Verification / Panel

Use a second independent verifier when:

* first verifier confidence < 0.85
* P0 issue is suspected
* mathematics is non-trivial
* two options appear plausible
* source evidence conflicts
* implementation behavior is version-sensitive
* question uses strong universal language
* first verifier and stored answer disagree

Recommended:

```text
Verifier A
Verifier B
    ↓
same verdict → increase confidence
different verdict → adjudication
```

Do not blindly average contradictory reasoning.

---

# 20. Adjudication

Adjudication should inspect:

1. original question
2. independent solutions
3. option-level verdicts
4. evidence
5. source quality
6. assumptions
7. stored answer
8. explanation

The adjudicator must choose one:

```text
KEEP
REVIEW
FIX
REJECT
```

### KEEP

Question is sufficiently supported and no material correctness issue exists.

### REVIEW

Evidence or reasoning is insufficient or genuinely conflicting.

### FIX

Question contains a correctness problem that is repairable.

Examples:

* wrong option key
* missing condition
* incorrect formula
* outdated API claim
* misleading wording

### REJECT

The assessment itself is fundamentally unsound.

Examples:

* impossible premise
* no defensible answer
* irreducible ambiguity
* inherently broken question structure

---

# 21. Severity

## P0 — Critical correctness error

Use P0 for:

* wrong answer key
* mathematically false result
* materially false technical fact
* invalid theorem application
* impossible premise
* single-choice question with multiple valid answers
* single-choice question with no valid answer
* multiple-choice answer set materially wrong
* explanation proves the wrong answer
* security-critical false claim

P0 questions MUST NOT be silently accepted.

---

## P1 — Material correctness / validity issue

Examples:

* missing assumption changes answer
* version-dependent claim presented as universal
* ambiguous technical condition
* important causal direction error
* outdated implementation behavior
* technically correct only under unstated constraints
* materially misleading explanation

---

## P2 — Minor precision issue

Examples:

* imprecise wording
* omitted secondary caveat
* terminology could be more precise
* explanation lacks an important nuance that does not change answer

P2 does not necessarily require question removal.

---

# 22. Verdicts

Question-level verdict:

```text
VERIFIED
CONDITIONAL
NEEDS_REVIEW
INCORRECT
```

Claim / option level:

```text
SUPPORTED
REFUTED
CONDITIONAL
INSUFFICIENT
CONFLICTING
```

Repair action:

```text
KEEP
FIX
REVIEW
REJECT
```

Do not collapse these into one boolean.

---

# 23. Confidence

Confidence is a judgment over the available evidence.

Suggested interpretation:

```text
0.95–1.00  very high
0.85–0.94  high
0.70–0.84  medium
0.50–0.69  low
<0.50       very low
```

Confidence must consider:

* evidence quality
* source authority
* reasoning complexity
* verifier agreement
* scope ambiguity
* version sensitivity

Never use confidence alone as a correctness guarantee.

# 26. Open Questions

For open questions there is no answer-option set.

Verify:

* whether the expected answer is technically correct
* whether key required points are correct
* whether important caveats are missing
* whether the expected answer assumes unstated conditions
* whether the explanation is technically correct

The verifier must NOT require the candidate answer to exactly match the
canonical wording.

The target is correctness, not wording identity.

---

# 27. AI / LLM-specific Verification

Be especially careful with claims about:

* context windows
* tokenization
* attention
* KV cache
* quantization
* LoRA / QLoRA
* RLHF
* DPO
* RAG
* tool calling
* agent loops
* memory
* reasoning
* chain-of-thought
* function calling
* structured output
* MCP
* framework APIs
* model capabilities
* benchmarks

Prefer primary sources.

For model-specific claims, record model/version/date.

Do not generalize behavior of one model to all LLMs unless the claim is
actually architecture-level.

---

# 28. Retrieval and Current Information

If a question depends on a current library, API, framework, model, product,
or recently published result:

1. Search current authoritative documentation.
2. Determine relevant version/date.
3. Verify the exact behavior.
4. Record the source and date.
5. Mark as `CONDITIONAL` when behavior depends on version/configuration.

Do not use an old blog as final evidence when official documentation exists.

# 30. Common Failure Modes

The verifier must actively watch for:

## 30.1 Answer-key anchoring

Seeing the stored answer causes the verifier to rationalize it.

Mitigation:

Independent solving before seeing the key.

---

## 30.2 Verbosity bias

Longer explanation appears more correct.

Mitigation:

Judge claims, not writing quality.

---

## 30.3 Position bias

Option A/B/C/D receives systematic preference.

Mitigation:

Reason from content.

For repeated verification, randomize option ordering.

---

## 30.4 Authority hallucination

The verifier invents a paper, URL, or specification.

Mitigation:

Never fabricate evidence.

Every cited source must actually support the claim.

---

## 30.5 Confirmation search

The verifier searches only for support.

Mitigation:

Always perform a refutation search for uncertain/high-risk claims.

---

## 30.6 Model-memory overconfidence

The model "remembers" an implementation detail incorrectly.

Mitigation:

Use current primary documentation.

---

## 30.7 Explanation contamination

The explanation contains the answer and causes the verifier to accept it.

Mitigation:

When practical, independently solve before reading explanation.

---

## 30.8 Benchmark confusion

A paper reports a result under specific conditions and the question turns it
into a universal claim.

Mitigation:

Check experimental setup and scope.

---

## 30.9 Theory / implementation confusion

A theoretical property is presented as an implementation guarantee.

Mitigation:

Separate:

```text
theory
algorithm
implementation
benchmark
```

---

# 31. Batch Verification

Do not verify the entire question bank with the same expensive process
unconditionally.

Use risk-based escalation.

## Tier A — Deterministic preflight

All questions.

Detect:

* malformed question
* invalid option indexes
* missing answers
* empty explanation
* suspicious claim markers
* math notation
* version/API terms
* absolute claims
* numeric claims

---

## Tier B — Semantic verification

High-risk questions first.

Priority:

1. mathematics
2. theorem / proof claims
3. answer-key disagreement
4. complexity
5. API / implementation
6. current model behavior
7. recent research
8. security
9. strong universal claims
10. random calibration sample

---

## Tier C — Independent second verifier

Use when:

* P0 suspected
* confidence < 0.85
* evidence conflict
* answer disagreement
* multiple plausible options
* theorem/math is non-trivial
* current implementation behavior is uncertain

---

## Tier D — Human review

Escalate:

```text
persistent disagreement
insufficient evidence
conflicting authoritative sources
subtle mathematical issue
ambiguous question intent
```

Maintain a small verified set of representative questions.

Recommended categories:

```text

ML theory
agents
systems
API/version-sensitive
multiple-choice

```

The gold set is used to calibrate the verifier.

```text

```

Start small.

# 34. Do Not Auto-edit

Version 1 of this skill MUST be report-only.

It may recommend:

```text
FIX ANSWER KEY
FIX OPTION
ADD ASSUMPTION
REWRITE CLAIM
UPDATE SOURCE
REMOVE QUESTION
```

It must NOT directly edit the question bank.

Reason:

Semantic verification can itself be wrong.

A wrong automated repair can turn one defect into a silent data corruption.

Future repair automation may be introduced as a separate skill.

---

# 35. Relationship With Existing Quality Skill

Existing skill:

```text
skills/check-question-bank-quality/SKILL.md
```

continues to own:

```text
schema
structure
coverage
duplicates
assessment quality
wording
distractors
retrieval readiness
```

This skill owns:

```text
factual correctness
mathematical correctness
logical correctness
technical correctness
answer-key correctness
explanation correctness
version correctness
```

Do not merge the responsibilities.

The overall quality pipeline is:

```text
                 Question
                     │
           ┌─────────┴─────────┐
           │                   │
           ▼                   ▼
  check-question-bank    verify-question-correctness
           │                   │
           │                   │
           ▼                   ▼
  assessment quality      truth / logic
           │                   │
           └─────────┬─────────┘
                     ▼
                Human review
```

---

# 36. Exit Criteria

A question can be marked `VERIFIED` only when:

1. independent solving agrees with the stored answer
2. every option is accounted for
3. material claims have no unresolved contradiction
4. assumptions required for the answer are present or harmless
5. explanation is consistent with the answer
6. required evidence has been checked
7. confidence is high enough for the risk level

Otherwise:

```text
CONDITIONAL
NEEDS_REVIEW
INCORRECT
```

---

# 37. Failure Policy

Never invent:

* citations
* equations
* benchmarks
* API behavior
* paper results
* model capabilities
* implementation details

When evidence is unavailable:

```text
INSUFFICIENT
```

is better than a fabricated answer.

When evidence conflicts:

```text
CONFLICTING
```

is better than silently choosing one.

---

# 38. Final Human Review Rule

A verifier report is evidence, not absolute truth.

Human review remains mandatory for:

* P0
* conflicting authoritative sources
* high-impact questions
* unresolved mathematical disputes
* persistent verifier disagreement

The system should optimize for:

```text
low false-negative rate on material correctness errors
```

without pretending that automated verification is infallible.

# 2. 配套脚本：`scripts/verify-question-candidates.ts`

这个脚本我建议不要直接调用 LLM。

它只做一件事：

> 从整个题库中筛出“最值得进行 correctness verification 的题”，并产生一个稳定的 JSONL worklist。

这样可以把昂贵的 Agent/Web verification 和 deterministic scanning 分开。

```ts
#!/usr/bin/env npx tsx

/**
 * Build a correctness-verification worklist for the question bank.
 *
 * This script intentionally does NOT decide whether a question is correct.
 * It performs deterministic risk detection and emits candidates for the
 * verify-question-correctness Agent Skill.
 *
 * Usage:
 *
 *   npx tsx scripts/verify-question-candidates.ts
 *
 *   npx tsx scripts/verify-question-candidates.ts \
 *     --output reports/question-correctness-worklist.jsonl
 *
 *   npx tsx scripts/verify-question-candidates.ts \
 *     --min-risk high
 */

import fs from "node:fs";
import path from "node:path";

type QuestionFormat = "single" | "multiple" | "open";

interface QuestionLike {
  id?: string;
  category?: string;
  topic?: string;
  subtopic?: string;
  difficulty?: string;
  angle?: string;
  cognitiveTask?: string;
  question?: string;
  explanation?: string;
  concepts?: {
    core?: string[];
    supporting?: string[];
  };
  formats?: {
    choice?: {
      type?: "single" | "multiple";
      options?: string[];
      answer?: number[];
    };
    open?: {
      referenceAnswer?: string;
    };
  };
}

interface Candidate {
  id: string;
  file: string;
  format: QuestionFormat;
  riskScore: number;
  priority: "P0" | "P1" | "P2";
  reasons: string[];
  metadata: {
    category?: string;
    topic?: string;
    difficulty?: string;
    angle?: string;
    cognitiveTask?: string;
  };
}

const ROOT = process.cwd();

const DEFAULT_QUESTION_DIRS = [
  path.join(ROOT, "src/data/questions"),
  path.join(ROOT, "src/data"),
];

const ABSOLUTE_PATTERNS: RegExp[] = [
  /\balways\b/i,
  /\bnever\b/i,
  /\bguarantee(?:s|d)?\b/i,
  /\bmust\b/i,
  /\bcannot\b/i,
  /\bonly\b/i,
  /\bexactly\b/i,
  /\bbest\b/i,
  /\boptimal\b/i,
  /\bequivalent\b/i,
  /\bnecessarily\b/i,
  /\bfor all\b/i,
  /\bin every case\b/i,
  /\beliminat(?:e|es|ed)\b/i,
  /\bprevent(?:s|ed)?\b/i,
];

const MATH_PATTERNS: RegExp[] = [
  /\bO\([^)]+\)/,
  /\bTheta\([^)]+\)/i,
  /\bΩ\([^)]+\)/,
  /\brank\b/i,
  /\beigenvalue\b/i,
  /\beigenvector\b/i,
  /\bgradient\b/i,
  /\bderivative\b/i,
  /\bconvergence\b/i,
  /\bprobability\b/i,
  /\bvariance\b/i,
  /\bexpectation\b/i,
  /\bentropy\b/i,
  /\bKL\b/i,
  /\bdivergence\b/i,
  /\bmatrix\b/i,
  /\btheorem\b/i,
  /\bproof\b/i,
  /\\[a-zA-Z]+/,
  /\^2/,
  /∑|∏|∫|≤|≥|≠|∀|∃/,
];

const VERSION_PATTERNS: RegExp[] = [
  /\bversion\b/i,
  /\bv\d+\.\d+(?:\.\d+)?\b/i,
  /\bdefault\b/i,
  /\bdeprecated\b/i,
  /\bAPI\b/,
  /\bSDK\b/i,
  /\bframework\b/i,
  /\blibrary\b/i,
  /\bPyTorch\b/i,
  /\bTensorFlow\b/i,
  /\bLangChain\b/i,
  /\bLangGraph\b/i,
  /\bOpenAI\b/i,
  /\bAnthropic\b/i,
  /\bGemini\b/i,
  /\bDeepSeek\b/i,
  /\bMCP\b/,
];

const QUANTITATIVE_PATTERNS: RegExp[] = [
  /\b\d+(?:\.\d+)?\s*%/,
  /\b\d+(?:\.\d+)?\s*(?:ms|s|GB|MB|TB|M|B|million|billion)\b/i,
  /\b\d+(?:\.\d+)?x\b/i,
  /\b\d+(?:\.\d+)?\s*times?\b/i,
];

const AI_CLAIM_PATTERNS: RegExp[] = [
  /\bRAG\b/i,
  /\bLoRA\b/i,
  /\bQLoRA\b/i,
  /\bRLHF\b/i,
  /\bDPO\b/i,
  /\bKV cache\b/i,
  /\battention\b/i,
  /\bTransformer\b/i,
  /\bagent\b/i,
  /\btool calling\b/i,
  /\bfunction calling\b/i,
  /\breasoning\b/i,
  /\bchain[- ]of[- ]thought\b/i,
  /\bhallucination\b/i,
  /\bembedding\b/i,
  /\bquantization\b/i,
];

function parseArgs() {
  const args = process.argv.slice(2);

  let output = path.join(
    ROOT,
    "reports/question-correctness-worklist.jsonl",
  );

  let minRisk: "low" | "medium" | "high" = "low";

  for (let i = 0; i < args.length; i++) {
    const arg = args[i];

    if (arg === "--output") {
      const value = args[i + 1];
      if (!value) {
        throw new Error("--output requires a path");
      }
      output = path.resolve(ROOT, value);
      i++;
      continue;
    }

    if (arg === "--min-risk") {
      const value = args[i + 1];
      if (value !== "low" && value !== "medium" && value !== "high") {
        throw new Error("--min-risk must be low, medium, or high");
      }
      minRisk = value;
      i++;
      continue;
    }
  }

  return {
    output,
    minRisk,
  };
}

function collectJsonFiles(dir: string): string[] {
  if (!fs.existsSync(dir)) {
    return [];
  }

  const result: string[] = [];

  for (const entry of fs.readdirSync(dir, { withFileTypes: true })) {
    if (
      entry.name === "node_modules" ||
      entry.name.startsWith(".") ||
      entry.name === "archive"
    ) {
      continue;
    }

    const fullPath = path.join(dir, entry.name);

    if (entry.isDirectory()) {
      result.push(...collectJsonFiles(fullPath));
      continue;
    }

    if (entry.isFile() && entry.name.endsWith(".json")) {
      result.push(fullPath);
    }
  }

  return result;
}

function loadQuestions(file: string): QuestionLike[] {
  const raw = JSON.parse(fs.readFileSync(file, "utf8"));

  if (Array.isArray(raw)) {
    return raw.filter(isQuestionLike);
  }

  if (raw && typeof raw === "object") {
    if (Array.isArray(raw.questions)) {
      return raw.questions.filter(isQuestionLike);
    }

    if (isQuestionLike(raw)) {
      return [raw];
    }
  }

  return [];
}

function isQuestionLike(value: unknown): value is QuestionLike {
  if (!value || typeof value !== "object") {
    return false;
  }

  const q = value as Record<string, unknown>;

  return typeof q.id === "string" && typeof q.question === "string";
}

function detectFormat(question: QuestionLike): QuestionFormat {
  if (question.formats?.choice) {
    return question.formats.choice.type === "multiple"
      ? "multiple"
      : "single";
  }

  return "open";
}

function getQuestionText(question: QuestionLike): string {
  const optionText =
    question.formats?.choice?.options?.join("\n") ?? "";

  const referenceAnswer =
    question.formats?.open?.referenceAnswer ?? "";

  return [
    question.question ?? "",
    optionText,
    question.explanation ?? "",
    referenceAnswer,
  ].join("\n");
}

function addReason(
  reasons: string[],
  score: { value: number },
  message: string,
  points: number,
) {
  reasons.push(message);
  score.value += points;
}

function inspectQuestion(
  question: QuestionLike,
  file: string,
): Candidate | null {
  if (!question.id || !question.question) {
    return null;
  }

  const text = getQuestionText(question);

  const reasons: string[] = [];
  const score = { value: 0 };

  if (ABSOLUTE_PATTERNS.some((pattern) => pattern.test(text))) {
    addReason(
      reasons,
      score,
      "contains universal/absolute wording",
      5,
    );
  }

  if (MATH_PATTERNS.some((pattern) => pattern.test(text))) {
    addReason(
      reasons,
      score,
      "contains mathematical/theoretical claims",
      6,
    );
  }

  if (VERSION_PATTERNS.some((pattern) => pattern.test(text))) {
    addReason(
      reasons,
      score,
      "contains version/API/implementation-sensitive claims",
      6,
    );
  }

  if (QUANTITATIVE_PATTERNS.some((pattern) => pattern.test(text))) {
    addReason(
      reasons,
      score,
      "contains quantitative/performance claims",
      5,
    );
  }

  if (AI_CLAIM_PATTERNS.some((pattern) => pattern.test(text))) {
    addReason(
      reasons,
      score,
      "contains AI/ML/LLM implementation or behavior claims",
      4,
    );
  }

  if (
    question.formats?.choice?.type === "single" &&
    (question.formats.choice.answer?.length ?? 0) !== 1
  ) {
    addReason(
      reasons,
      score,
      "single-choice answer cardinality requires verification",
      20,
    );
  }

  if (
    question.formats?.choice &&
    question.formats.choice.answer &&
    question.formats.choice.options &&
    question.formats.choice.answer.some(
      (index) =>
        index < 0 ||
        index >= question.formats!.choice!.options!.length,
    )
  ) {
    addReason(
      reasons,
      score,
      "answer index is structurally invalid",
      30,
    );
  }

  if (!question.explanation?.trim()) {
    addReason(
      reasons,
      score,
      "missing explanation/reference explanation",
      3,
    );
  }

  if (
    question.difficulty === "hard" ||
    question.difficulty === "expert"
  ) {
    addReason(
      reasons,
      score,
      "high-difficulty question",
      3,
    );
  }

  if (score.value === 0) {
    return null;
  }

  let priority: Candidate["priority"];

  if (score.value >= 15) {
    priority = "P0";
  } else if (score.value >= 8) {
    priority = "P1";
  } else {
    priority = "P2";
  }

  const relativeFile = path.relative(ROOT, file);

  return {
    id: question.id,
    file: relativeFile,
    format: detectFormat(question),
    riskScore: score.value,
    priority,
    reasons,
    metadata: {
      category: question.category,
      topic: question.topic,
      difficulty: question.difficulty,
      angle: question.angle,
      cognitiveTask: question.cognitiveTask,
    },
  };
}

function minimumScore(
  minRisk: "low" | "medium" | "high",
): number {
  switch (minRisk) {
    case "high":
      return 15;
    case "medium":
      return 8;
    case "low":
    default:
      return 1;
  }
}

function main() {
  const { output, minRisk } = parseArgs();

  const jsonFiles = Array.from(
    new Set(DEFAULT_QUESTION_DIRS.flatMap(collectJsonFiles)),
  ).sort();

  const candidates: Candidate[] = [];

  let questionCount = 0;

  for (const file of jsonFiles) {
    let questions: QuestionLike[];

    try {
      questions = loadQuestions(file);
    } catch (error) {
      console.warn(
        `[warn] failed to parse ${path.relative(ROOT, file)}:`,
        error,
      );
      continue;
    }

    for (const question of questions) {
      questionCount++;

      const candidate = inspectQuestion(question, file);

      if (!candidate) {
        continue;
      }

      if (candidate.riskScore < minimumScore(minRisk)) {
        continue;
      }

      candidates.push(candidate);
    }
  }

  candidates.sort((a, b) => {
    if (b.riskScore !== a.riskScore) {
      return b.riskScore - a.riskScore;
    }

    return a.id.localeCompare(b.id);
  });

  fs.mkdirSync(path.dirname(output), { recursive: true });

  fs.writeFileSync(
    output,
    candidates.map((candidate) => JSON.stringify(candidate)).join("\n") +
      (candidates.length ? "\n" : ""),
    "utf8",
  );

  const p0 = candidates.filter((c) => c.priority === "P0").length;
  const p1 = candidates.filter((c) => c.priority === "P1").length;
  const p2 = candidates.filter((c) => c.priority === "P2").length;

  console.log("");
  console.log("Question Correctness Verification Worklist");
  console.log("------------------------------------------");
  console.log(`Question files: ${jsonFiles.length}`);
  console.log(`Questions scanned: ${questionCount}`);
  console.log(`Candidates: ${candidates.length}`);
  console.log(`P0 candidates: ${p0}`);
  console.log(`P1 candidates: ${p1}`);
  console.log(`P2 candidates: ${p2}`);
  console.log(`Output: ${path.relative(ROOT, output)}`);
  console.log("");
}

main();
````

You are a technical correctness verifier for an AI engineering interview

MANDATORY PROCEDURE:

11. For mathematical claims, derive the result and attempt counterexamples.
12. For API/model/version claims, verify current authoritative documentation.

15. If evidence conflicts, report CONFLICTING.
16. Do not modify the question.

QUESTION:

<question-json>

Return JSON matching the verify-question-correctness schema exactly.

# 6. 我建议再加一个非常关键的约束

对于 choice question，Agent 不应该只输出：

```json
{
  "correct": [1, 3]
}
```

而必须输出：

```json
{
  "options": [
    {
      "index": 0,
      "status": "REFUTED",
      "reason": "..."
    },
    {
      "index": 1,
      "status": "SUPPORTED",
      "reason": "..."
    },
    {
      "index": 2,
      "status": "CONDITIONAL",
      "reason": "..."
    },
    {
      "index": 3,
      "status": "REFUTED",
      "reason": "..."
    }
  ]
}
```

这是整个设计里非常重要的一点。

因为真正危险的错误经常不是：

```text
正确答案明显错了
```

而是：

```text
官方答案 A
但 C 在某个合理条件下其实也是对的
```

这种错误普通的 `questionChallenger` 很容易漏掉。

---

# 7. 与现有 `questionChallenger` 的职责边界

最终建议固定成：

| 模块                            | 判断什么       |
| ----------------------------- | ---------- |
| Schema                        | 格式是否正确     |
| Deterministic validation      | 数据契约是否正确   |
| Heuristic detector            | 有没有可疑信号    |
| `questionChallenger`          | 是不是一题好的面试题 |
| `verify-question-correctness` | 题目本身是否正确   |
| Human review                  | 对争议问题最终拍板  |

即：

```text
Good Question ≠ Correct Question
```

一题完全可能：

```text
结构优秀
难度合适
distractor 很好
assessment 合理

但是答案错了
```

你之前题库里已经出现过这种真实情况，尤其是数学问题：deterministic gate 和现有 detector 都通过，但人工复核才发现 theorem / rank / counterexample 层面的错误。因此这个新 Skill 的价值非常明确。

# 8. 不建议现在增加的东西

当前阶段我明确不建议加入：

```text
Knowledge Graph fact checker
ontology
claim/evidence database
自动修复 Agent
自动重写错误题
复杂 provenance system
独立 fact-checking service
专门向量数据库
全题库每次都联网验证
```

现在只需要：

```text
question bank
    ↓
candidate scanner
    ↓
correctness verifier
    ↓
evidence
    ↓
review report
```

先证明它能抓到真实错误，再决定是否需要进一步工程化。

尤其不要让它直接修改 1354 道题。当前最合理的是 **report-only → 观察误报/漏报 → 建 gold set → 再考虑 gate**。
